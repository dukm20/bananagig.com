# BananaGig: repository constitution

Local help, done fast. This file is the entry point for every Claude Code session. Keep it short; the details live in the files it points to. (`AGENTS.md` is generated by Turborepo; read it before touching `turbo.json`.)

## Start of every session / checkpoint

1. Read this file.
2. Read `docs/project/PROJECT_STATE.md` (current truth: what exists, what is next).
3. Read the relevant skills: `skills/infrastructure/SKILL.md`, `skills/database/SKILL.md`, `skills/api/SKILL.md`, `skills/web/SKILL.md`, `skills/worker/SKILL.md`, `skills/testing/SKILL.md`, `skills/identity/SKILL.md`, `skills/configuration/SKILL.md`.
4. Read relevant ADRs in `docs/architecture/` (index by number; the latest is named in PROJECT_STATE).
5. Read `docs/data/DATA_MODEL.md` (and `DATA_MODEL_GUARDRAILS.md`) before **any** persistence change.
6. Inspect the existing implementation before coding. Reuse; do not duplicate functionality because a request sounds new.
7. Run `pnpm checkpoint:start <ID>` (clean tree check, state, latest migration, relevant debt).

## Hard rules

- Work on the **active checkpoint only**. Stop before implementing future checkpoints.
- **Never edit an applied migration.** Fix forward with a new `db/migrations/NNNN_*.sql`.
- **Never hardcode configurable business values** (fees, prices, durations, windows, rates). They belong in product configuration data, not code or env.
- PostgreSQL is the authoritative store. Valkey, OpenSearch and NATS hold derived or in-flight data.
- Respect workspace boundaries (`pnpm deps:check`): web never imports database/platform; contracts import nothing from the workspace.
- API contracts: OpenAPI and AsyncAPI are generated from code; run `pnpm specs:generate`, never hand-edit `docs/api/openapi.yaml` or `docs/events/asyncapi.yaml`.
- No real secrets in git. `.env` and `.env.host` are never committed.
- Source code and config beat stale documentation: when they disagree, fix the document.
- Do not push, force-push, rewrite history, or commit unless the user asked for commits in the checkpoint.

## Data Model Review Gate (every persistence change)

Add a migration; update `DATA_MODEL.md`, `DATA_MODEL_CHANGELOG.md`, `DATA_DICTIONARY.md`, `ERD.md` (if relationships changed) and `NORMALIZATION_LOG.md` (1NF/2NF/3NF/BCNF review, duplicates, derived fields, denormalization, indexes); regenerate `docs/data/SCHEMA_SNAPSHOT.sql` with `pnpm schema:snapshot --write`. `pnpm data-model:check <ID>` enforces this.

## A checkpoint is NOT COMPLETE until Claude has

1. completed the requirements;
2. run the tests;
3. run the data-model review;
4. updated the data model if necessary;
5. updated the normalization log if the schema changed;
6. updated `docs/project/PROJECT_STATE.md` (current state only);
7. appended an entry to `docs/project/IMPLEMENTATION_HISTORY.md`;
8. recorded new technical debt in `docs/project/TECH_DEBT.md` (do not hide shortcuts in reports);
9. evaluated whether a skill needs updating (update the narrowest `SKILL.md` only when reusable knowledge was created; never to generate activity);
10. evaluated whether an ADR is required (only for real architecture decisions);
11. run `pnpm checkpoint:finalize <ID> --skill-update=UPDATED|NOT_REQUIRED`;
12. created the checkpoint commit with `pnpm checkpoint:commit <ID> "<type>(<ID>): <description>"` **if the user enabled commits** for this checkpoint.

Add a learning (`docs/project/LEARNINGS.md`) only for durable knowledge a future session would otherwise rediscover painfully, never for debugging noise.
