# Claude Code hooks (ENG-GOV-001)

Repository-level safeguards for the local Claude Code agent. They are wired in `.claude/settings.json` (committed) and implement the "Claude Code configuration model" of the Production Engineering Standard (`docs/engineering/PRODUCTION_STANDARD.md`): permissions and `PreToolUse` hooks guard risky operations and protected paths, `PostToolUse` / `Stop` hooks produce reminders and verification evidence.

**These hooks are a local guardrail against accidents, not a security boundary and not release enforcement.** They stop the common ways an agent (or a tired human driving one) destroys work, bypasses a gate or touches secrets, and they make that visible. They do not stop a determined actor: a command-text guard can always be argued around (see "What the hooks cannot see"). CI and the GitHub rulesets (required checks, review, branch protection) are the independent controls and do not depend on Claude or on these hooks. A passing hook proves nothing about the release.

## What is wired

| Event / matcher                                      | Script                        | Mode                             | Purpose                                                                                                                          |
| ---------------------------------------------------- | ----------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `PreToolUse` `Bash`                                  | `pre-bash.mjs` (+ `bash.mjs`) | blocking (deny / ask)            | tokenizes the command and evaluates every simple command                                                                         |
| `PreToolUse` `Edit\|Write\|MultiEdit\|NotebookEdit`  | `pre-edit.mjs`                | blocking (deny / ask) + advisory | applied migrations, secrets files, secret-looking content, gate/config files, disabled tests; advisory on lint/type suppressions |
| `PostToolUse` `Bash` and `PostToolUseFailure` `Bash` | `post-bash.mjs`               | advisory (records evidence)      | appends verification runs to `.claude/state/verify.json`                                                                         |
| `PostToolUse` `Edit\|Write\|MultiEdit`               | `post-edit.mjs`               | advisory                         | reminds to format/lint/typecheck/test after production-source edits and names the standard's risk class                          |
| `Stop`                                               | `stop.mjs`                    | advisory only (never blocks)     | warns when production source changed after the last successful recorded verification                                             |

Modules: `lib.mjs` (event I/O, paths, cached git, applied-migration index, secret/test/suppression/gate rules, evidence store), `shell.mjs` (shell parser and command normalisation), `bash.mjs` (the Bash analysis), `git-options.mjs` (git option tables). A failed Bash command is delivered by Claude Code as `PostToolUseFailure`, not `PostToolUse`, so `post-bash.mjs` is registered for both events.

`permissions` in `settings.json`: `deny` `Read`/`Edit` of `.env` and `.env.host` (bare names match at any depth; `.env.example` and `.env.host.example` are different file names and stay readable) and `ask` for `git push`, `git commit --amend`, `git rebase`, `git branch -D`, `docker compose down -v`, `pnpm stack:reset`, `docker volume rm|prune`, `docker system prune`. Permission rules for Bash match the command text as typed, so the hook repeats the important ones in a form that also catches `git -C dir push`, `sudo`, `env X=1`, `bash -c '...'`, and compound commands.

## Decision protocol

- The hooks read the JSON event from stdin (`hook_event_name`, `tool_name`, `tool_input`, `cwd`, `tool_response`, ...). They never grep raw text.
- Output is `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny"|"ask","permissionDecisionReason":"..."}}` with exit code 0. **Allow is silence**: the hooks never emit `allow`, because that would skip the normal permission prompt. Deny and ask rules in `settings.json` still apply on top of the hooks.
- Fail safe. For the blocking guards, malformed or empty input, missing `tool_input.command` / `file_path`, a parse failure, a time-budget overrun, or an internal error produces an **ask** decision, never an allow. The two guards are also registered with `"onFailure": "block"` (Claude Code 2.1.295+), so a crash, non-zero exit or timeout of the guard blocks the call instead of letting it through (see RECOVERY below for what that means when a hook is itself broken). Advisory hooks print a message on stderr and exit 1 (a non-blocking hook error) and never block.
- Most severe wins: deny > ask > silent allow, across all simple commands of a compound command. Every reason is listed.
- Scripts are re-executed on every tool call, so **edits to a hook script take effect immediately** (they are not snapshotted at session start). Only the wiring in `settings.json` is read when Claude Code loads its settings.
- Time budget: the Bash analysis gives up after 8 s, 4000 commands, 400 000 characters or 60 git calls and asks. Git answers are cached per run (the applied-migration index costs two git calls however many files a command names).

## pre-bash decisions (`pre-bash.mjs`, `bash.mjs`)

The tokenizer handles quotes and escapes, ANSI-C `$'\x67it'` strings (decoded), brace expansion (`-{f,}`, `--{hard,soft}`, `{1..3}`, capped), `; && || | |& &` and newlines, `( )` groups, `$(...)`, backticks and `<(...)` as nested command lists, redirections, here-documents (the bodies of **unquoted** here-documents are scanned for `$(...)` / backticks, because the shell runs them) and here-strings, comments, leading `VAR=x`, and these wrappers: `env`, `sudo`/`doas`, `su -c`, `command`, `exec -a`, `nohup`, `time`, `timeout`, `nice`/`ionice`, `arch`, `xcrun`, `flock`, `chroot`, `watch`, `ssh host '...'`, `xargs`, `npx`, `pnpm exec`, path-qualified executables, `git -C dir -c k=v ...` (including `-c alias.x=...`), and it recurses into `bash|sh|zsh|dash|ksh|fish -c '...'` (also after `--rcfile F` / `--init-file F`), `eval`, `docker|kubectl exec ... sh -c '...'`, `find -exec`, and scripts fed to a shell by heredoc, here-string, a readable file, or a literal `echo`/`printf`/`cat` pipe (`echo 'git reset --hard' | bash`, `bash <(echo ...)`). Only the executed command name is matched, so `echo "git reset --hard"` and `grep -r 'git push --force' docs` are silent.

git long options on `reset commit clean push add rebase branch checkout restore merge am cherry-pick` are **canonicalised against the real option list** of the installed git (`git <sub> -h`, with a static snapshot as fallback) by unique prefix, so `--har`, `--no-verif`, `--forc`, `--delet`, `--mirro`, `--amen` are treated as `--hard`, `--no-verify`, `--force`, ... An option that is not an exact option or a unique prefix, or is ambiguous, asks.

DENY: `git push` with `--force`, `-f`, `--force-with-lease`, `--force-if-includes`, `--delete`, `-d`, `--mirror`, `--prune`, `+refspec`, `:refspec`; `git reset --hard`; `git clean -f*`; `git checkout`/`git restore` of the whole tree (`.`, `:/`, `*`; `git restore --staged .` is allowed); `--no-verify` on commit, push, merge, rebase, am, cherry-pick, and `git commit -n`; hook bypass through `git -c core.hooksPath=...`, `--config-env=core.hooksPath=...`, `GIT_CONFIG_PARAMETERS` / `GIT_CONFIG_KEY_n`, `HUSKY=0`; `git config --global|--system` writes (reads are allowed); `curl|wget ... | sh|bash`, `sh -c "$(curl ...)"`, `bash <(curl ...)`, `eval`/`source` of a download; `chmod -R 777` and equivalents; `rm` of `.git` itself; recursive `rm` of `/`, `~`, `$HOME`, `.`, `..`, `*` in the repository root, the repository root, any parent of the root or of the home directory, the `db` / `db/migrations` directories, and top-level system directories (a literal `rm -rf .` after a literal `cd` into a build-output directory such as `dist` is allowed); `rm --no-preserve-root`; any shell write to `.env` / `.env.host` (redirect, `tee`, `sed -i`, `perl -pi`, `cp`, `mv`, `install`, `ln`, `dd of=`, `truncate`, also through a symlink); `git add -f .env`; shell edits that touch an **applied** migration: redirect, `tee`, `sed -i`, `rm`, `mv`, `git rm|mv`, `cp`/`mv`/`rsync`/`ln`/`install` of a file whose basename is an applied migration into `db/migrations` (directory destinations and `-t DIR` are resolved per source, through relative, absolute and symlinked paths, with globs expanded), and `git apply` / `patch` whose readable patch names one.

ASK: any `git push` (a `--dry-run` is silent), `git commit --amend`, `git rebase`, `git branch -D` / `-f`, `git checkout|switch --force`, `git filter-branch|filter-repo`, `git reflog expire|delete`, `git update-ref -d`, `git send-pack --force`; `docker compose down -v|--volumes`, `pnpm stack:reset`, `docker volume rm|prune`, `docker system prune`, `docker rm -v`; destructive SQL (`DROP DATABASE|SCHEMA|TABLE`, `TRUNCATE`, `dropdb`, `pg_restore --clean`) in a `psql` command, a pipeline feeding it, a heredoc, or a readable `-f` / `<` / `cat` SQL file, unless the database is a throwaway (`bananagig_t_*`, `*_review`, `*_test`) **on a local host** (no host, `localhost`, `127.0.0.1`, a socket directory, or a compose service name); any pipe into a shell interpreter whose text the guard cannot read, a process substitution it cannot read, a script file it cannot read; **any argument that names `.env` / `.env.host`** (by name, case-insensitively on case-insensitive file systems, by a glob that could match them such as `.en*` or `.e?v`, through a symlink, or produced by a `$(echo ...)` substitution) for every command except a short safe list (`ls test [ stat wc file echo printf chmod touch ... git check-ignore|status|ls-files|add|rm`); `--env-file .env.host` options and the pattern argument of `grep`/`sed`/`awk` are not file operands; `source` and `.` count as readers; `cp .env.example .env` and `cp .env.host.example .env.host` (the documented first-run bootstrap) ask with a message saying so; `node -e` / `python -c` / `perl -e` programs that mention `.env`, `db/migrations`, `.claude/` or `.github/`; shell writes (redirect, `tee`, `sed -i`, `cp`, `mv`, `rm`, `perl -pi`, `ed`, `truncate`, `dd of=`, `git rm|mv`) to **gate files** (the same list as pre-edit below) and in-place edits or redirects to **test files**; `xargs` / `find -exec` running a file-writing command (`sed -i`, `tee`, `rm`, `mv`, `cp`, ...) on paths that could include migrations or secrets files; a new migration not numbered after the latest committed one, or whose destination cannot be resolved; deploy/release commands: `gh pr merge`, `gh release create|delete|...` (not `list|view|download`), `gh workflow run`, `gh secret set|delete`, `gh api` with a non-GET method or fields, `curl|wget -X POST|PUT|PATCH|DELETE` to the GitHub API or a `/merge` endpoint, `kubectl apply|delete|replace|patch|rollout|scale|create`, `helm install|upgrade|uninstall|rollback`, `terraform|tofu apply|destroy|import`, `fly deploy|launch|destroy|scale|secrets`, `vercel|netlify ... --prod`, `wrangler deploy`, `docker push`, `npm|pnpm|yarn publish|unpublish|deprecate`, deploy/release scripts; and any command the tokenizer cannot parse or finish within the budget.

Everything else is silent (normal permission flow).

## pre-edit decisions (`pre-edit.mjs`)

DENY: editing or overwriting an **applied** migration (`db/migrations/*.sql` present in `HEAD` or anywhere in git history, including one deleted later); writing `.env` or `.env.host` anywhere, through a symlink, or (on case-insensitive file systems) with another capitalisation; new content containing a private key header, an AWS access key id or secret-key assignment, a GitHub (`ghp_` ... / `github_pat_`), Stripe live, Slack, Anthropic (`sk-ant-`), Google (`AIza`), npm, SendGrid or JSON Web token, or a database URL with an embedded non-placeholder password for a non-local host. Secrets are looked for in the **post-edit file** (MultiEdit edits applied in order, so a token split across edits is seen) after stripping zero-width characters, and only tokens the edit **adds** count.

The `secret-scan:allow` line marker is **not** self-service: it is honoured silently only when the file is a test or fixture file (`*.test.*`, `*.itest.*`, `*.spec.*`, `__tests__`, `tests`, `fixtures`, `packages/testing`) **and** the token is obviously fake (contains `fake`, `example`, `dummy`, `test`, a long run of one character, ...). A marker anywhere else makes the guard ASK instead of allowing.

ASK: a new migration that is not numbered after the latest committed one, or not named `NNNN_name.sql`, or when git cannot say; other `.env.*` files that are not `*.example|sample|template`; gate/config files: `.github/**`, `.claude/**` except `.claude/state/**`, `.git/**` (not `*.lock`), `.gitleaks.toml`, `CODEOWNERS`, `.gitignore`, `.prettierrc*`, `.prettierignore`, every `package.json`, `eslint.config.*`, `tsconfig*.json`, `vitest*.{ts,js,mjs}`, `turbo.json`, `Dockerfile*`, `compose*.y(a)ml`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `redocly.yaml`, `scripts/check-boundaries.mjs`, `scripts/*-check.mjs`, `scripts/governance*`, `scripts/migrate.mjs`, `scripts/generate-specs.mjs`, `scripts/claude-hooks.test.mjs`, `docs/engineering/TEMPORARY_MITIGATIONS.md`; a test file whose edit adds `.skip` / `.only` / `.fails` / `.todo` / `.skipIf` / `.runIf` (calls, references, `.each` forms, `it['skip']`), `{ skip: true }`, `xit(`, `xdescribe(`, `fit(`, ... on a non-comment line (counted against the text being replaced, so editing next to an existing one is not blocked, and moving a commented-out skip into code is caught); the same files are recognised under `__tests__/`, `tests/` and `packages/testing/`.
ADVISORY (`additionalContext`, no block): a new TypeScript ignore/nocheck directive or lint-disable directive without a stated reason.

"Applied" means committed. A new migration that is untracked or only staged is still editable, so the author can finish it; once committed it is immutable. The hook cannot see which migrations a particular database has applied (`schema_migrations`); git is the offline approximation, which is also what CI checks.

## Verification evidence (post-bash, stop)

`post-bash.mjs` records `pnpm test|lint|typecheck|format:check|build|test:integration|specs:check|deps:check|smoke|checkpoint:finalize` (and `data-model:check`, `openapi:lint`, `asyncapi:validate`, `identity:check`, `pnpm --filter ... test`, `pnpm -r ...`, `npx|pnpm exec vitest`, `tsc --noEmit`, `eslint`, `prettier --check`, `turbo run <task>`) into `.claude/state/verify.json` (git-ignored, last 50 entries): command, class, `status`, `exit` (when Claude Code supplies it), timestamp, session id.

`status` is `passed` only when Claude Code delivered the call as a successful `PostToolUse` **and** the command shape makes its exit status trustworthy. `failed` / `interrupted` come from `PostToolUseFailure`, an `interrupted` response or a non-zero exit field. Everything uncertain is `unknown`, never `passed`: a pipe without `set -o pipefail` (`pnpm test | tail` reports `tail`'s status), `|| true`, a `;`-chain after the command, a background run, control flow (`if pnpm test; then`), and a green exit whose output says no tests ran ("No test files found", "No projects matched the filters"). `--help`, `--version` and `--listTests` runs are not recorded at all. To record evidence, run the command plainly (`pnpm test`, `pnpm lint && pnpm typecheck`).

`stop.mjs` looks at modified and untracked production-source files (`git status`) and requires a recorded `passed` run of each of `format:check`, `lint`, `typecheck` and a test class (`test`, `test:*`, `vitest`) **newer than the latest change** (file mtime). If any is missing it prints a `systemMessage` ("changes were made after the last recorded successful verification: report as NOT VERIFIED" when something changed after the last pass, otherwise "the verification recorded since the latest change is incomplete"), listing the files and the missing classes. A lone passing `pnpm lint` therefore does not clear the warning. It never blocks, returns immediately when `stop_hook_active` is true, and warns once per (session, change set, missing set). The warning is shown to the user; the agent is not made to continue. Recorded evidence is a convenience for honest reporting. It does not prove the code is correct and is not a gate.

## How to test

```
npx vitest run scripts/claude-hooks.test.mjs     # also part of `pnpm test` (vitest run scripts)
echo '{"tool_name":"Bash","tool_input":{"command":"git reset --hard"},"cwd":"'"$PWD"'"}' | CLAUDE_PROJECT_DIR="$PWD" node .claude/hooks/pre-bash.mjs
```

The tests spawn each script with the structured event, assert the exact JSON and exit code, build throwaway git repositories for the migration, status and verification cases (including symlinks and case-insensitive-file-system behaviour through `BANANAGIG_HOOKS_ASSUME_CASE_INSENSITIVE=1`), check that every entry script links all of its imports, and build credential-looking strings at runtime. Add a table row for every new rule and for every false positive you fix.

## False positives and legitimate exceptions

1. The reason string names the rule. If the command is legitimate and the decision is **ask**, approve it in the permission prompt (the user's decision, once).
2. If it is **deny** and the action is truly intended, the user runs it themselves in their terminal, or asks Claude to do it a different safe way (for example `git push --force-with-lease` is denied; the user pushes). Hooks cannot be approved around by the agent.
3. If the rule is wrong (a false positive that will recur), change the hook **with review**: edit the module, add the false-positive case to `scripts/claude-hooks.test.mjs`, run the test, and get the change reviewed like any production change. Edits to `.claude/**` themselves trigger an ask (self-protection); review them in every pull request.
4. A deliberate fake credential in a test fixture carries `secret-scan:allow` on the same line, in a test/fixture file, and looks fake. A genuinely new class of secret is added to `SECRET_PATTERNS` in `lib.mjs`.
5. Do not widen a rule by keyword. Match structure (executable, subcommand, option) as the existing rules do.

Known intentional asks that look like false positives: `cp .env.example .env` (bootstrap), `echo it's` (an unterminated quote is a shell syntax error), reading `.env` by any tool, every `git push`, a pipe into `bash` from anything but a literal `echo`/`printf`/`cat`, an ambiguous abbreviated git option, and the rare `rm -rf .` outside a build-output directory.

## RECOVERY: a broken hook can lock the session out

The two guards are fail-closed (`onFailure: "block"`) and editing `.claude/**` asks. If a hook script has a syntax error, a missing import, or a bug that makes it crash, **every Bash, Write and Edit call is blocked, including the call that would repair it**. Only a human can recover:

1. Restore a known-good copy from a backup you took before the change (`cp -R <backup>/hooks/. .claude/hooks/`), or `git checkout -- .claude/hooks` once the hooks are committed.
2. Or switch hooks off for this checkout while you fix them: create `.claude/settings.local.json` (git-ignored) containing `{"disableAllHooks": true}`, repair the scripts, run `npx vitest run scripts/claude-hooks.test.mjs`, delete the file.
3. Or use `/hooks` in an interactive session to disable the hook entries.

Rule for changing hooks: build and test the complete new set in a scratch copy first (the test file needs only `.claude/`, `scripts/claude-hooks.test.mjs`, a `.gitignore` and `node_modules`), take a backup of the live `.claude/hooks`, then swap the whole set in with one `cp` and immediately run the tests and an import check (`node .claude/hooks/pre-bash.mjs </dev/null` must print an ask decision, not a SyntaxError). Never overwrite one module of a live set in place.

## What the hooks cannot see (out of scope, by design)

- Anything outside the tool events: the user's own terminal, other editors, `--bare`, `bypassPermissions` / `--dangerously-skip-permissions` modes, `.claude/settings.local.json` with `disableAllHooks`, tools that run code but are not matched (`Monitor`, MCP servers, subagents with their own settings).
- Shell features the tokenizer does not model: variables and `IFS` tricks (`F=--force; git push $F`, `git${IFS}reset`), aliases and functions defined elsewhere, `source`d scripts, `curl -o x.sh && sh x.sh` (download then run), globs that expand to a protected name outside the literal patterns above, and `cat dump.sql | psql` when the file is unreadable.
- Programs run for their side effects: `node -e` / `python -c` / `perl -e` / `awk 'BEGIN{system(...)}'` are only checked for mentions of protected paths, not interpreted; `find -delete`, `rsync --delete`, `git ci -n` style user aliases from `~/.gitconfig`, `base64 -d | sh` (asks, not decoded), compression tools, `xargs` with computed arguments.
- Windows path quirks (trailing dots and spaces, 8.3 names).
- The relative-path checks assume `event.cwd` plus any `cd <literal>` earlier in the same command; a computed `cd` makes relative targets unknown (the literal `rm -rf .` / `..` is always refused outside a literal cd into a build-output directory).
- `.git`-based migration logic needs a working `git` and a readable history; a shallow clone may miss old, deleted migrations.
- A hook timeout or crash of an advisory hook is non-blocking by design. For the guards `onFailure: "block"` makes it blocking; if Node is unavailable the Bash and edit tools are refused until it is fixed (see RECOVERY).
- The Stop warning and `verify.json` are advisory and local (git-ignored). They cannot prove a verification covered the whole change (a filtered `pnpm --filter x test` is recorded as `test`; read the stored command).
- Schema facts were checked against Claude Code 2.1.302 and the official hooks and permissions documentation; the exact `tool_response` shape for an exit code is not documented, so success is inferred from the event type.
