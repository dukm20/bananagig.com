# ADR-0041 — Gig Templates are versioned, platform-owned structures: identity and frozen versions are separate, a provider Gig will reference the exact version, and the wording stays content

Status: ACCEPTED
Date: 2026-10-17
Checkpoint: CAT-002

## Context

The PRD builds a provider Gig from a service-type template: the "Activate" button opens the Gig builder prefilled from it (PR-03.02), the builder validates against "the template and limits" (PR-03 step 3), a Gig carries scope, time, price, geography, capacity and policies (PR-03.04), and publishing a change creates a new Gig version while confirmed bookings keep an immutable snapshot (PR-03.12, R-06). Administrators maintain Gig templates with activation flags and display order, and nothing appears unless an admin activated it (AD-01.03, AD-01.04); verification is configurable by category and market (SV-09.01). CAT-001 deliberately created NO version tables for the taxonomy (ADR-0040): a category or service type has a stable identity and its only history is status and availability. A template is different: its STRUCTURE changes over time (a new required field, other duration bounds) while Gigs built from an older structure must keep meaning what they meant. Seven questions had to be answered before any Gig table exists: what is identity and what is version data, how the version lifecycle works, how fields are modelled, where wording lives, how pricing and area models and trust requirements are represented without implementing them, how the hierarchy is enforced, and how a future Gig references a template.

## Decision

- **Identity and version are separate tables.** `catalog.gig_templates` holds only what never changes meaning: the immutable `code`, the immutable service type, the copy keys (name, optional description and instructions) and a status. `catalog.gig_template_versions` holds the structure: duration guidance, allowed pricing models, allowed service-area modes, plus the typed fields, options and requirement hooks in child tables. A rename or a wording change is a content change, never a new version.
- **A version is a draft until it is published, then it is frozen by the database.** `DRAFT` (editable, initial only) -> `ACTIVE` (published) | `RETIRED` (discarded); `ACTIVE` -> `SUPERSEDED` (set only as a consequence of publishing a newer version of the same template) | `RETIRED` (the database allows it, and the retirement of the template does it; the service offers no direct withdraw of an ACTIVE version: pause or retire the template); `SUPERSEDED` and `RETIRED` are terminal. Guards refuse any change of a published version's columns and any insert, update or delete of its field, option and requirement rows. A version is never deleted. At most one DRAFT and one ACTIVE version exist per template (partial unique indexes) and version numbers are contiguous (1, 2, 3), so the history reads without gaps. There is no `IN_REVIEW`: no reviewer role or workflow exists, so it would be a state nothing can reach; adding it later is a CHECK change.
- **The future Gig references `gig_template_versions.gig_template_version_id`.** CAT-003 will store that id on the provider Gig. Because a published version is immutable, the structure the Gig was built from can always be read back, whatever happens to the template afterwards. The id is exposed in the public and management reads and in the publication event.
- **Typed field definitions, not a JSON document.** `gig_template_fields` has a field type (text, long text, integer, decimal, boolean, enum, duration, money, media, equipment reference, skill reference), a behaviour (`PLATFORM_FIXED`, `PROVIDER_CONFIGURABLE`, `PROVIDER_REQUIRED`; "editable" and "required" are derived, never stored twice), a section for the builder, customer visibility, an order and typed metadata columns (lengths, numeric bounds and default, boolean default, item counts). A CHECK matrix makes every column that does not belong to the type NULL and refuses a fixed field without its default. Enum options are a child table. Money fields carry no numeric metadata: amount limits are configuration (CFG-001), not template data. A photo rule (optional, required, prohibited) is a media field with the item counts, not a separate column.
- **Wording is content, derived from the code and SHARED by all versions.** Name, description, instructions, labels, help, default texts and option labels are CFG-002 entries whose keys are derived from the template code and the field key; the database verifies the derivation (the template name is a generated column, the others are checked by the guard). A version freezes the structure; the wording keeps its own immutable, effective-dated history in the content registry. A field whose meaning changes gets a new field key. Publication requires every referenced key to be published as the content resolver reads it (an ACTIVE entry with a SCHEDULED, PUBLISHED or SUPERSEDED platform-scope version in force now in the platform default locale; the database guard is the backstop, the service names the missing keys).
- **Pricing and area models are closed sets stored as flags.** `FIXED` (the base price every Gig has), `FIXED_WITH_VARIANTS`, `BUNDLE_ELIGIBLE`, `DROP_ELIGIBLE`; `RADIUS`, `POSTAL_CODES`, `POLYGON` (PR-03.04). A CHECK requires at least one base pricing model and one area mode. This is metadata about what a later Gig may select; no price, floor price, radius or area is stored. Flags avoid two child tables and two guards for sets that change by migration anyway.
- **Requirements are hooks.** `gig_template_requirements` says a version needs a skill, equipment, licence, insurance or background check, with an optional opaque reference code that TRUST-001 will give a catalogue. Nothing validates the code and no verification logic lives here (SV-09 owns policy by category and market).
- **The hierarchy is enforced downwards at write time and checked upwards at read time.** A template is created only under a non-RETIRED service type, becomes ACTIVE only under an ACTIVE one, and a version is published only under an ACTIVE template and service type (FOR SHARE reads so concurrent changes serialize). The public read re-checks the service type, its category and their market rows. CAT-001 guards are NOT changed: pausing a service type never has to cascade into templates, and a template under a paused service type is simply not public. Retiring a template closes its ACTIVE version (so an ACTIVE version never sits under a RETIRED template) and is refused while a DRAFT exists (the service discards the draft first, audited).
- **Concurrency and stale drafts.** The service locks the template row first in every version operation, then the version row. A draft carries a `revision` that the service bumps on every change; a replace or a publish names the revision the administrator read and a different one is refused (`STALE_DRAFT`), so one administrator cannot overwrite or publish another's change. A replace carries the WHOLE definition and is atomic.
- **Availability per market** is a plain row per (market, template) with an order unique per market (the same shape as the taxonomy), preparable in a market of any status; a RETIRED template is never enabled. Public exposure needs the market public (geography), the whole chain above the template, the template ACTIVE and enabled, and an ACTIVE version.
- **Audit, events, cache.** The CAT-001 audit table gains the template and version subjects (no second audit table); `changes` holds identifiers, keys and counts, never copy. Outbox events: template activated, deactivated (paused), retired, version published (with the exact version id), availability changed. Draft edits emit nothing. The public snapshot is cached per market under the SAME generation counter as the taxonomy, so a service type or category change also invalidates it.
- **Seed: two DRAFT templates without versions** (Full Detail for Car Detailing, Standard Clean for Regular Cleaning) with their copy through the real content lifecycle. Nothing is public until an administrator builds, publishes, activates and enables one.

## Alternatives considered

- **No versions: edit the template in place.** A Gig built from yesterday's structure would silently change meaning (a new required field, other duration bounds) and R-06 ("provider edits never retroactively change confirmed scope") would have no anchor.
- **One JSON document per version.** Rejected: no foreign keys to content, no per-field constraints, no uniqueness of keys, validation only in code; the typed columns are checkable in the database.
- **Version-specific content keys.** Would freeze wording per version at the price of one set of entries per version and a content-authoring step per release; the content registry already provides immutable effective-dated text versions, and a wording change that changes meaning is a new field key.
- **Child tables for pricing models and area modes.** Correct but heavier: two tables, two guards and two reads for sets of 4 and 3 that change by migration.
- **Cascade from service type to templates (CAT-001 guards extended).** Would couple the taxonomy to its consumers and make a pause of a service type write many rows; the read-time re-check gives the same visibility without the coupling.
- **An `IN_REVIEW` status and approval workflow now.** No reviewer exists; the second-approver machinery belongs to the admin-console checkpoints.
- **A separate audit table for templates.** The audit schema is identical in kind; one trail per schema is simpler to read and to retain.

## Consequences

- CAT-003 (provider Gigs) stores `gig_template_version_id` and validates a Gig against that frozen version; it never reads the mutable template for structure.
- Adding a template is data plus content (create the name entry, create the template, build and publish a version, activate, enable in markets), never a deployment; a structural change is a new version.
- A published version can only be superseded or closed; there is no way to fix a mistake in place. The fix is a new version (copied from the old one), which is the point.
- Wording is not frozen per version: changing the text of a label changes it for every version, including the one a Gig was built from. This is recorded as accepted behaviour (DEBT-0084).
- The unvalidated requirement reference codes, the missing requirement catalogues, the admin UI, the complete template catalogue, the media-rule editor, pricing suggestions and the provider Gig builder are recorded debt, not framework gaps.

## Migration / compatibility

`0016_gig_templates.sql` adds six tables, nine functions (six guards, the version status machine, the publishability check and the content check), twelve triggers (a guard and a TRUNCATE refusal per table) and the seeds, and widens two CHECK constraints and adds two nullable columns on `catalog.audit_events`. No existing row changes. `0017_gig_templates_hardening.sql` is the forward fix after the independent review (a field with options keeps its type and key, the publication re-verifies the option rules, the audit key to a version is composite, stale comments). No new role: the catalogue roles `catalog-read` and `catalog-write` cover the new operations.
