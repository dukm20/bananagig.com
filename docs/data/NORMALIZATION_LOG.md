# Normalization Log

Append one entry per schema-changing checkpoint (and per review checkpoint that confirms no change). `pnpm data-model:check <ID>` verifies the entry when the schema snapshot changes. Findings are recorded even when the answer is PASS.

Template:

```
## <CHECKPOINT>

Tables reviewed:

### 1NF
### 2NF
### 3NF
### BCNF
### Duplicate concepts examined
### Derived fields examined
### Intentional denormalization
### Index review
### Final decision
```

Every review also covers: ownership of each table, FK cardinality, uniqueness, check constraints, nullability, immutable historical state, configuration vs schema, concurrency, and retention (see `DATA_MODEL_GUARDRAILS.md`).

## INF-003

Tables reviewed: `public.schema_migrations` (changed), `integration.outbox_events` (new). `pgboss.*` and PostGIS objects are third-party and out of scope.

### 1NF
PASS. All columns are atomic scalars. `payload_json` is a single opaque document by design (the event body), not a repeating group standing in for a relation; nothing in it is queried relationally by the outbox.

### 2NF
PASS. Both tables have single-column keys (`version`, `outbox_event_id`), so partial dependencies are impossible.

### 3NF
PASS with two documented, constraint-enforced derivations. Every non-key attribute depends on the key and nothing else, except: `schema_migrations.version` is derivable from `filename`, and `outbox_events.event_version` is derivable from `event_type`. Both are kept deliberately (see Intentional denormalization).

### BCNF
PASS. `schema_migrations` has two candidate keys (`version`, `filename`) that determine each other and every other attribute; each determinant is a candidate key. `outbox_events` has one candidate key.

### Duplicate concepts examined
Event version appears in both `event_type` and `event_version` (see below). The outbox does not duplicate pg-boss job state: jobs live in `pgboss`, committed domain events in the outbox. Migration bookkeeping exists only in `schema_migrations`. Actor data is stored as two columns because the event envelope carries it; there is no users table yet to reference.

### Derived fields examined
`event_version` and `schema_migrations.version`: derived, immutable once written, consistency guaranteed by CHECK constraints (`ck_outbox_events__version_matches_type`, `ck_schema_migrations__filename_matches_version`). Mutable relay state (`next_attempt_at`, `published_at`, `publish_attempts`, `last_error`) is not derived from other columns: it is the relay's own state and lives on the row it describes. No stored totals or aggregates.

### Intentional denormalization
1. `schema_migrations.version` (from `filename`): numeric primary key and ordering; drift prevented by check.
2. `outbox_events.event_version` (from `event_type`): the envelope exposes the version explicitly and relay queries need no string parsing; drift prevented by check.

### Index review
`pk_schema_migrations`, `uq_schema_migrations__filename` (tiny table). `pk_outbox_events` plus two partial indexes: `idx_outbox_events__pending (next_attempt_at, created_at) WHERE published_at IS NULL` serves the relay claim query and stays small because published rows leave it; `idx_outbox_events__published_at WHERE published_at IS NOT NULL` serves retention purge. No foreign keys, so no foreign-key indexes are needed. No speculative indexes.

### Final decision
Schema accepted. Ownership: both tables are application-owned (`public` bookkeeping, `integration`). Nullability reviewed (only genuinely optional columns are nullable). Immutable historical state: all columns except the relay's four state columns are write-once; published rows are retained for `OUTBOX_RETENTION_DAYS` (default 7) then purged by the worker under an advisory lock. Concurrency: relay claims with `FOR UPDATE SKIP LOCKED` plus a lease so no lock is held during publishing; duplicate publishes are absorbed by JetStream (`Nats-Msg-Id`) and consumers dedupe by `eventId`. Configuration vs schema: no business values in the schema. Idempotency records deferred (DEBT-0013).

## CFG-001

Tables reviewed: all new, in schema `configuration`: `scope_levels`, `parameters`, `parameter_scopes`, `parameter_values`, `value_versions`, `change_requests`, `change_approvals`, `snapshots`, `snapshot_items`, `audit_events`. Reused: `integration.outbox_events` (five new event types; no change).

### 1NF
PASS. Every column is an atomic scalar except three deliberate JSON documents (see intentional denormalization): `parameters.validation_rules`, `value_versions.value` / `change_requests.proposed_value`, `snapshots.context`. None is a repeating group; each is a single typed document read back whole. The allowed scope levels of a parameter are NOT an array on `parameters`; they are rows in `parameter_scopes`.

### 2NF
PASS. Composite keys: `parameter_scopes (parameter_id, scope_type)` has no non-key columns; `snapshot_items (snapshot_id, parameter_id)` has only `version_id`, which depends on the whole key. Every other table has a single-column surrogate key.

### 3NF
PASS. No transitive dependencies. Value history is separate from the holder (`parameter_values` -> `value_versions`) so scope identity is not repeated per version. Parameter definition attributes (type, sensitivity, criticality) live only on `parameters`; they are not repeated on values or versions. The scope rank lives only on `scope_levels`; the resolver joins it instead of copying it onto values.

### BCNF
PASS. Every determinant is a candidate key. Candidate keys checked: `parameters.key`; `scope_levels.rank`; `parameter_values (parameter_id, scope_type, scope_ref)` (NULLS NOT DISTINCT); `value_versions (parameter_value_id, version)` and the no-overlap period per holder; `change_requests.value_version_id`; `change_approvals (change_request_id, approver)`.

### Duplicate concepts examined
- Default value vs PLATFORM value: a `default_value` column on `parameters` would duplicate the PLATFORM-scope value and drift. Omitted; the PLATFORM version is the default.
- Allowed scope levels vs existing values: `parameter_scopes` is the single source for what is allowed; values and change requests reference it through a composite foreign key rather than re-validating in code only.
- Current value vs history: no "current value" column exists anywhere. Current is derived from effective dates at resolution time, so it cannot go stale.
- Snapshot copy vs pointer: items point at immutable versions instead of copying values.
- Audit vs change request history: `audit_events` records actions (who/when/which version), while `change_requests` and `change_approvals` hold request content and decisions; values are not copied into audit.

### Derived fields examined
- Active/scheduled status of a version: derived from `effective_from/effective_to` and `now()`, not stored.
- `change_requests.state` ACTIVE/SUPERSEDED is a workflow marker moved by the activation job and by supersession; resolution never depends on it (the resolver uses timestamps only), so a delayed job cannot produce a wrong value.
- `value_versions.effective_to` of a predecessor equals the `effective_from` of its successor. This is stored (see below).

### Intentional denormalization
1. `change_requests.approval_policy`: copy of `parameters.approval_policy` at request time. The policy that governed a request must not change retroactively when the parameter is edited. Frozen after DRAFT by trigger.
2. `value_versions.effective_to`: derivable from the successor's `effective_from`. Stored so a database exclusion constraint (`ex_value_versions__no_overlap`, gist) can make overlapping validity impossible. Closed exactly once, by the publisher in the same transaction as the successor insert; trigger-guarded; verified by tests.
3. JSON columns `validation_rules`, `value`/`proposed_value`, `context`: the shape depends on `data_type` or is an input copy; never queried relationally; validated by the service against the definition before insert, object-type checked in the database.
4. `parameter_values.scope_ref` / `change_requests.scope_ref` have no foreign key: the referenced entities (markets, categories, providers) do not exist yet and the registry must not depend on domain tables. The scope LEVEL is enforced by foreign key; the existence of the referenced entity is validated by the owning domain when it exists (DEBT-0024).
5. `change_requests.scope_type/scope_ref` repeat the holder identity: the holder does not exist until publish, so the request must carry the target itself.

### Index review
Primary and unique keys cover identity lookups and the foreign key from `parameter_scopes`. Added: `idx_value_versions__holder_effective (parameter_value_id, effective_from DESC)` for resolution (candidate versions by time; the resolver runs 3 queries per batch); partial `idx_change_requests__pending` and `idx_change_requests__scheduled` (small, serve the approver queue and the activation job); `idx_change_requests__parameter (parameter_id, created_at DESC)` for history; `idx_audit_events__parameter (parameter_id, occurred_at DESC)` and partial `idx_audit_events__change_request`. The exclusion constraint adds a gist index used for overlap checks. Foreign-key indexes: `parameter_values`/`change_requests` are covered by the composite keys and `uq_parameter_values__parameter_scope_ref`; `change_approvals` by `uq_change_approvals__request_approver`; `snapshot_items` by its primary key (snapshot) and the immutable version pointer (low volume, no reverse lookups yet); `audit_events.old/new_version_id` are not indexed (no lookup path). No speculative indexes.

### Final decision
Schema accepted. Ownership: all ten tables application-owned in schema `configuration`. Nullability reviewed (only genuinely optional columns nullable). Immutable historical state: `value_versions` (only a one-time closure), `change_approvals`, `snapshots`, `snapshot_items`, `audit_events` are immutable by trigger; `change_requests` content frozen after DRAFT and transitions guarded; parameters and change requests are never deleted. Concurrency: publish takes row locks on the holder and relies on the exclusion constraint as the final arbiter; approvals are unique per approver; activation is idempotent. Configuration vs schema: no business parameters or values are seeded; `scope_levels` is structural reference data. Retention: all history retained (no purge).

## CFG-002

Tables reviewed: all new, in schema `content`: `content.locales`, `content.entries`, `content.entry_variables`, `content.versions`, `content.version_approvals`, `content.snapshots`, `content.snapshot_items`, `content.audit_events`. Reused read-only: `configuration.scope_levels` (foreign keys from `content.entries` and `content.versions`; no change), `integration.outbox_events` (content event types; no change). Migration 0006 is data only (8 shell entries seeded through the lifecycle, five audit rows each, no outbox events) and changes no table definition.

### 1NF
PASS. Every column is an atomic scalar except two deliberate JSON documents: `content.entry_variables.example_value` and `content.snapshots.context` (see "Unnecessary JSON" below). Items that could have been arrays are rows: the variables of an entry are rows in `content.entry_variables`, not an array on `content.entries`; the versions of an entry are rows in `content.versions`; the items of a snapshot are rows in `content.snapshot_items`; approvals are rows, not a list on a version. `content.versions.body` is a single text document (template source), not a JSON structure and not a repeating group. A locale tag such as `zh-Hant-TW` is treated as one atomic identifier (it is the unit that is registered, activated and authored for); its language and script prefixes are not stored as separate columns because they are derivable by progressive truncation (see Derived fields). `scope_ref` is one opaque string.

### 2NF
PASS. Composite keys: `content.entry_variables (entry_id, name)`: every other column (`var_type`, `is_required`, `description`, `example_value`, `pii_class`) describes that variable of that entry, so it depends on the whole key. `content.snapshot_items (snapshot_id, entry_id)`: the only other column is `version_id` (plus the repeated `entry_id`, covered by the BCNF discussion below). Every other table has a single-column surrogate primary key (`locale` for `content.locales`), so partial dependencies are impossible. The natural candidate key of `content.versions` is `(entry_id, locale, scope_type, scope_ref, version)`; every attribute (body, status, period, reason, author) describes that exact version, none describes only part of the key.

### 3NF
PASS with three documented, trigger-enforced derivations. Entry governance attributes (content type, owner, sensitivity, criticality, fallback policy, max scope) live only on `content.entries`; versions do not repeat them. Locale attributes (`is_active`, `is_platform_default`) live only on `content.locales`; versions carry just the locale key. Scope rank lives only on `configuration.scope_levels`; the guard trigger and the resolver join it rather than copying it. Deliberate exceptions (see Intentional denormalization): `content.versions.approval_policy` (determined by `entry_id`), `content.versions.body_sha256` (determined by `body`), and `content.snapshot_items.entry_id` (determined by `version_id`).

### BCNF
PASS except four recorded, deliberate violations, each prevented from drifting by the database. Candidate keys checked: `content.locales.locale` (and the single-default rule: the partial unique index `uq_locales__platform_default` allows at most one default and `guard_locales` refuses any UPDATE that unsets it, so exactly one exists from the seed onward; a migration that moves the default disables the guard inside its own transaction and sets the new default there); `content.entries.entry_id` and `content.entries.key`; `content.entry_variables (entry_id, name)`; `content.versions.version_id`, `(entry_id, locale, scope_type, scope_ref, version)` (NULLS NOT DISTINCT) and the superkey `(version_id, entry_id)`; `content.version_approvals (version_id, approver)`; `content.snapshot_items (snapshot_id, entry_id)`; `content.snapshots.snapshot_id`; `content.audit_events.audit_event_id`. Determinants that are NOT candidate keys: (1) `content.versions`: `entry_id -> approval_policy` (version copies the entry policy so the governing policy never changes retroactively; the guard trigger forces equality at insert and freezes the column, and the entry policy is itself immutable, so the dependency cannot be violated); (2) `content.versions`: `body -> body_sha256` (derived; computed by the insert trigger, never trusted from the caller, immutable); (3) `content.snapshot_items`: `version_id -> entry_id` (repeated so that the primary key can express "one version per entry per snapshot"; the composite foreign key `(version_id, entry_id) -> content.versions (version_id, entry_id)` makes drift impossible); (4) `content.audit_events`: `version_id -> entry_id` and `previous_version_id -> entry_id` (an audit row names the entry once, and the versions it mentions must belong to that entry; the composite foreign keys `fk_audit_events__version_entry (version_id, entry_id)` and `fk_audit_events__previous_version_entry (previous_version_id, entry_id)` to `uq_versions__version_entry` make drift impossible, with MATCH SIMPLE so locale and entry actions, which carry no version, are unaffected). A second dependency, `version_id -> locale`, is NOT stored: `ck_audit_events__subject` requires `locale` to be NULL for every entry and version action, so a locale is stored only for locale actions, where it is the subject itself (an audit row has no key on it, and `action` determines which subject columns are NULL, which is a CHECK shape and not a stored fact). Everything else is determined by a candidate key.

### Duplicate concepts examined
Each of the following was challenged and the decision recorded.

- **Entry / version / locale duplication.** `content.entries` is the stable identity and policy (what the copy is and how it is governed), `content.versions` is the text of one (locale, scope) at one point in time, `content.locales` is the registry of languages. The key is not repeated in versions (they reference `entry_id`), the entry policy attributes are not repeated in versions (except the one deliberate policy copy), and the locale is stored once per version as a foreign key to the registry. No text or policy is stored in two tables. Decision: three tables, no duplicated attributes beyond the documented exceptions.
- **Is locale a property of the version, or should translations be a child table?** Considered `version_translations (version_id, locale, body)` under one language-neutral version. Rejected: the lifecycle (draft, review, approval, schedule, publish, supersede, effective dates) is per locale: a Spanish legal document is approved and effective on a different date than the English one, and a translation correction must not re-version or re-approve the other languages. Lifecycle attributes would then depend on `(version, locale)`, so the child table would just be `content.versions` under another name, and the parent would be an empty shell. Locale therefore belongs to the version holder `(entry, locale, scope_type, scope_ref)` and the per-holder `version` number. The locale registry is separate because its attributes (`is_active`, `is_platform_default`) depend on the locale alone, not on any entry or version; embedding them in versions would repeat them on every row (update anomaly: activating a locale would touch every version) and could not enforce "exactly one platform default" with a constraint. Activation is also an operational decision independent of authoring, so a locale can be authored for before it is served.
- **Publication lifecycle duplication: why no publications / change-request table.** CFG-001 needs `configuration.change_requests` because the value version does not exist until publication (published values are immutable and carry the only timeline), so a proposal must live somewhere else first. Content versions are different: the body is immutable from the moment of creation, so the draft IS the future published row. A separate `publications` or `change_requests` table would be 1:1 with `content.versions` (same identity, same lifetime) and would either duplicate the body/locale/scope or hold only status columns that depend on the version key alone, i.e. the same entity split in two with a join on every read and a cross-table consistency problem. Instead the lifecycle is `content.versions.status` (guard trigger state machine), decisions are `content.version_approvals`, and the history is `content.audit_events`. Cost accepted: unpublished and never-published rows (DRAFT, REJECTED, CANCELLED) share the table; partial indexes and the partial exclusion constraint keep them out of resolution and overlap checks.
- **Scope polymorphism.** `content.versions.scope_type` is a foreign key to the existing `configuration.scope_levels` (one scope hierarchy for the platform; no `content.scope_levels` copy to drift), restricted to `PLATFORM, COUNTRY, MARKET` by a check and bounded per entry by `content.entries.max_scope_type` (guard trigger compares ranks from `scope_levels`). `scope_ref` is an opaque text reference with NO foreign key and is NULL exactly for PLATFORM (`ck_versions__platform_has_no_ref`): the referenced entities (country, market) do not exist as tables yet and a polymorphic reference cannot be a single foreign key. Alternatives rejected: one nullable FK column per scope kind (sparse, grows with every new level) and a separate scope table (a second hierarchy). The level is enforced by the database; existence of the referenced entity is validated by the owning domain when it exists (same limitation as DEBT-0024). A new content scope level is a migration that widens `ck_versions__scope_type` and `ck_entries__max_scope_type`.
- **Template variable normalization.** Variables belong to the entry (`content.entry_variables (entry_id, name)`), not to a version or a locale. Placing them per version would repeat the contract on every translation and allow translations to disagree about what placeholders exist, which breaks the guarantee that every locale of an entry renders from the same inputs. A translation may legitimately omit a variable, so "variables used by this body" is not stored: it is derived by parsing the body (a stored `used_variables` array would be a derived, driftable duplicate). `is_required` is a property of the variable, and `trg_entry_variables__no_late_required` blocks adding a required variable after versions exist (existing copy would stop rendering).
- **Snapshot duplication.** A snapshot could copy locale, body and metadata of the resolved text. Rejected: `content.snapshot_items.version_id` points at an immutable version (body, hash, locale, scope, version number and `effective_from` can never change after publication, and the row can never be deleted), so for the text and what identifies it the pointer is equivalent to a stored copy without duplicating up to 200000 characters per item. It is NOT equivalent for `effective_to`: that column is the live end of the version's period and is closed once when a successor is published, so a read through the pointer after that would differ from what was true at creation. Snapshot items therefore deliberately expose no `effective_to` (the service, the API and the contract omit it); only the text, version, version id, hash, `effective_from`, scope and locale are fixed, which makes a snapshot read-back byte-stable. The period that applied at `evaluated_at` is derivable from `evaluated_at` and the version history if ever needed. `entry_id` is repeated in the items only so the primary key `(snapshot_id, entry_id)` can state "one version per entry per snapshot" (a constraint cannot span tables); the composite foreign key `(version_id, entry_id)` to `uq_versions__version_entry` prevents drift. Dropping the column and keying on `(snapshot_id, version_id)` would allow two versions of the same entry (for example two locales) in one snapshot and make reproduction ambiguous. `content.snapshots.requested_locale` is an input (what the caller asked for), distinct from the resolved locale that the version carries, so it is not a duplicate.
- **Legal-document overlap with generic content.** Legal documents are `content.entries` with `content_type = 'LEGAL'`; `ck_entries__legal_policy` forces owner LEGAL, SECOND_APPROVER, CRITICAL and EXACT fallback. Versions, locales (jurisdictional language), COUNTRY/MARKET scopes, approvals, audit and snapshots are exactly what a legal document needs, so separate `legal_documents` / `legal_document_versions` / `legal_approvals` tables would duplicate all of them and give two places to enforce immutability. No legal tables were created. The future acceptance record (ID-005) will reference `content.versions.version_id` (immutable primary key) and may store `body_sha256` as evidence; `body_sha256` is computed by the database at insert, so such a copy can be verified. That future copy is an ID-005 decision and will go through its own review.
- **Audit vs lifecycle.** `content.audit_events` records who did what and when (action, entry, locale for locale actions, versions, reason, correlation id); content, decisions and timeline stay in `content.versions` and `content.version_approvals`. Bodies are never copied into audit.

### Derived fields examined
- **No "is current", "is published", "is latest" or "current_version" column exists anywhere.** `SCHEDULED`, `PUBLISHED` and `SUPERSEDED` in `content.versions.status` are workflow markers moved by the publisher and the activation job. Which version applies at an instant is derived from `effective_from <= at AND (effective_to IS NULL OR effective_to > at)` over published rows, so a delayed activation job can never serve a wrong version, and a stored flag cannot go stale. Status is still stored because the exclusion constraint, the immutability guard and the partial indexes need to distinguish unpublished rows from published ones.
- `content.versions.body_sha256`: derived from `body`; stored and computed by the insert trigger (see Intentional denormalization).
- Language of a locale (`zh-Hant-TW` -> `zh-Hant` -> `zh`): derived by progressive truncation in code, not stored.
- Fallback chain: derived at resolution from `entries.fallback_policy`, the requested locale, the caller-supplied market default and the platform default; not stored.
- Next version number: derived as max+1 per holder inside a transaction holding the entry row lock; `uq_versions__holder_version` is the arbiter.
- `content.versions.effective_from` while unpublished is a proposal, not a derived value (see below).

### Intentional denormalization
1. `content.versions.approval_policy`: copy of `content.entries.approval_policy` at creation, so the policy that governed a version never changes retroactively. Trigger `content.guard_versions` requires equality at insert and freezes the column; the entry policy is immutable (`content.guard_entries`).
2. `content.versions.body_sha256`: derived hash of `body`, computed by the insert trigger (the caller value is overwritten), immutable. Lets later consent and audit records bind to exact text without copying it.
3. `content.snapshot_items.entry_id`: repeats `content.versions.entry_id`; composite foreign key `(version_id, entry_id)` prevents drift; supports the one-version-per-entry primary key.
4. `content.versions.effective_from`: holds the proposed start while the version is unpublished and is raised exactly once at publication to `max(proposed, now)` (trigger allows a change only during `APPROVED -> SCHEDULED/PUBLISHED` and only upward). One column replaces a request-time/actual-time pair and a separate publication table; immutable afterwards. `effective_to` is stored (a successor's start could be derived) so that `ex_versions__no_overlap` can forbid overlap in the database; it can be closed once on a published version.
5. JSON columns `content.entry_variables.example_value` and `content.snapshots.context`: shape depends on `var_type` (scalar, or `{amount_minor, currency}` for MONEY) or is an input copy; never queried relationally; validated by the service, object type checked in the database for `context`.
6. `content.versions.scope_ref` has no foreign key (see Scope polymorphism); `content.audit_events.locale` is a plain value stored only for locale actions (`ck_audit_events__subject` requires NULL for entry and version actions; the locale of a version event is reached through the immutable version). `content.audit_events.entry_id` next to `version_id` is the repeated determinant of BCNF item (4), pinned by the composite foreign keys.
7. Status markers SCHEDULED/PUBLISHED/SUPERSEDED versus derived currency: markers are workflow, currency is derived from timestamps (see Derived fields).

Unnecessary JSON, challenged: only `example_value` and `snapshots.context` are JSON. `versions.body` is text (the template syntax is parsed by the service; storing a parsed tree would duplicate it). No `metadata`, `settings` or `variables` JSON column exists on entries or versions: governance attributes are typed, checked columns and variables are rows. `audit_events` carries no JSON payload (bodies are reached through version ids). `example_value` stays JSON because splitting it into typed columns per `var_type` would be sparse (nine variable types, MONEY needs two fields) and it is only read back whole to dry-render; `context` is an input copy of the resolution request, read back whole and never filtered by its fields.

### Index review
Each index and the query path it serves (constraint-backed indexes included):
- `content.locales`: `pk_locales` (locale lookup, FK target); `uq_locales__platform_default` (partial unique: enforces at most one default and finds it; the trigger `guard_locales` makes it exactly one by refusing to unset it).
- `content.entries`: `pk_entries` (FK target); `uq_entries__key` serves the lookup by key (resolution by key; key + locale resolves the key to `entry_id` here and then uses the holder index below).
- `content.entry_variables`: `pk_entry_variables (entry_id, name)` serves loading the variables of an entry and covers the `entry_id` foreign key.
- `content.versions`: `pk_versions`; `uq_versions__version_entry (version_id, entry_id)` is the target of the snapshot composite foreign key; `uq_versions__holder_version (entry_id, locale, scope_type, scope_ref, version)` serves key + locale lookup of a holder's versions, the max+1 version number and covers the `entry_id` foreign key; `ex_versions__no_overlap` (gist) is created by the exclusion constraint and is used for the overlap check at publication; `idx_versions__resolution (entry_id, locale, scope_type, effective_from DESC) WHERE status IN ('SCHEDULED','PUBLISHED','SUPERSEDED')` serves the effective_from branch of the next-boundary query only (index-only scan over entry, locale, scope and a future `effective_from`); it does NOT serve the candidate query (verified with EXPLAIN ANALYZE on a scratch database with 3000 entries x 2 locales x 5 versions and 20 keys: the candidate rows are read through `idx_versions__entry` or the gist exclusion index `ex_versions__no_overlap` (equality on entry, locale and scope), 200 rows read and 40 returned in under 1 ms, then filtered by time; the effective_to branch of the boundary query reads the same history). Candidate read cost therefore grows with the history length of a holder (every published row of the holder is read), which is short and bounded by editorial practice; the query was deliberately not changed, and the index is kept for the boundary query; `idx_versions__scheduled (effective_from) WHERE status = 'SCHEDULED'` serves the activation job (due rows only); `idx_versions__in_review (created_at) WHERE status = 'IN_REVIEW'` serves the reviewer queue; `idx_versions__entry (entry_id, created_at DESC)` serves the management history of one entry.
- `content.version_approvals`: `pk_version_approvals`; `uq_version_approvals__version_approver` serves the decisions of a version and covers the `version_id` foreign key.
- `content.snapshots`: `pk_snapshots` serves snapshot lookup by id. `content.snapshot_items`: `pk_snapshot_items (snapshot_id, entry_id)` serves loading a snapshot's items (snapshot lookup is by primary key) and covers the `snapshot_id` foreign key.
- `content.audit_events`: `pk_audit_events`; `idx_audit_events__entry (entry_id, occurred_at DESC) WHERE entry_id IS NOT NULL` serves the audit trail of an entry (locale actions have no entry and stay out of it); `idx_audit_events__version (version_id) WHERE version_id IS NOT NULL` serves the audit trail of one version, including a legal document version.
- Legal version lookup: by `version_id` (primary key) for acceptance evidence, and by key + locale through `uq_entries__key` and `uq_versions__holder_version`; no extra index.

Foreign keys without a supporting index, and why: `content.entries.max_scope_type` and `content.versions.scope_type` (target `configuration.scope_levels` is an eight-row reference table that is never deleted, so no referential check scans these tables, and no query filters by scope level alone); `content.versions.locale` (locales are never deleted, guarded by `trg_locales__guard`; versions are always read per entry, through the holder index); `content.snapshot_items (version_id, entry_id)` (versions can never be deleted; no reverse "which snapshots used this version" path is needed yet, and a future need would add a partial or plain index through its own review); `content.audit_events.entry_id`/`version_id` are indexed (partial), `content.audit_events.previous_version_id` is not (no lookup path; versions never deleted). The composite foreign keys `fk_audit_events__version_entry` and `fk_audit_events__previous_version_entry` reference the existing unique index `uq_versions__version_entry`; they replace the former single-column foreign keys on `version_id` and `previous_version_id` (same cost, stronger guarantee). No speculative indexes.

### Final decision
Schema accepted. Ownership: all eight tables are application-owned in schema `content`. Cardinality: entry 1-N variables, entry 1-N versions, locale 1-N versions, version 1-N approvals, snapshot 1-N items, version 1-N snapshot items (one per snapshot). Nullability reviewed: only genuinely optional columns are nullable (`scope_ref` exactly for PLATFORM, `effective_to` while open-ended, audit subject columns constrained by `ck_audit_events__subject`). Immutable historical state: variables, approvals, snapshots, snapshot items and audit events by `content.forbid_mutation`; versions by `content.guard_versions` (body frozen, one-time period changes, an end can only be closed at or after the start of the closing transaction so history is never rewritten); entries immutable except `is_active`; locales and entries are never deleted and the platform default locale is never unset. Concurrency: version numbers are allocated while holding the entry row lock with the holder unique key as arbiter; publication locks the version row and the exclusion constraint is the final arbiter against overlap; the activation job is idempotent (`FOR UPDATE SKIP LOCKED`). Configuration vs schema: no business values or product copy are seeded by the migration (only the structural `en-US` locale row); the 8 shell entries are data (migration 0006: one PUBLISHED `en-US` PLATFORM version each plus five causally ordered audit rows each (`clock_timestamp()`), no outbox events, no trigger disabled) created through the lifecycle, and fees, windows and durations stay in `configuration`. Retention: all history retained (no purge). Migration risk: low; new schema and tables only, brief lock on the eight-row `configuration.scope_levels` while its two foreign keys are added, no existing data touched, single transaction. Backfill: none (the seeded locale is reference data). Rollback strategy: forward-fix only (`MIGRATION_POLICY.md`); locally rebuild from zero with `pnpm stack:reset`; the schema holds only the seeded locale until entries are created, so there is nothing to preserve in a fresh environment. Known limitation: `scope_ref` existence is not database-enforced (as DEBT-0024).

## GEO-001

Tables reviewed: all new, in schema `geography`: `geography.currencies`, `geography.time_zones`, `geography.countries`, `geography.country_locales`, `geography.country_time_zones`, `geography.markets`, `geography.market_locales`, `geography.audit_events`. Changed: `content.locales` (display name plus three generated columns; remains the single locale authority). Reused read-only: `content.entries` (foreign key from `geography.countries.display_name_content_key`; one new entry row seeded by migration 0007), `integration.outbox_events` (geography event types, no change).

### 1NF
PASS. Every column is an atomic scalar except one deliberate JSON document, `geography.audit_events.changes` (see "Unnecessary JSON" below). Everything that could have been an array is rows: the locales of a country are rows in `geography.country_locales`, its time zones rows in `geography.country_time_zones`, the locales of a market rows in `geography.market_locales`; nothing is a comma list or array. Format settings are single enum codes (`distance_unit`, `first_day_of_week`, `date_format_code`, `time_format_code`), not format strings or JSON blobs. A locale tag stays one atomic identifier (it is what is registered, activated and authored for); GEO-001 additionally exposes its parts as generated columns `content.locales.language`, `script`, `region` (derived, see Derived fields; this supersedes the CFG-002 remark that the parts are not stored). `geography.time_zones.iana_name` is one identifier; a UTC offset is never stored as identity.

### 2NF
PASS with one recorded, deliberate exception. Composite keys: `geography.country_locales (country_id, locale)`, `geography.country_time_zones (country_id, time_zone_id)` carry only `created_at`, which describes the link. `geography.market_locales (market_id, locale)`: `created_at` depends on the whole key, but `country_id` depends on `market_id` alone, a partial dependency (2NF violation). It is intentional and enforced by the database, see BCNF and "Intentional denormalization". Every other table has a single-column primary key (`currency_code`, `time_zone_id`, `country_id`, `market_id`, `audit_event_id`), so partial dependencies are impossible there.

### 3NF
PASS. No transitive dependencies. Country display defaults (default currency, default locale, distance unit, first day of week, date format code, time format code) are facts about the country and live only on `geography.countries`; markets do not repeat the formats (a market that needs a different format would be a different country-level decision, not a copy). Currency attributes (numeric code, minor unit digits, display name, symbol) live only on `geography.currencies`; countries and markets hold the code, never the digits or the name. The country display name is not a column at all: `display_name_content_key` points at a content entry, so the text is stored once, in the content registry, with its translations and approval trail. `dialing_code` is a country fact (`+1` is legitimately shared by several countries, so it is not a determinant). `markets.currency_code`, `markets.default_locale` and `markets.default_time_zone_id` are the market's own facts (a market may use a different currency or zone than the country default), so they are not derived from the country and not transitive through it. Format settings are not derivable from `default_locale` either: a country with a Spanish default locale can still use miles and `MDY`, which is why they are country facts and not looked up from the locale. `content.locales`: `display_name`, `is_active`, `is_platform_default` depend on `locale` only; the generated columns are derived from the key by expression (see Derived fields).

### BCNF
PASS except one recorded, deliberate violation. Candidate keys checked: `geography.currencies` (`currency_code`, `numeric_code`: each determines every other column); `geography.time_zones` (`time_zone_id`, `iana_name`); `geography.countries` (`country_id`, `iso_alpha2`, `iso_alpha3`, `iso_numeric`; `dialing_code` and `default_*` determine nothing); `geography.country_locales` and `geography.country_time_zones` (all-key tables, each primary key is the only determinant); `geography.markets` (`market_id`, `code`; the superkey `(market_id, country_id)` is the target of the market_locales composite key); `geography.audit_events` (`audit_event_id`; `action` determines which subject columns are NULL, which is a CHECK shape and not a stored fact); `content.locales` (`locale`). The one determinant that is NOT a candidate key: `geography.market_locales`: `market_id -> country_id` (the primary key is `(market_id, locale)`, so `market_id` alone is not a key). It is stored so that the composite foreign key `fk_market_locales__country_locale (country_id, locale) -> geography.country_locales (country_id, locale)` can force every market locale to be supported by the market's country, and the composite foreign key `fk_market_locales__market_country (market_id, country_id) -> geography.markets (market_id, country_id)` (target `uq_markets__market_country`) makes drift impossible. A second dependency of the same kind runs through the deferred composite keys: `countries.default_locale` and `markets.default_locale` select one member of `country_locales` / `market_locales`; the member row is the fact and the default only points at it, so nothing is duplicated (see Duplicate concepts).

### Duplicate concepts examined
Each of the following was challenged and the decision recorded.

- **Duplicated locale authority.** A `geography.locales` table (language, script, region, is_active) was considered because countries and markets need locales. Rejected: `content.locales` already is the registry that content authoring, serving and the fallback chain use, so a second table would give two answers to "is `es-MX` active" and two places to keep language, script and region. Decision: `content.locales` remains the single authority and was extended additively (expand step): `display_name text NOT NULL` and the generated stored columns `language`, `script`, `region`. Geography only references it (`geography.country_locales.locale -> content.locales (locale)`), and reads `content.locales.is_active` (`FOR SHARE`) when it validates an activation. Dependency direction: database foreign keys and trigger reads go geography -> content; content has no foreign key to geography. The one trigger that touches `content.locales` for geography reasons, `trg_locales__geography_guard` (refuses deactivating a locale that is the default of an ACTIVE country or market), is a BEFORE UPDATE guard owned by geography and does not change the content table's own rules (`trg_locales__guard` is untouched). The content package receives market defaults through a port (service layer), not a table dependency. A test proves no `geography.locales` table exists (`geography-seed.itest.ts`).
- **Duplicated currency strings.** Country and market could hold a free-text currency. Decision: `geography.countries.default_currency_code` and `geography.markets.currency_code` are `char(3)` foreign keys to `geography.currencies (currency_code)`. The alpha code is the natural, immutable key (immutability is enforced by `geography.guard_currencies`, so a foreign key on it never needs ON UPDATE CASCADE) and matches the money convention (`amount_minor` plus a `char(3)` code, `DATABASE_CONVENTIONS.md`), so no surrogate id and no join is needed to read a code. The digits (`minor_unit_digits`) and names live only on the currency row; there is no `currency` text column on any geography table other than these two foreign keys.
- **Country default locale: duplicate or not.** `geography.countries.default_locale` plus the membership rows in `geography.country_locales` look like the same fact twice. They are not a copy: the membership rows are the set of supported locales, and the default selects one member. The deferred composite foreign key `fk_countries__default_locale (country_id, default_locale) -> geography.country_locales (country_id, locale)` (DEFERRABLE INITIALLY DEFERRED) guarantees the default is a member, and deferral lets a country and its first locale link be inserted in one transaction (a test shows a default that is not a member fails at COMMIT). Alternatives rejected: a boolean `is_default` on `country_locales` (needs a partial unique index per country and cannot be made mandatory by a foreign key, so a country could have none or be inconsistent with the column), and no default at all (every consumer would invent one). Same pattern for `geography.markets.default_locale -> geography.market_locales`.
- **Market defaults versus country formats.** A market has its own default locale, currency and operational time zone (they legitimately differ inside a country), so they are stored on the market. The distance unit, first day of week, date format code and time format code are stored only on the country and inherited by markets at read time (`resolveMarketDefaults`); copying them to markets would create four columns that must all be kept equal to the country's and could drift. A market-specific override would be a deliberate future change with its own column and review, not a silent copy now. The market default time zone is constrained to a time zone of its own country by the composite key `fk_markets__country_time_zone (country_id, default_time_zone_id) -> geography.country_time_zones`.
- **Many-to-many tables.** `geography.country_locales`, `geography.country_time_zones` and `geography.market_locales` are real association tables (a country supports several locales and a locale is supported by several countries; the same for time zones; markets likewise), with composite primary keys and restrict foreign keys, never arrays or comma lists. `geography.market_locales` repeats `country_id` with composite foreign keys, documented above and below as intentional denormalization enforced by foreign key: without it, a market locale could be one the country does not support (a plain `(market_id, locale)` key cannot express a rule that spans the market's country). A trigger could enforce the same rule, but a declarative foreign key is stronger (it cannot be bypassed by a disabled trigger and is checked by the engine), so the foreign key was chosen. The three association tables are also immutable as rows: a BEFORE UPDATE trigger (`geography.forbid_mutation`) refuses rewriting a link, so a link changes only by insert or delete, and deleting a link of an ACTIVE country is refused by a BEFORE DELETE trigger (which share-locks the country row before it reads the status, so it serializes with an activation).
- **Format settings: enum codes, not strings.** Dates and times are rendered with `Intl`; the database stores only the choice (`MDY`, `DMY`, `YMD`; `12_HOUR`, `24_HOUR`; `MILES`, `KILOMETERS`; `MONDAY ... SUNDAY`) as checked codes, so there is no free-text format pattern (`MM/dd/yyyy`) to validate, localize or inject, and one code has one meaning. Each is a CHECK list rather than a lookup table: the sets are closed by what the renderer can do, and adding a value is a migration plus code change in the same checkpoint.
- **Status flags versus derived state.** `status` (`PLANNED`, `ACTIVE`, `INACTIVE`) on currencies, time zones, countries and markets is the operator's decision, stored once; the database guards what an ACTIVE row must have. Readiness (what a market still lacks before it could go live: country, currency, locale, time zone and future checks such as tax or payment provider) is DERIVED by an in-code registry and never stored, because a stored `is_ready` would go stale whenever any dependency changes (a test asserts that `geography.markets` has no such column). Market "in effect" is derived at read time from `status = 'ACTIVE'` and the window `[effective_from, effective_to)` containing the evaluation time; there is no `is_current` column. The only status the database cannot derive is the operator's intent, which is why `PLANNED`/`INACTIVE` exist. The status is a small state machine enforced by the guard triggers: `PLANNED` is the initial status only (any UPDATE back to `PLANNED` is refused), and `PLANNED -> ACTIVE`, `PLANNED -> INACTIVE`, `ACTIVE -> INACTIVE`, `INACTIVE -> ACTIVE` are the permitted moves, each subject to the activation and deactivation rules (the service never writes `PLANNED`).
- **Effective dating of markets.** The window sits on the market row (`effective_from`, nullable `effective_to`, `ck_markets__effective_range`). No version table: a market is a place that opens and closes, not a record whose past values need to be reproduced (when a default changes, the change is audited in `geography.audit_events` with old and new values and snapshots/outbox events carry identifiers). A versioned markets table would need the same exclusion-constraint machinery as `configuration.value_versions` for no reader that needs "market as of last June"; if one appears, it is its own review. No exclusion constraint is needed because one row per market means nothing can overlap.
- **Audit subject: two nullable foreign keys instead of a polymorphic id.** `geography.audit_events` has `country_id` and `market_id`, both real foreign keys, with `ck_audit_events__subject` requiring exactly the one that matches the action prefix (`COUNTRY_%` or `MARKET_%`). A polymorphic `subject_id` plus `subject_type` could not be a foreign key (referential integrity lost, orphans possible); the cost is one extra nullable column, and the check keeps the shape unambiguous. `action LIKE 'COUNTRY\_%'` escapes the underscore on purpose.
- **Audit versus state.** Audit records who did what and when plus the field diff; the current values live on the row. Reference data is public, so values are recorded in the diff, unlike `configuration.audit_events` where values are reached through version ids because they can be sensitive.
- **Country display name.** A `display_name` column on countries would duplicate content that needs translation, approval and effective dates. It is a content entry (`display_name_content_key`, foreign key to `content.entries (key)`); the seeded `geography.country.us.name` is taken through the real content lifecycle. The currency `display_name` stays a column: it is a stable English reference label, not localized product copy (a localized currency name would also become a content entry through its own review).
- **Scope references.** `configuration` and `content` keep `scope_ref` as opaque text for COUNTRY and MARKET scopes; no foreign key was added from them to geography (it would create a dependency from the lower-level registries onto geography and a polymorphic reference cannot be one foreign key). Existence is validated by the service layer through a port; DEBT-0024 stays open for the other scope types.

### Derived fields examined
- `content.locales.language`, `script`, `region`: derived from the tag; implemented as generated stored columns (`GENERATED ALWAYS AS ... STORED`), so they cannot be written and cannot drift. Rewriting a one-row table was the cost. Alternatives rejected: derive on every read (the service and filters would each parse tags) and plain columns with a trigger or check (can drift or be bypassed).
- `content.locales.display_name`: not derived; a stored label. Rows inserted without one get the tag itself by trigger (`content.default_locale_display_name`), so the NOT NULL never blocks an existing code path, and the service replaces it with an `Intl.DisplayNames` name for newly registered locales.
- Market readiness: derived in code, never stored (see Duplicate concepts). Market "in effect": derived from `status` and the window. Distance unit and date/time formats of a market: derived from the country at read time. Country "usable": derived from `status` plus the guard rules, not a flag.
- `geography.markets.effective_to` and `geography.markets.effective_from` are facts (planned opening and closing), not derived.
- `updated_at` columns are maintained by the application in the same transaction (no trigger), as in the other registries.
- No counts, totals or "number of markets in country" columns exist.

### Intentional denormalization
1. `geography.market_locales.country_id`: repeats `geography.markets.country_id` so that the composite foreign key `(country_id, locale)` to `geography.country_locales` enforces "a market only supports locales its country supports". Drift prevented by the composite foreign key `fk_market_locales__market_country (market_id, country_id)` to `geography.markets (market_id, country_id)` (target `uq_markets__market_country`).
2. `geography.countries.default_locale` / `geography.markets.default_locale`: a selected member of the supported-locale sets. Not a copy; enforced by the deferred composite foreign keys `fk_countries__default_locale` and `fk_markets__default_locale` (checked at commit).
3. `geography.countries.default_currency_code` / `geography.markets.currency_code`: currency code stored as the natural key; foreign key to `geography.currencies`; immutability of the code by trigger.
4. `geography.audit_events.changes`: a JSON document, see below.
5. `geography.audit_events.country_id` / `market_id`: two nullable subject foreign keys under `ck_audit_events__subject`, instead of a polymorphic id.
6. `content.locales.language`, `script`, `region`: derived columns, generated and stored (cannot drift).
7. `geography.countries.display_name_content_key` is a reference to content by key (a natural-key foreign key to `content.entries (key)`), not a copy of the name. Entry keys are immutable (`content.guard_entries`), so the reference cannot go stale.

Unnecessary JSON, challenged: the only JSON column is `geography.audit_events.changes`, a `{field: [old, new]}` diff. Its shape depends on the subject (country fields versus market fields) and on which fields changed, it is read back whole for the audit trail and never filtered relationally, and typed old/new columns per field would be sparse and grow with every new column. It is checked to be a JSON object (`ck_audit_events__changes_object`), and the rows are immutable. No other JSON exists in the schema: no `settings`, `metadata`, `formats` or `locales` JSON on countries or markets (locales and zones are rows, formats are typed enum columns, readiness is derived).

### Index review
Each index and the query path it serves (constraint-backed indexes included):
- `geography.currencies`: `pk_currencies (currency_code)` (lookup by code, foreign key target); `uq_currencies__numeric_code` (ISO numeric uniqueness and lookup).
- `geography.time_zones`: `pk_time_zones`; `uq_time_zones__iana_name` (lookup and uniqueness by IANA name; the guard queries by id).
- `geography.countries`: `pk_countries`; `uq_countries__iso_alpha2` (lookup by the canonical code `US`, the scope reference and the public lookup); `uq_countries__iso_alpha3`, `uq_countries__iso_numeric` (ISO uniqueness, lookup by the other codes); `idx_countries__active (iso_alpha2) WHERE status = 'ACTIVE'` (public active-country list, stays small and ordered by code; anonymous callers never see other statuses).
- `geography.country_locales`: `pk_country_locales (country_id, locale)` (locales of a country; covers the `country_id` foreign key; target of `fk_countries__default_locale` and `fk_market_locales__country_locale`).
- `geography.country_time_zones`: `pk_country_time_zones (country_id, time_zone_id)` (zones of a country; covers the `country_id` foreign key; target of `fk_markets__country_time_zone`).
- `geography.markets`: `pk_markets`; `uq_markets__code` (lookup by the canonical market code, the scope reference); `uq_markets__market_country (market_id, country_id)` (composite foreign key target for `market_locales`); `idx_markets__active (country_id, code) WHERE status = 'ACTIVE'` (public list of active markets by country, and the country deactivation guard `EXISTS ... WHERE country_id = ? AND status = 'ACTIVE'`).
- `geography.market_locales`: `pk_market_locales (market_id, locale)` (locales of a market; covers the `market_id` foreign key; target of `fk_markets__default_locale`).
- `geography.audit_events`: `pk_audit_events`; `idx_audit_events__country (country_id, occurred_at DESC) WHERE country_id IS NOT NULL` and `idx_audit_events__market (market_id, occurred_at DESC) WHERE market_id IS NOT NULL` (audit trail of one subject, newest first; partial because exactly one of the two keys is set per row, so each index holds only its own half; they also serve the foreign key checks).

Foreign keys without a supporting index, and why: `geography.countries.display_name_content_key`, `geography.countries.default_currency_code` and `geography.markets.currency_code` (targets `content.entries` and `geography.currencies` are never deleted, the geography tables are tiny, and no query filters by these columns alone; the currency and locale deactivation guards scan `countries` and `markets`, which hold tens of rows); `geography.markets.country_id` (no full index: the only hot path, active markets of a country, is the partial `idx_markets__active`; management listing by country scans a tiny table; the unique `(market_id, country_id)` does not lead with `country_id`); `geography.markets (country_id, default_time_zone_id)` and `geography.market_locales (country_id, locale)` (targets are never deleted or updated while referenced; tiny tables); `geography.country_locales.locale` and `geography.country_time_zones.time_zone_id` (the second column of the primary key; locales and time zones are never deleted, and the guards that start from a locale or a time zone scan tiny tables); `geography.markets.default_time_zone_id` (as above); `geography.countries.default_locale` and `geography.markets.default_locale` are covered through the composite foreign keys, whose referencing columns are not separately indexed (same reason). If a table grows to thousands of rows, an index is added through its own review. No speculative indexes.

### Final decision
Schema accepted. Ownership: all eight tables are application-owned in schema `geography`; `content.locales` stays owned by `content` and was extended additively. Cardinality: country 1-N markets; country N-M locales and N-M time zones; market N-M locales (subset of the country's); market 1-1 default locale, currency and default time zone; currency 1-N countries and markets; country 0-N and market 0-N audit events. Nullability reviewed: only genuinely optional columns are nullable (`currencies.symbol`, `markets.effective_to`, audit `country_id`/`market_id`/`changes`/`reason`, and the generated `script`/`region`). Immutable historical state: identity columns by trigger (currency code, numeric code and minor unit digits; ISO codes; time zone id and name; market id, code and country), the status can never return to `PLANNED` (guard triggers on all four status-bearing tables), link rows (`geography.country_locales`, `geography.country_time_zones`, `geography.market_locales`) are never updated (BEFORE UPDATE trigger; inserted or deleted only), audit rows immutable by trigger, rows never deleted (DELETE refused by trigger on currencies, time zones, countries, markets; foreign keys are restrict). `markets.name` is bounded to 120 characters by `ck_markets__name_not_blank`. Concurrency: activation of a market locks its country, currency, time zone and locale rows `FOR SHARE`, and activation of a country locks its currency, its default locale and the ACTIVE time zone rows it relies on (`FOR SHARE OF` the time zone), so a concurrent deactivation (which needs the row lock) serializes with it and exactly one wins; deterministic race tests prove it (market activation versus country deactivation and the reverse; country activation versus deactivation of its only ACTIVE time zone and the reverse, the time zone pair mutation-checked by removing the lock), and two identical activations are idempotent. Two rules read SIBLING rows and a plain read of siblings is blind to another transaction's uncommitted change (write skew), so they lock the row that owns the invariant first: `geography.guard_time_zones` locks every ACTIVE country that uses the zone (`FOR UPDATE`, `country_id` order) before it checks that the country keeps another ACTIVE zone (two concurrent deactivations of two zones of one country: the second waits and is refused), and `geography.guard_country_links` share-locks the country row before it reads its status (country activation versus removal of its only zone link, both orders). Both race pairs are deterministic two-connection tests, mutation-checked by removing the lock. The zone check of a country runs only when the country BECOMES ACTIVE (an ACTIVE country that changes currency or locale does not re-read its zones: the zone guard keeps that rule), which avoids a lock cycle with the zone guard. Lock order in the triggers and the service: markets of a country (`market_id` order), country, then currency, time zone, locale rows; the service reads a row only after locking it with a bare single-table statement (a `SELECT ... JOIN ... FOR UPDATE` re-evaluates only the locked row after a lock wait in READ COMMITTED, so joined and `ARRAY(subselect)` columns would come from the old snapshot), and checks with plain reads that a link is unused before deleting it (the foreign key check would lock the market row in the opposite order). Every guard `RAISE` carries `geography_rule:<KEY>` in its DETAIL (15 keys) and the service classifies by it, never by message text. Accepted limits, recorded rather than hidden: (a) `geography.market_locales.country_id` is a deliberate denormalization (2NF and BCNF), enforced by composite foreign keys so it cannot drift; (b) there is no stored readiness flag and no stored "currently in effect" flag: both are derived at read time; (c) there is no cross-row cardinality rule such as "a country has at least N locales": the single default is the NOT NULL `default_locale` column and the deferred composite foreign key guarantees it is a member, nothing counts the members; (d) `trg_locales__geography_guard` protects only a locale that is the default of an ACTIVE country or market: deactivating a non-default supported locale is allowed on purpose, and public reads then hide it from `supportedLocales`; (e) the links of an ACTIVE country cannot be removed but can be added; (f) custom readiness checks (future domains) are application-level only, the triggers know the four built-in dependencies; (g) one lock-order inversion is inherent: the UPDATE of a time zone row locks the zone before its trigger can lock the countries, so a raw SQL zone deactivation racing a market activation (which holds the country share lock and waits for the zone) can deadlock; PostgreSQL aborts one side (`40P01`) and the service reports a retryable `CONFLICT` (`CONCURRENT_UPDATE`), nothing is half-written (tested with a real deadlock); the service has no operation that changes a time zone status, so this needs a manual SQL change at the same moment; (h) the time zone name check reads the server's tz database on insert only (not re-validated when tzdata is updated) and an already registered name skips the scan; the service pre-check in front of it accepts only members of the runtime's canonical regional list (`Intl.supportedValuesOf('timeZone')`, plus 19 IANA names that list spells differently such as Asia/Kolkata) so fixed offsets and legacy aliases never reach the database as identities; (j) the country alpha-2 code is checked against the runtime's region data when a country is created (unassigned codes such as QQ are refused; ZZ only with the DEV/TEST gate), while alpha-3 and numeric codes are checked by pattern and uniqueness only and are not verified to belong to the same country; (i) a public country read hides PLANNED and INACTIVE zones, a raw SQL zone status change is seen by cached public reads after the cache TTL or the next service change (there is no service operation that changes a zone status, so no generation bump). Configuration vs schema: no business values, fees, taxes, payment data or addresses are in the schema; currencies, zones, countries, markets and every default are rows. Seeds (reference data, not business values): USD; four US time zones; US created PLANNED, linked, then activated through the guard; the country display name as a content entry through the real lifecycle (no trigger disabled); market `la-oc` PLANNED (never ACTIVE until the owner activates it through the management API); three geography audit rows; no outbox events. Retention: all history retained (no purge). Migration risk: low; one new schema, eight new tables, one small existing table (`content.locales`, one row) gains four columns (generated columns rewrite the table, a brief exclusive lock on one row), a NOT NULL set after the back-fill, no existing data touched apart from that back-fill, single transaction. Backfill: `content.locales.display_name` for `en-US` (`English (United States)`; any other existing row would get its tag), generated columns computed by the engine, then the seeds above. Rollback: forward-fix only (`MIGRATION_POLICY.md`); locally rebuild from zero with `pnpm stack:reset`; reference rows are never deleted, so there is nothing to restore. Compatibility: additive and backward compatible (existing inserts into `content.locales` still work because the display name defaults to the tag; the new columns are read-only; no content column or constraint was removed or loosened).

## GEO-002

Tables reviewed: all new, in schema `geography`: `geography.administrative_areas`, `geography.address_formats`, `geography.address_format_fields`, `geography.addresses`. Changed: `geography.audit_events` (one nullable subject column `address_format_id`, two widened CHECKs, one partial index). Reused read-only: `content.entries` (foreign key from `address_format_fields.content_label_key`; twelve new entries seeded by migration 0008), `geography.countries` and `geography.time_zones` (foreign keys), `integration.outbox_events` (two new event types, no change), PostGIS (the `geography` type, first column that uses it).

### 1NF
PASS. Every column is an atomic scalar except two that are deliberate and recorded: `geography.addresses.location` is ONE `geography(Point,4326)` value (a spatial point is an atomic value of its type, and there are no separate latitude and longitude columns to repeat it) and `geography.addresses.raw_input` is a JSON document (see "Unnecessary JSON" below). Everything that could have been an array is rows: the fields of a format are rows in `geography.address_format_fields` (not a JSON list on `address_formats`), the versions of a country format are rows in `geography.address_formats`, the areas of a country are rows in `geography.administrative_areas`, and the lines of an address are columns of one row with a fixed vocabulary (`address_line_1`, `address_line_2`, `dependent_locality`, ...), not a repeating `address_line[]`. `display_template` is one text document (template source parsed by the formatter), not a repeating group; `formatted_address` is one derived text value. A postal code is a single value; countries with several accepted spellings express them in one pattern.

### 2NF
PASS. Composite key: `geography.address_format_fields (address_format_id, field_type)`: every other column (`display_order`, `content_label_key`, `required`, `max_length`, `input_type`, `validation_pattern`, `example_value`, `autocomplete_hint`, `normalization_rule`, `created_at`) describes that field of that format version, and none depends on `field_type` alone: the label key, requirement, length and pattern of an `ADDRESS_LINE_1` legitimately differ between countries and between versions of one country, so there is no partial dependency to split into a `field_types` table (see "format versus field duplication"). Every other table has a single-column surrogate primary key (`administrative_area_id`, `address_format_id`, `address_id`), so partial dependencies are impossible there.

### 3NF
PASS with the documented, constraint-enforced derivations. `geography.administrative_areas`: `code`, `name`, `area_type`, `status`, `parent_area_id`, `display_order` are facts about the area; nothing about the country is repeated (the country is the `country_id` foreign key). `geography.address_formats`: `display_template`, `status` and the period are facts about the version; the country attributes live on `geography.countries`. `geography.address_format_fields`: no attribute of the format (status, period, template) is repeated on a field. `geography.addresses`: the address parts, `location`, `validation_status`, `validation_source`, `provider_*`, `raw_input` and `time_zone_id` are facts about the address; the country name, the format rules and the area attributes (type, status, parent) are NOT repeated (they are reached through the foreign keys). Deliberate exceptions, each enforced so it cannot drift (see Intentional denormalization): `addresses.administrative_area_code` (determined by `administrative_area_id`), `addresses.administrative_area_name` (determined by `administrative_area_id` as of insert), `addresses.formatted_address` (determined by the parts and the format template) and `addresses.country_id` (determined by `address_format_id`).

### BCNF
PASS except four recorded, deliberate determinants that are not candidate keys, each prevented from drifting by the database. Candidate keys checked: `geography.administrative_areas`: `administrative_area_id` and `(country_id, code)` (the superkeys `(administrative_area_id, country_id)` and `(administrative_area_id, country_id, code)` are the targets of composite foreign keys); `geography.address_formats`: `address_format_id` and `(country_id, version)` (superkey `(address_format_id, country_id)`); `geography.address_format_fields`: `(address_format_id, field_type)` and `(address_format_id, display_order)`, both candidate keys, so every dependency among the other columns of a row is determined by a key; `geography.addresses`: `address_id` only. Determinants that are NOT candidate keys: (1) `geography.addresses`: `address_format_id -> country_id` (a format version belongs to exactly one country; the country is stored on the address because it is filtered and keyed on directly and is part of the area key; the composite foreign key `fk_addresses__format_country (address_format_id, country_id)` to `uq_address_formats__format_country` makes drift impossible); (2) `geography.addresses`: `administrative_area_id -> administrative_area_code` (the composite foreign key `fk_addresses__area_country_code (administrative_area_id, country_id, administrative_area_code)` to `uq_administrative_areas__area_country_code` makes drift impossible, and the code is immutable on the area); (3) `geography.addresses`: `administrative_area_id -> administrative_area_name` holds only as of insert (a snapshot: area names may be corrected later, so it is not a dependency over time and cannot go stale in the sense of drifting; the row is immutable); (4) `geography.administrative_areas`: for a non-NULL parent, `parent_area_id -> country_id` (children carry their own country because `(country_id, code)` is the natural key; the composite foreign key `fk_administrative_areas__parent (parent_area_id, country_id)` states that it equals the parent's country and neither value can change, so there is no update anomaly). `address_formats.effective_to` equals the successor's `effective_from` (a cross-row dependency, recorded under Intentional denormalization, closed once, exclusion constraint as arbiter). `audit_events`: `action` determines which subject columns are NULL, which is a CHECK shape and not a stored fact (as in GEO-001). Everything else is determined by a candidate key.

### Duplicate concepts examined
Each of the following was challenged and the decision recorded.

- **Format versus field duplication.** A format version and its fields could have been one row (a JSON `fields` list) or fields could have been defined once per field type and shared. Rejected both. A JSON list loses typed checks (field type vocabulary, lookup only for the area, pattern length, label key as a real foreign key to content) and could not be validated or queried by the database. A shared `field_types` table (type, label, required, length, pattern) would make attributes that legitimately vary per country (the requirement and length of `ADMINISTRATIVE_AREA`, the pattern of `POSTAL_CODE`, the label wording) depend on the type alone, which is false, so it would either be empty or force a country override table that is the same table again. One row per (format version, field type) states the truth. The cost is that a new version repeats the fields it did not change; that is accepted on purpose: a published version must stay immutable and complete, and an inheritance model (a version stores only the diff from its predecessor) would make an old version's meaning depend on another row and on code that merges them. Fields are not duplicated across countries either: each country has its own versions because the data differs.
- **Postal code rules: why there is no `postal_code_rules` table.** The pattern, example, normalization and maximum length of a postal code are attributes of the `POSTAL_CODE` field of one format version, so they live on that `address_format_fields` row. A separate table keyed by country would duplicate (format version, field) information in a second place, give two answers to "is `12345` a valid US postal code" when they disagree, and could be edited independently of the version an old address was validated with (re-interpreting stored addresses). One validator serves forms, the service and any list of postal codes (`validateFieldValue` / `validatePostalCode`), so a service-area postal list validates with the same rule. Countries with several accepted spellings put the alternatives in the one pattern; a country without postal codes simply has no `POSTAL_CODE` field. Phone numbering rules are not modelled (DEBT-0038).
- **Administrative area hierarchy.** Areas form a tree (state, then optionally county or region) held as an adjacency list: `parent_area_id` with the composite foreign key `(parent_area_id, country_id)` keeps parent and child in one country. No `level` or `path` column: depth is derived by walking the parent chain (at most two or three hops, and only the areas a format needs are loaded), `area_type` names the kind, not the depth. A closure table or materialized path was rejected as speculative (no query needs ancestors yet, and each would be a derived duplicate of the parent column). Identity (country, code, parent) is immutable and the parent must exist before the child, so a cycle is structurally impossible and `ck_administrative_areas__not_own_parent` covers the trivial case. Areas are reference rows of a country, not a copy of `geography.markets`; markets do not yet reference an area (DEBT-0041).
- **Latitude and longitude duplication.** Coordinates are stored ONCE, as the single `geography(Point,4326)` `location`. Separate `latitude` and `longitude` columns next to the point (or instead of it) were rejected: two representations can drift, and they cannot be checked by a CHECK on the stored geography value because PostGIS silently coerces out-of-range input into range (so the range is validated BEFORE the point is built, in `isValidCoordinate`). Latitude and longitude are derived on read with `ST_Y` and `ST_X` of the geometry cast. `geography` (not `geometry`) keeps distances in meters and containment correct over any extent without casts (`DATABASE_CONVENTIONS.md` section 9). A geohash or cell id was not added (derivable, and nothing queries it).
- **`formatted_address` derivation.** The display text is derivable from the parts and the format template, yet it is stored, immutable, on the address (see Intentional denormalization): a historical address shown in a booking, receipt or message must stay byte-stable and must not depend on a later template or on the formatter's code version, and reads need no formatting. Drift is impossible because the row is immutable; it is recomputable from the row and its format version for verification (`formatStoredAddress`). The country line is not part of it (the country name is localized content resolved at display time).
- **`raw_input` JSON.** Kept as JSON, challenged below under "Unnecessary JSON".
- **Version references.** An address references the exact format VERSION it was validated with (`address_format_id`), never just the country, so a newer or corrected format cannot re-interpret a stored address and `formatStoredAddress` renders with the original template. Formats are never deleted, so the reference is permanent. The surrogate id plus the unique `(address_format_id, country_id)` key was chosen over a foreign key on `(country_id, version)` so audit rows, events and the field table can point at one id; the composite key keeps the country consistent.
- **Snapshot duplication: why there is no address snapshot table.** A booking could copy the address into its own snapshot table at confirmation. Rejected: `geography.addresses` rows are immutable (an UPDATE is refused by trigger; a changed or enriched address is a NEW row), so the row an `address_id` names is already exactly what was accepted. A copy would store personal data in a second place with its own retention and erasure problem and would add a table that holds the same columns. The booking (and any owning domain) stores `address_id` with a restrict foreign key. Costs accepted: an edited saved address creates a new row (the owner repoints its reference; the old row stays for the bookings that used it), and erasure cannot simply delete a referenced row (DEBT-0036: anonymization in place or reference-aware deletion).
- **Country-specific columns: none.** There is no `state`, `zip_code`, `province`, `prefecture` or `county` column, and no per-country table. The eight field types (`ORGANIZATION`, `ADDRESS_LINE_1`, `ADDRESS_LINE_2`, `DEPENDENT_LOCALITY`, `LOCALITY`, `ADMINISTRATIVE_AREA`, `POSTAL_CODE`, `SORTING_CODE`) are generic address components; the format decides which apply, in which order, with which label, length and pattern. A ninth component would be a reviewed migration that widens `ck_address_format_fields__field_type` (the vocabulary is closed on purpose so a typo cannot create a field), not a per-country change.
- **Nullable-field explosion: why the nullable parts are inherent.** `geography.addresses` has many nullable parts (`organization`, `address_line_2`, `dependent_locality`, `locality`, `postal_code`, `sorting_code`, the area columns, `location`, `time_zone_id`, `provider_code`, `provider_reference`). That is the nature of one canonical model for every country: which parts exist is a property of the country format, so a part that a country does not use is NULL, and only `address_line_1` is required everywhere. The alternative, an entity-attribute-value table `address_parts (address_id, field_type, value)`, was rejected: it loses per-column length and not-blank checks (`ck_addresses__text_values`), makes every read a pivot over eight rows, cannot hold the typed foreign key of the area or the geography point, and replaces a closed, small vocabulary (not an open-ended attribute set) with a generic bag. Per-country tables or columns were rejected as the very thing this model avoids. Cross-column rules that make the NULLs meaningful are CHECKs (`ck_addresses__area_consistent`, `__located_status_has_location`, `__manual_is_not_located`, `__provider`).
- **Provider data on the address.** `provider_code` and `provider_reference` are facts about how THIS address was obtained (the adapter and the vendor's place identifier), not attributes of a provider table: no provider table exists (no vendor is selected, DEBT-0037) and the code is a lower-case adapter code, not a key into a registry.
- **Time zone.** `time_zone_id` is a reference to the registered `geography.time_zones` row, never free text or an offset. It is a fact about the location supplied by a geocoder, distinct from the market default time zone (which stays the fallback; DEBT-0034).
- **Format lifecycle: draft and published rows in one table.** A separate `address_format_drafts` table would be 1:1 with `address_formats` (same identity, same fields) and would require copying the rows at publication. As in content, the draft IS the future published row: lifecycle is `address_formats.status` with a guard trigger, and a draft is immutable from creation. Unused drafts stay `DRAFT` (partial indexes are not needed at this size; DEBT-0039).
- **Audit versus state.** Audit records who did what and when plus the field diff (`{status: [DRAFT, PUBLISHED], effectiveFrom: [proposed, actual]}`); the current values live on the format row. Area changes are audited against the country with the changed area codes. Address rows themselves are not audited: they are immutable and carry their own validation status, source and creation time.

### Derived fields examined
- `geography.addresses.formatted_address`: derived from the parts and the format template; stored and immutable (see above).
- Latitude and longitude: derived on read from `location` (`ST_Y`, `ST_X` of the geometry cast); not stored.
- Whether a format is "current", "in force" or "latest": derived from `status` and the half-open window at read time (`formatInEffect`); no `is_current` or `is_latest` column. The `status` marker `PUBLISHED` is a lifecycle fact (the exclusion constraint and the immutability guard need it), not a current flag.
- The administrative-area entry mode of a country (`LOOKUP`, `FREE_TEXT`, `NONE`): derived from the `ADMINISTRATIVE_AREA` field of the format in force, not stored.
- Area depth, ancestors, and the number of areas of a country: derived by walking `parent_area_id` or counting rows; no `level`, `path` or count columns.
- `postalCodeExample` of the read model: derived from the `POSTAL_CODE` field `example_value`.
- The next format version number: max plus one per country, allocated while the country row is locked; `uq_address_formats__country_version` is the arbiter.
- Display order of areas: `display_order` when set, otherwise alphabetical by name (derived at read time).
- `updated_at` columns on `administrative_areas` and `address_formats` are maintained by the application in the same transaction (no trigger), as in the other registries; `addresses` and `address_format_fields` have no `updated_at` because their rows never change.
- No counts, totals or "number of addresses per country" columns exist.

### Intentional denormalization
1. `geography.addresses.formatted_address`: derived display text, written at insert by the central formatter from the parts and the template of the format version used; immutable row, so no drift; recomputable. Lets historical addresses stay byte-stable.
2. `geography.addresses.administrative_area_code`: repeats `administrative_areas.code`; composite foreign key `fk_addresses__area_country_code (administrative_area_id, country_id, administrative_area_code)` to `uq_administrative_areas__area_country_code`; the code is immutable there; `ck_addresses__area_consistent` makes id and code NULL together.
3. `geography.addresses.administrative_area_name`: the area name as of insert (a snapshot) for a lookup area, the normalized free text for a format whose area field is `TEXT` (no id, no code); `ck_addresses__area_consistent` requires a name whenever a code exists.
4. `geography.addresses.country_id`: repeats the country of the format version; composite foreign key `fk_addresses__format_country (address_format_id, country_id)` to `uq_address_formats__format_country` makes drift impossible; it also keeps the area in the address country.
5. `geography.address_formats.effective_to` (and `effective_from` raised once): `effective_to` equals the successor's `effective_from`; stored so that `ex_address_formats__no_overlap` can forbid overlapping periods in the database. The guard trigger permits exactly one raise of `effective_from` at publication (never lowered) and exactly one closure of a NULL `effective_to` of a published format; a draft is immutable.
6. `geography.addresses.raw_input`: JSON document, see below.
7. `geography.audit_events.address_format_id`: a third nullable subject foreign key under `ck_audit_events__subject`, instead of a polymorphic id (as in GEO-001); `changes` stays the one JSON diff column.
8. `geography.address_format_fields.content_label_key`: a reference to content by key (natural-key foreign key to `content.entries (key)`), not a copy of the label text; keys are immutable, so it cannot go stale. Error messages are likewise content keys derived from the issue code (`address.error.<code>`), not stored anywhere in geography.

Unnecessary JSON, challenged: the only new JSON column is `geography.addresses.raw_input`. Its shape depends on the source (structured form fields for a manual entry; the query, the suggestion id and the resolved fields for an autocomplete selection; whatever a future import provides), it is read back whole for review and disputes, and it is never filtered or joined relationally; typed columns per source would be sparse and mostly NULL. It is checked to be a JSON object of at most 4000 characters of text (`ck_addresses__raw_input`), the row is immutable, and it is personal data: never returned by ordinary responses, never logged. Everything the platform queries is a typed column (the normalized parts, the area reference, the point, status, source). No other JSON exists in the new tables: the fields of a format are rows, not a JSON list; `geography.audit_events.changes` keeps its GEO-001 shape.

### Index review
Each index and the query path it serves (constraint-backed indexes included):
- `geography.administrative_areas`: `pk_administrative_areas` (lookup by id, foreign key target); `uq_administrative_areas__country_code (country_id, code)` serves the lookup of an area by country and code and the whole area list of a country (leading `country_id`), and covers the `country_id` foreign key; `uq_administrative_areas__area_country (administrative_area_id, country_id)` is the target of the parent key; `uq_administrative_areas__area_country_code (administrative_area_id, country_id, code)` is the target of the address area key. These supporting unique keys are required by the composite foreign keys and cost one tiny index each (tens to hundreds of rows per country).
- `geography.address_formats`: `pk_address_formats`; `uq_address_formats__country_version (country_id, version)` serves the versions of a country, the next version number and covers the `country_id` foreign key; `uq_address_formats__format_country (address_format_id, country_id)` is the target of `fk_addresses__format_country`; `ex_address_formats__no_overlap` (partial gist on `country_id` and the period, created by the exclusion constraint) serves the overlap check at publication and the lookup of the PUBLISHED format of a country at an instant (equality on `country_id`; a country has a handful of versions, so the time filter is applied to a few rows). No separate index for "the active format by country and time": the exclusion constraint's gist index and the unique key serve it.
- `geography.address_format_fields`: `pk_address_format_fields (address_format_id, field_type)` serves loading the fields of a format and covers the `address_format_id` foreign key; `uq_address_format_fields__format_order (address_format_id, display_order)` guarantees a unique order and serves ordered reads of the same rows.
- `geography.addresses`: `pk_addresses` serves the only lookup path, by `address_id` (the reference owning domains hold). There is no index on `postal_code`: nothing looks addresses up by postal code (a service area will hold its own postal-code rows, and an address-by-postal-code query would need its own review). There is no GiST index on `location`: no query filters by location yet; the first spatial query (service areas and search) creates `idx_addresses__location` through its own review (`DATABASE_CONVENTIONS.md` section 9 requires it for any filtered geography column).
- `geography.audit_events`: `idx_audit_events__address_format (address_format_id, occurred_at DESC) WHERE address_format_id IS NOT NULL` serves the audit trail of one format, newest first; partial because exactly one subject key is set per row (like the country and market indexes), and it serves the foreign key check.

Foreign keys without a supporting index, and why: `geography.addresses.country_id`, `geography.addresses (address_format_id, country_id)`, `geography.addresses (administrative_area_id, country_id, administrative_area_code)` and `geography.addresses.time_zone_id` (the referenced countries, formats, areas and time zones are never deleted or re-keyed, so no referential check scans `addresses`; no query filters addresses by country, format version, area or time zone yet; an index is added with the first query that needs it, through its own review; addresses can become a large table, which is exactly why no speculative index is added); `geography.address_format_fields.content_label_key` (the target `content.entries` is never deleted and keys are immutable; no query starts from a label key); `geography.administrative_areas (parent_area_id, country_id)` (areas are never deleted or re-keyed; the country list is read whole; tiny table). `geography.address_formats.country_id`, `geography.address_format_fields.address_format_id` and `geography.administrative_areas.country_id` are covered by the unique or primary keys above. No speculative indexes.

### Final decision
Schema accepted. Ownership: all four tables are application-owned in schema `geography`; `content.entries` stays owned by `content` (twelve entries added by migration through the real lifecycle). Cardinality: country 1-N administrative areas; area 1-N child areas; country 1-N address format versions (at most one PUBLISHED version in force at any instant, by exclusion constraint); format 1-N fields (one per field type); country 1-N addresses; format version 1-N addresses; area 0..1-N addresses; time zone 0..1-N addresses; format 0-N audit events. Nullability reviewed: only genuinely optional columns are nullable (`organization`, second line, dependent locality, locality, postal code and sorting code because countries differ; `location` and `time_zone_id` until a provider supplies them; area and provider columns by their CHECKs; `effective_to` while open-ended; field pattern, example, autocomplete hint and normalization); `address_line_1`, the format reference, `formatted_address`, status, source and `raw_input` are required. Immutable historical state: addresses and field rows are never updated (`ROW_IMMUTABLE` by trigger); formats are immutable from `DRAFT` creation, `PUBLISHED` formats change only by the one-time closure of the open end, and never go back to `DRAFT` or get deleted; area identity is immutable and areas are never deleted. Concurrency: publications of one country serialize on the country row (`FOR UPDATE`, then the draft row, then the open predecessor), the exclusion constraint is the final arbiter against overlap (reason `FORMAT_PERIOD_OVERLAP`), and the version number is allocated under the same lock with `uq_address_formats__country_version` as arbiter; a field insert share-locks its format row, so it serializes with a publication; an address insert share-locks its format, area and time zone rows (in that order), so a concurrent deactivation of the area or time zone serializes with it and exactly one wins; the service writes the audit row and the outbox event in the same transaction and bumps the cache generation after commit. Every guard `RAISE` carries `geography_rule:<KEY>` in its DETAIL (nine new keys) and the service classifies on the key, never on message text. Configuration versus schema: field limits, patterns, templates and labels are rows and content keys, not code; no fee, price or tax value exists; no country is hardcoded. Seeds (reference data, not business values): 51 US administrative areas; US address format version 1 created `DRAFT`, given its fields and published through the guard; twelve content entries (five labels, seven validation messages) with 14 published versions through the real lifecycle (no trigger disabled); two geography audit rows; no outbox events; no address rows. Accepted limits, recorded rather than hidden: (a) addresses are personal data with no retention, erasure or exact-location access policy yet (DEBT-0036); the DELETE of an address is not refused, and referencing tables will use ON DELETE RESTRICT; (b) the insert guard requires the format to be PUBLISHED, not in force, so an address can be stored against a superseded version (the row records which version it used, and public validation reads a cache that can lag a publication by its TTL); (c) the rule that the last ACTIVE area of a country cannot be retired while a published format has a LOOKUP field is enforced by the service (`AREAS_IN_USE`) and at publication by the trigger, but a raw SQL deactivation of the last area is not refused by a trigger; (d) pattern safety (bounded length, no backreferences, lookbehind or repeated repeating groups) is vetted by the service, not by the database, and the engine runs patterns in the API process (DEBT-0042); (e) duplicate template tokens and stray braces are refused by the service only (the database checks membership and completeness at publication); (f) only the US dataset exists (DEBT-0040), markets do not reference an area (DEBT-0041), no provider is configured (DEBT-0037); (g) the 4000-character limit of `raw_input` is checked by the service on compact JSON text and by the database on the `jsonb` text (which adds a space after every separator), so an input near the limit can pass the service and still be refused by `ck_addresses__raw_input` (a constraint error, never data loss). Retention: all history retained (no purge) pending DEBT-0036. Migration risk: low; four new tables, one additive nullable column and two CHECKs widened on a small append-only table in one transaction (a brief exclusive lock on `geography.audit_events`), seeds are data, nothing existing is rewritten. Backfill: none. Rollback: forward-fix only (`MIGRATION_POLICY.md`); locally rebuild from zero with `pnpm stack:reset`; formats, fields and addresses are never updated and reference rows never deleted, so there is nothing to restore. Compatibility: additive and backward compatible (existing audit rows satisfy the wider CHECKs; no column or constraint was removed or loosened beyond the audit widening).

## ID-001

Tables reviewed: all new, in schema `identity`: `identity.roles`, `identity.accounts`, `identity.account_roles`, `identity.external_identities`, `identity.account_status_history`, `identity.account_profiles`, `identity.account_audit_events`. Reused read-only: `content.entries` (foreign key from `roles.name_content_key`; 17 entries seeded by migration 0009 through the real lifecycle), `content.locales` (foreign key from `account_profiles.preferred_locale`), `geography.time_zones` (foreign key from `account_profiles.time_zone_id`), `integration.outbox_events` (five new event types, aggregate type `identity_account`, no change). No existing table, column or constraint is changed. Keycloak's own database is out of scope (infrastructure-owned; nothing of it is mirrored).

### 1NF
PASS. Every column is an atomic scalar except `identity.account_audit_events.changes`, a JSON object recorded and justified under "Unnecessary JSON" below. Everything that could have been an array is rows: the roles of an account are rows of `account_roles` (not a `roles text[]` or a JSON list on `accounts`), the logins of an account are rows of `external_identities` (not a `subject` column on `accounts`), the status changes are rows of `account_status_history` (not a log column), the grants and deactivations are audit rows. There is no repeating group: first and last name are two named facts, the provider key is three named columns (`provider_type`, `issuer`, `provider_subject`), and a status vocabulary is a CHECKed scalar, not a list.

### 2NF
PASS. The only composite key is `account_roles (account_id, role_id)`. Every other column of that table (`status`, `granted_at`, `activated_at`, `deactivated_at`, `granted_by`, `grant_source`, `updated_at`) describes the membership of THAT account in THAT role; none depends on the account alone (the account status, primary role and profile live on `accounts` and `account_profiles`) or on the role alone (the code, name and status live on `roles`). Every other table has a single-column key (`role_id`, `account_id`, `external_identity_id`, `status_history_id`, `account_id` again for the one-to-one profile, `audit_event_id`), so partial dependencies are impossible there.

### 3NF
PASS with the documented, constraint-enforced derivations. `roles`: `name_content_key` and `status` are facts about the role. `accounts`: `status`, `primary_role_id`, `closed_at` and the timestamps are facts about the account; the primary role is a reference to the membership, no role attribute (code, name) is copied onto the account. `account_roles`: no attribute of the account or of the role is repeated; `status` is a function of `activated_at` and `deactivated_at` (recorded below); `granted_by` and `grant_source` are correlated (a `system:` actor usually means `BOOTSTRAP` or `SYSTEM`) but neither determines the other (the same actor type grants under different sources), so there is no transitive dependency. `external_identities`: `account_id`, `created_at` and `last_seen_at` depend on the link; `issuer` and `provider_subject` are part of a candidate key, not dependents, and no attribute of the account (email, name, status) is repeated. `account_status_history`: `from_status` repeats the `to_status` of the previous row (recorded below). `account_profiles`: the names, locale and time zone are facts about the person's profile; the locale display name, the time zone offset and the market defaults are reached through foreign keys and never copied. `account_audit_events`: `role_id` is NULL or set according to the action (a shape rule, not a stored fact).

### BCNF
PASS except four recorded, deliberate determinants that are not candidate keys, each prevented from drifting by the database. Candidate keys: `roles`: `role_id` and `code`; `accounts`: `account_id`; `account_roles`: `(account_id, role_id)`; `external_identities`: `external_identity_id` and `(provider_type, issuer, provider_subject)` (two candidate keys, every other dependency in the row is determined by one of them); `account_status_history`: `status_history_id` and `history_seq`; `account_profiles`: `account_id`; `account_audit_events`: `audit_event_id`. Determinants that are NOT candidate keys: (1) `account_roles`: `(activated_at IS NULL, deactivated_at IS NULL)` determines `status` (`ck_account_roles__lifecycle` states the equivalence and the guard trigger the transitions); (2) `accounts`: `status = 'CLOSED'` determines `closed_at IS NOT NULL` (`ck_accounts__closed_at`); (3) `account_status_history`: within one account, the previous row's `to_status` determines `from_status` (a cross-row dependency, stored so each row states its own transition; immutable rows, the writer takes it from the status read under the account row lock, the account trigger enforces the transition table, and the deferred constraint trigger `trg_account_status_history__consistent` refuses at commit a row whose `from_status` is not the previous row's `to_status`, NULL for the first row); (4) `account_audit_events`: `action` determines whether `role_id` is NULL (a CHECK shape). Everything else is determined by a candidate key.

### Duplicate concepts examined
Each of the following was challenged and the decision recorded.

- **Account versus external identity.** One table (`accounts` with a unique `keycloak_subject` column) was considered and rejected. The account is the long-lived business identity that every later domain references (addresses, bookings, balances, consents); the external identity is a technical binding to an identity provider that can be added, replaced or merged (ADR-0013: the IdP is swappable behind OIDC). With a column on `accounts` a second login, a second provider type, a re-created Keycloak user or a merge of two duplicate people would each be an account-level data migration; with a link table it is a row. It also keeps the Keycloak subject, a personal identifier, out of the table every other domain joins to: no business table stores it, and clients receive a separate generated `account_id` that is not derived from it. The subject alone is unique only within its issuer (a realm), so the key is `(provider_type, issuer, provider_subject)`, not the subject. The surrogate `external_identity_id` exists next to that natural key so audit rows, events and future references can point at the link with a short stable id (the natural key can be about 770 characters long). There is deliberately NO unique key on `account_id`: one account may have several links later. Cost: one extra row per person and one unique-key probe on the authenticated path, which is the lookup that is needed anyway.
- **Keycloak role duplication.** The Keycloak realm roles `customer` and `provider` and the application roles `CUSTOMER` and `PROVIDER` look like one fact held twice; they are not. A realm role is a coarse identity claim issued by another system and valid for the life of a token; an application role is marketplace state BananaGig owns, audits, can grant and deactivate, and must still know about when no token is present (ADR-0015: identity roles are not application permissions). Copying Keycloak roles into PostgreSQL on every login would create a second copy that can drift and would tie authorization to token content. Decision: roles are application REFERENCE DATA (`identity.roles`), and the realm roles are used exactly once, as a bootstrap hint when an account is created (`customer` gives CUSTOMER, `provider` gives PROVIDER, anything else no role; ADR-0025), and never read again; after that PostgreSQL is the only authority and the two can legitimately differ (a provider role added server-side to a customer account does not change the token). The hint is a recorded debt that goes away when explicit sign-up flows grant the role (DEBT-0044). A copy of the Keycloak role list is therefore never stored.
- **`roles` versus `account_roles`.** Two tables, two facts: `roles` is the catalog of roles that exist (name key, status, never deleted), `account_roles` is which accounts hold which role (a many-to-many resolved into a table with its own lifecycle). Rejected: `is_customer` and `is_provider` booleans or a `roles text[]` on `accounts` (a new role is a schema change for every row, no per-role lifecycle or grant source, no foreign key for audit and events, no managed display name). One row per (account, role) rather than one row per grant episode: the primary key makes a duplicate ACTIVE membership structurally impossible (an episode table would need a partial unique index `WHERE status = 'ACTIVE'` and a sort to find the current one), a deactivated role is reactivated in place, and the episode history lives where immutable history belongs, in `account_audit_events`. The accepted cost is that the latest-grant columns are overwritten on a re-grant (see Intentional denormalization).
- **Profile table versus `accounts`.** A one-to-one table is sometimes a normalization smell (the same key, so it could be columns); here it is a decision. A person has a name only after giving one (the Keycloak access token carries no name claim, by claim minimization), so an account exists before its profile; merging the two would make `first_name` and `last_name` nullable with a CHECK that says "both or neither", while a separate table keeps them `NOT NULL` and the row simply absent. It also keeps the personal data in one table (erasure and export, DEBT-0045, concern one table) and keeps the `accounts` row, which is read on every authenticated request, narrow. The profile has no `display_name`: the public display (first name and last initial, PRD SV-11.02) is derivable, so storing it would be a derived duplicate that can drift when a name changes, and no requirement asks for a chosen nickname. There is no stored full name either.
- **Current status plus status history.** Three designs were weighed. Status only: loses who, why and when (a suspension dispute or a closure under SV-11.09 cannot be answered). History only (the current state is the newest row): every authenticated request and every guard would need a subquery on a table that grows with every account, `closed_at` could not be a plain CHECK, and nothing could filter accounts by status without a lateral join. Both (chosen): `accounts.status` is the current state and `account_status_history` is the immutable record; this is intentional denormalization (the current state equals the newest `to_status`). Drift is prevented in BOTH directions by two DEFERRED constraint triggers (`STATUS_HISTORY_MISMATCH`), by immutable history rows, and by the service writing both in one transaction under the account row lock. `trg_accounts__status_history` (on `accounts`, `AFTER INSERT OR UPDATE OF status`) requires, at commit, the newest history row (highest `history_seq`) to equal the CURRENT `accounts.status`; `trg_account_status_history__consistent` (on the history table, `AFTER INSERT`) refuses at commit a stray row, a row whose `from_status` does not continue the previous row's `to_status` (NULL for the first row) and a newest row that differs from the account status. Both read the live account row at commit and not the row version that queued the event: the first version compared with the queued version and wrongly refused a transaction that passes through a transient status (suspend, then reactivate), which an integration test pinned and the fix corrected. A pointer `accounts.current_status_history_id` to the newest history row was rejected: a circular reference that needs deferral and no simpler than the equality check. No limit remains here: a stray raw INSERT, a broken `from_status` chain and a transient status are all handled at commit (tests in `packages/testing/src/identity-model.itest.ts`).
- **Active role persistence (rejected).** A column for the role the person is currently acting as (on `accounts`, or a `sessions` table) was considered and rejected. The active role is request context: the web server keeps it in its server session and sends `x-active-role`, and the API validates it against the ACTIVE memberships PostgreSQL holds on every request. Persisting it would create a second source of truth beside the web session, let two browsers of one account overwrite each other, need its own consistency rule against deactivating the role (a clear-before-deactivate rule like the primary role), turn a navigation click into a write that locks the hottest row, and go stale across logout. A tampered header cannot elevate: it can only name a role the account holds as ACTIVE. The one durable choice is the PREFERRED role (`primary_role_id`), explicit and rare, which only decides the default when a request names none. There is no `sessions` table (Keycloak owns protocol sessions; the web session lives in Valkey and holds the chosen role). Switching role never creates a Keycloak login or session (PRD CU-03.03).
- **Contact data duplication (deferred to ID-002 and ID-003).** The login email lives in Keycloak; the PRD also needs email and phone as BananaGig data with verification states (CU-03.04 to CU-03.06, SV-03, SV-11.03). Storing an `email` column on `accounts` now would duplicate the Keycloak email (two copies that drift) without any verification model, and inventing `email_verified_at` before the verification design would fix a model no flow exercises. So no contact column or table exists. ID-002 (email) and ID-003 (phone) decide which side is authoritative for the login email, the uniqueness of the normalized value, the verification record and the E.164 phone format. Accepted consequence: until then an account has no email in PostgreSQL, support finds a person through Keycloak, and access tokens keep carrying no email.
- **Premature address ownership (rejected).** `accounts.home_address_id` or an `account_addresses (account_id, address_id, label, is_default)` table was considered and rejected: no use case exists yet (saved addresses are CU-09, a provider's business address is PR), and the ownership semantics (labels, one default, per role, removal, retention under DEBT-0036) are undecided. `geography.addresses` stays ownerless (ADR-0023); the checkpoint that needs an address owner adds its own table that stores `address_id` with `ON DELETE RESTRICT`. Adding a speculative column now would also put a personal-data reference on the account row.
- **Polymorphic provider fields.** `provider text` plus an `attributes jsonb` bag, one table per provider (`keycloak_identities`, `google_identities`) and provider-specific columns (`email`, `username`) were considered and rejected. OIDC defines `iss` and `sub` for every provider, so `(issuer, provider_subject)` is the one universal key and a second OIDC provider needs no new column; `provider_type` only separates the namespaces and selects behavior, and its vocabulary is a closed CHECK (`KEYCLOAK`) that a migration widens when a provider genuinely needs different handling. Social sign-in (Google, Apple) goes through Keycloak brokering and arrives as the same Keycloak subject, so it adds no row type. No JSON, no per-provider column, no token claim copy is stored.
- **`history_seq` next to the primary key.** The uuid `status_history_id` is the entity key (convention), `history_seq` is the order. Ordering by `occurred_at` is not safe (equal timestamps for rows written in one statement batch, clock adjustments); an identity column gives a total order that also holds inside one transaction. Per account the sequence order equals the commit order because every status change locks the account row until commit.
- **Actors as text, not a foreign key.** `granted_by`, `actor` are text (`account:<account_id>`, `system:<name>` or, once admin actions exist with AD-07, `admin:<subject>`), as in the other audit tables: an actor can be a person, the platform or (later) an administrator whose identity model does not exist yet (DEBT-0046), and a foreign key to `accounts` would be wrong for two of the three. An actor names WHO acted; it is not the subject of the account being changed, which never appears in audit `changes`, events, errors, logs or responses.
- **Locale and time zone on the profile.** Both are references (`content.locales`, `geography.time_zones`), never free text, and neither copies a market default (a NULL means follow the market default, resolved at read time).

### Derived fields examined
- The public display name (first name and last initial): derived on read (`publicDisplayName`); no `display_name` column.
- The active role of a request: derived per request from the memberships and the preferred role; never stored.
- Whether an account is usable (not `SUSPENDED` or `CLOSED`): derived from `status` in code (`isAccountUsable`); no `is_active` flag.
- Whether an account is a customer or a provider, and its list of roles: derived from the ACTIVE rows of `account_roles`; no `is_provider` flag and no cached role list.
- The primary role code: derived by joining `roles`; only the id is stored.
- `accounts.closed_at`: stored, derived from the `CLOSED` transition; `ck_accounts__closed_at` (Intentional denormalization, 2).
- `account_roles.status`: stored, a function of `activated_at` and `deactivated_at`; `ck_account_roles__lifecycle` (Intentional denormalization, 3).
- `account_status_history.from_status`: stored, the previous row's `to_status` (Intentional denormalization, 7).
- The label of a status (`account.status.<status>`) and of a role (`name_content_key`): managed content keys, never stored text.
- `updated_at` on `roles`, `accounts`, `account_roles` and `account_profiles` is maintained by the writer in the same statement (no trigger), as in the other registries; `external_identities` has `last_seen_at` instead, and the history and audit tables have no `updated_at` because their rows never change.
- No counts, totals or "number of roles" columns exist.

### Intentional denormalization
1. `identity.accounts.status` next to `identity.account_status_history`: the current state equals the newest `to_status`. Kept because the status is read on every authenticated request and by the guards; drift is prevented in both directions by the two deferred constraint triggers `trg_accounts__status_history` (the newest history row equals the CURRENT status at commit) and `trg_account_status_history__consistent` (every history row continues the previous one and the newest equals the status), immutable history rows and the one-transaction write under the account row lock.
2. `identity.accounts.closed_at`: the closure instant, also visible as the `CLOSED` history row (the history `occurred_at` is a statement-clock time slightly after the transaction-time `closed_at`). `ck_accounts__closed_at` ties it to the status; a closed account never changes again.
3. `identity.account_roles.status`: a function of `activated_at` and `deactivated_at`, stored so the guards, the primary role rule and queries read an explicit state; `ck_account_roles__lifecycle` states the equivalence.
4. `identity.account_roles.granted_by`, `grant_source` (and `granted_at`, `activated_at`): describe the LATEST grant of the membership; re-granting a deactivated role overwrites them and clears `deactivated_at`. The row cannot hold the episode history (the primary key is the "no duplicate active membership" rule), so every grant, activation and deactivation is an immutable `ROLE_*` row in `account_audit_events` with actor, source and reason.
5. `identity.accounts.primary_role_id`: a pointer to one of the account's OWN memberships, via the composite foreign key `fk_accounts__primary_role (account_id, primary_role_id)` to `account_roles (account_id, role_id)` (MATCH SIMPLE, NULL means no preference). A foreign key proves the membership exists and belongs to this account; it cannot say the membership is ACTIVE and a CHECK cannot read another table, so `PRIMARY_ROLE_NOT_ACTIVE` (account trigger, membership row share-locked) and `PRIMARY_ROLE_IN_USE` (membership trigger, account row locked first) complete it, and the service moves or clears the primary role before it deactivates a role and when the account closes. Chosen over `is_primary boolean` plus a partial unique index on the membership: the pointer makes "at most one" true by construction (one column), moving the preference is one row change, and the foreign key carries the "held by this account" guarantee. The two tables reference each other without a deferred key because an account is inserted without a primary role (`ACCOUNT_INITIAL_STATE`).
6. `identity.external_identities.last_seen_at`: a mutable operational timestamp on an otherwise immutable row (the trigger allows exactly this column to change). It is touched by one conditional UPDATE at most once per `IDENTITY_LAST_SEEN_TOUCH_SECONDS` (default 300) so authenticated reads do not write on every request, and a failed touch never fails a request.
7. `identity.account_status_history.from_status`: repeats the previous row's `to_status` (NULL on the first row) so each row states its own transition; immutable rows, written from the status read under the account row lock, transition table enforced on `accounts`, continuity enforced at commit by `trg_account_status_history__consistent`.
8. `identity.account_audit_events.changes` (JSON) and `role_id`: `changes` is a document whose shape depends on the action, read back whole; `role_id` is a real foreign key set exactly for `ROLE_*` actions (`ck_account_audit_events__role`), instead of a polymorphic id.

Unnecessary JSON, challenged: the only JSON column is `account_audit_events.changes` (`{status: [from, to], source}` for role rows, `{status: [null, 'ACTIVE']}` and `{providerType}` for the creation rows, `{primaryRole: [old code, new code]}` (new code null when the primary role is cleared, also on account closure), `{fields: [names]}` for a profile update). Its shape depends on the action, it is read back whole for review, and nothing filters or joins on its content; typed columns per action would be sparse and mostly NULL. It is checked to be an object (`ck_account_audit_events__changes_object`), the row is immutable, and it never holds a token, a subject, a name or any personal value (a profile update records field NAMES only). Everything the platform queries is typed: roles and memberships, status, the provider key, names, locale and time zone. No JSON exists for the roles of an account, the status log, the provider data, the profile preferences or token claims (claims are never stored).

### Index review
Each index and the query path it serves (constraint-backed indexes included), and each deliberate absence:
- `identity.roles`: `pk_roles` (lookup by id; target of `account_roles.role_id` and `account_audit_events.role_id`); `uq_roles__code` (lookup by code at every grant, and the uniqueness rule). The table holds two rows; nothing else is indexed.
- `identity.accounts`: `pk_accounts` only. It serves the lookup by account id on every authenticated request (after the identity lookup), is the target of the foreign keys of five tables, and also serves the referencing side of the composite foreign key `fk_accounts__primary_role` (a lookup by `account_id`, which is unique). There is no index on `status`, `primary_role_id` or `created_at`: nothing filters accounts by them yet, and an administrative account search adds its own index through its own review.
- `identity.account_roles`: `pk_account_roles (account_id, role_id)` serves the membership list of one account (leading `account_id`), covers the `account_id` foreign key and is the target of `fk_accounts__primary_role`. No partial index on `status = 'ACTIVE'`: an account holds a handful of rows. No index on `role_id` (see below).
- `identity.external_identities`: `pk_external_identities` (the touch of `last_seen_at` and future references by id); `uq_external_identities__provider_issuer_subject (provider_type, issuer, provider_subject)` is THE lookup of every authenticated request and the arbiter of the first-request race (the loser gets a unique violation). No index on `account_id` (see below).
- `identity.account_status_history`: `pk_account_status_history`; `uq_account_status_history__seq (history_seq)` declares the uniqueness of the identity column as a constraint (an identity is unique only while its sequence is not reset or overridden; no query depends on it today, it is the one index kept for the guarantee); `idx_account_status_history__account (account_id, history_seq DESC)` serves the status timeline of one account, newest first, the newest-row and previous-row lookups of the two deferred consistency triggers (`ORDER BY history_seq DESC LIMIT 1`) and the `account_id` foreign key.
- `identity.account_profiles`: `pk_account_profiles (account_id)` serves the profile lookup by account and covers the `account_id` foreign key. No index on `preferred_locale` or `time_zone_id` (see below).
- `identity.account_audit_events`: `pk_account_audit_events`; `idx_account_audit_events__account (account_id, occurred_at DESC)` serves the audit timeline of one account and the `account_id` foreign key. These two history tables are the only ones that grow per account and are read per account.

Foreign keys without a supporting index, and why (the same list as in the migration header): `identity.external_identities.account_id` (lookups go from the identity to the account, never from an account to its identities on a hot path; an account has one Keycloak identity; accounts are never deleted); `identity.account_roles.role_id` (the question "who holds role X" is an administrative query that does not exist yet and a role is never deleted, so no foreign key check scans the table by role; the one reader is the `ROLE_IN_USE` check of the role guard, which reads `account_roles` by `role_id` when a role is deactivated, a rare administrative change that is refused while any membership holds the role; if roles are ever deactivated at scale, a partial index on `role_id` for PENDING and ACTIVE rows is added through its own review); `identity.accounts.primary_role_id` (the composite key is served through `pk_account_roles` on the referenced side and `pk_accounts` on the referencing side); `identity.roles.name_content_key`, `identity.account_profiles.preferred_locale`, `identity.account_profiles.time_zone_id` and `identity.account_audit_events.role_id` (the targets `content.entries`, `content.locales`, `geography.time_zones` and `identity.roles` are never deleted or re-keyed, so no foreign key check scans the referencing table, and no query filters by these columns). An index is added through its own data model review when a query path appears (administrative role listing, account search); there are no speculative indexes.

### Final decision
Schema accepted. Ownership: all seven tables are application-owned in schema `identity`; `content.entries`, `content.locales` and `geography.time_zones` stay owned by their schemas and are referenced read-only; Keycloak keeps credentials, MFA, protocol sessions and tokens. Cardinality: account 1-N memberships (one per role), role 1-N memberships, account 0..1 preferred membership (composite foreign key), account 1-N external identities, account 1-N status history rows, account 0..1 profile, account 1-N audit events, role 0-N audit events; locale and time zone 0..1-N profiles; content entry 1-N roles. Nullability reviewed: only genuinely optional columns are nullable (`accounts.primary_role_id` and `closed_at`; membership `activated_at` and `deactivated_at` by the lifecycle CHECK; history `from_status` for the creation row and `reason`; profile `preferred_locale` and `time_zone_id` meaning "follow the market default"; audit `role_id`, `changes`, `reason`); the names are NOT NULL because the profile row exists only once a name was given. Immutable historical state: history and audit rows by trigger (UPDATE and DELETE refused); identity columns by trigger (role id, code and `created_at`, account id and `created_at`, membership account and role, every column of `external_identities` except `last_seen_at`, profile account and `created_at`); `CLOSED` is terminal; no row of any table is ever deleted (DELETE refused by trigger on all seven, foreign keys restrict). Concurrency and lock order: ONE order everywhere, the ACCOUNT row first (`FOR UPDATE` in every service mutation), then the ROLE row (`FOR SHARE`), then the membership, external identity and profile rows of that account (the service's `grantInTx` takes the role share lock before the membership row lock; there is no lock cycle, because no transaction waits for an account or membership lock while holding an exclusive role lock); a rule that reads sibling rows locks the owner first (`PRIMARY_ROLE_IN_USE` locks the account row before it reads the primary role); activation checks share-lock the role or account row they read (a grant or activation locks the role and the account; an identity link or a profile write locks the account), so a concurrent role deactivation or account closure, which needs the row lock, serializes with them and exactly one wins (deterministic two-connection tests in `packages/testing/src/identity-model.itest.ts` prove each pair in both orders: primary role change against deactivation, closure against grant, role deactivation against grant, and two sessions linking one identity); the first request of a person is decided by the unique key (concurrent inserts of one `(provider_type, issuer, provider_subject)` have one winner; the loser rolls back its half-created account and re-reads the winner's), not by an application check, and a retried grant or a repeated profile write is idempotent by the membership primary key and by a no-change comparison. Every guard `RAISE` carries `identity_rule:<KEY>` in its DETAIL (13 keys) and the service classifies on the key, never on message text. Configuration versus schema: no fee, price, duration or rate exists; the name length bounds (1 to 50) are structural (PRD sign-up rule, CHECK plus contract constants), not configurable policy; the role names, status labels and messages are content keys, not text; the last-seen interval is configuration (`IDENTITY_LAST_SEEN_TOUCH_SECONDS`), not a value in the schema. Seeds (reference data, not business values): roles `CUSTOMER` and `PROVIDER` (both ACTIVE) and 17 content entries through the real lifecycle (no trigger disabled); no account, membership, identity, profile, history or audit row; no outbox events. Retention: all history retained (no purge); the profile and the external identity are personal data with no erasure or anonymization procedure yet (DEBT-0045, with DEBT-0036). Accepted limits, recorded rather than hidden: (a) the ACTIVE state of a preferred locale and of a time zone override is checked by the service at write time, not by a trigger on `account_profiles` (unlike `geography.addresses`): `upsertProfile` reads the locale and the zone `FOR SHARE` inside the transaction, so a concurrent deactivation serializes with the write, but a deactivation committed AFTER the write is allowed and the profile keeps referencing the now-inactive locale or zone by design (a historical reference, the same stance as addresses keeping their time zone), which readers resolve by falling back to the content chain and the market default; (b) one lock inversion is inherent: a raw SQL membership deactivation locks the membership row before its trigger can lock the account row, so racing a service call that holds the account row it can deadlock; PostgreSQL aborts one side (`40P01`) and the service reports a retryable `CONFLICT` (`CONCURRENT_UPDATE`); (c) the status vocabularies are wider than today's use on purpose: no path creates a `PENDING` account (the bootstrap creates `ACTIVE`; verification is a separate state, ID-002 and ID-003) and no code closes an account with rules (the machine exists, the closure rules do not, DEBT-0045); (d) the initial roles come from the Keycloak realm roles of the first token until explicit sign-up flows exist (DEBT-0044); (e) there is no contact data and no address ownership (ID-002, ID-003, DEBT-0017, DEBT-0036, DEBT-0038); (f) admin identities have no account and the admin actor is not modelled (DEBT-0046); (g) no cache of the account lookup (DEBT-0047) and no endpoint for the preferred role (DEBT-0048); (h) the role guard's `ROLE_IN_USE` check scans `account_roles` by `role_id` without an index (rare administrative operation, see above). Migration risk: low; one new schema, seven new tables, 17 content entries through the lifecycle in one transaction, nothing existing is rewritten. Backfill: none. Rollback: forward-fix only (`MIGRATION_POLICY.md`); locally rebuild from zero with `pnpm stack:reset`; no row is deleted by the application, so there is nothing to restore. Compatibility: additive and backward compatible (new schema; `content` gains entries only; `integration.outbox_events` is reused unchanged).
