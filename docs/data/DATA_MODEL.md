# Data Model (as of ID-004)

Describes what exists in the database today, verified against a database migrated from zero. The application schemas are the platform registries (`configuration`, `content`, `geography`), the outbox and, since ID-001, the first application identity schema (`identity`: accounts, roles and memberships and, since ID-002, email contacts and their verification challenges and, since ID-003, phone contacts and their verification challenges and, since ID-004, application sessions and devices). No other business-domain tables (catalog, booking, finance and so on) exist yet. Conventions: `DATABASE_CONVENTIONS.md`; migration rules: `MIGRATION_POLICY.md`; review rules: `DATA_MODEL_GUARDRAILS.md`; exact structure: `SCHEMA_SNAPSHOT.sql`.

## Application-owned tables

### `public.schema_migrations`
Migration bookkeeping. Columns: `version integer` (PK), `filename text` (unique), `checksum text`, `applied_at timestamptz`, `duration_ms integer` (nullable; NULL for 0001). Checks: `version > 0`, filename must match the zero-padded version, `duration_ms >= 0`. Rows are never updated or deleted.

### `integration.outbox_events`
Generic transactional outbox. One row per domain event, inserted in the same transaction as the state change; relayed to NATS JetStream by the worker; `published_at` marks completion. Key `outbox_event_id uuid` (also the event id and the JetStream message id). No foreign keys by design (domain-agnostic; `aggregate_id` is text). Partial indexes serve the relay (`idx_outbox_events__pending`) and retention purge (`idx_outbox_events__published_at`). Checks guard event-type format, version/type consistency, actor type, object payload, attempt counts. Business events do not exist yet; only the infrastructure `bananagig.infra.ping.v1` is produced (by the worker self-test).

### `configuration.*` (CFG-001): the product configuration registry

Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/CONFIGURATION.md`.

| Table | Role |
|---|---|
| `configuration.scope_levels` | Canonical scope hierarchy as reference data (`PLATFORM` rank 0 ... `DROP` rank 7). Higher rank is more specific and wins |
| `configuration.parameters` | One typed definition per key: data type, validation rules, sensitivity, approval policy, criticality, owner. No default column (the PLATFORM value is the default) |
| `configuration.parameter_scopes` | Scope levels at which a parameter may be overridden (allowed overrides) |
| `configuration.parameter_values` | One holder per (parameter, scope level, scope reference). `scope_ref` has no foreign key by design; the composite FK to `parameter_scopes` enforces the allowed level |
| `configuration.value_versions` | Immutable published values with half-open validity `[effective_from, effective_to)`; exclusion constraint prevents overlap per holder |
| `configuration.change_requests` | Workflow: `DRAFT -> PENDING_APPROVAL -> APPROVED -> SCHEDULED/ACTIVE -> SUPERSEDED`, plus `REJECTED`, `CANCELLED`. Content frozen after DRAFT; transitions guarded by trigger |
| `configuration.change_approvals` | Immutable decisions, one per approver per request; self-approval blocked by trigger under SECOND_APPROVER |
| `configuration.snapshots`, `configuration.snapshot_items` | Immutable record of a resolution: context and time, plus the exact version used per parameter |
| `configuration.audit_events` | Append-only audit of every mutation (actor, action, versions, reason, correlation id) |

Scope polymorphism choice: `scope_type` (FK to `scope_levels`) plus an opaque text `scope_ref`, with no foreign keys into domain tables that do not exist yet. Integrity of the *level* is enforced by the database; existence of the *referenced entity* is validated by the owning domain when it exists (DEBT-0024). ADR-0016.

### `content.*` (CFG-002): the content and localization registry

Managed product copy (UI text, message templates, help articles, legal documents) as stable keys with localized, effective-dated, immutable versions. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/CONTENT.md`. Content is not configuration: values that tune behavior stay in `configuration.*`.

| Table | Role |
|---|---|
| `content.locales` | Registry of locales (canonical BCP 47 subset) and the single locale authority for the platform (geography references it; GEO-001 added `display_name` and the generated `language`, `script`, `region`). `is_active` controls what may be served; the `is_platform_default` row (always active) is the last resort of every fallback chain: the unique index allows at most one, the guard trigger refuses to unset it (a migration moves it by disabling the guard inside its own transaction), and the resolver fails with `UNAVAILABLE` (`NO_PLATFORM_DEFAULT`) if none exists. Seeded with `en-US` only (structural reference data, not copy). Rows are never deleted |
| `content.entries` | Stable identity of one piece of content: unique dotted `key`, `content_type`, `owner_role`, `sensitivity`, `criticality`, `approval_policy`, `fallback_policy`, `max_scope_type`. Immutable except `is_active`. Legal documents are entries with `content_type = 'LEGAL'` (forced owner, policy, criticality and fallback by check constraint) |
| `content.entry_variables` | Typed placeholders of an entry, shared by every locale and version. Immutable; no required variable once the entry has versions |
| `content.versions` | One row per (entry, locale, scope, version number) holding the template body and its own lifecycle `DRAFT -> IN_REVIEW -> APPROVED -> SCHEDULED/PUBLISHED -> SUPERSEDED`, plus `REJECTED`, `CANCELLED`. Body immutable from creation; half-open validity `[effective_from, effective_to)`; exclusion constraint `ex_versions__no_overlap` forbids overlapping published rows per holder |
| `content.version_approvals` | Immutable review decisions, one per approver per version; trigger blocks self-approval under SECOND_APPROVER and requires the version to be `IN_REVIEW` |
| `content.snapshots`, `content.snapshot_items` | Immutable record of a resolution (requested locale, context, evaluation time) plus the exact version used per entry (snapshot reads expose no `effective_to`, so a read-back is byte-stable). Created only for copy that must be reproducible; routine UI labels are never snapshotted |
| `content.audit_events` | Append-only audit of every content mutation (actor, action, entry, locale for locale actions only, versions tied to the entry by composite foreign keys, reason, correlation id); bodies are never copied |

Scope reuse: `content.entries.max_scope_type` and `content.versions.scope_type` are foreign keys to `configuration.scope_levels`, so the platform has ONE scope hierarchy. Content uses only `PLATFORM < COUNTRY < MARKET` (a check restricts the values; specificity comes from `scope_levels.rank`). `versions.scope_ref` is an opaque text reference with no foreign key, the same polymorphism choice as ADR-0016 / DEBT-0024.

Legal documents are `LEGAL` entries, not a separate table family. Future acceptance records (ID-005) will reference `content.versions.version_id` (immutable) and `body_sha256`; no legal-specific table exists.

### `geography.*` (GEO-001): the geography registry

Country, currency, time zone and market reference data. Every default (currency, locale, time zone, distance unit, first day of week, date and time format) is a row value, never code. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`. Rows are never deleted: statuses are `PLANNED`, `ACTIVE`, `INACTIVE` (check constraints on the four status-bearing tables), and "active" never means anything else than `status = 'ACTIVE'`.

| Table | Role |
|---|---|
| `geography.currencies` | ISO 4217 currencies. Primary key is the alpha code `char(3)`; unique numeric code; `minor_unit_digits` 0..4 is data (not every currency has two decimals). Code, numeric code and minor unit digits are immutable (stored money depends on them) |
| `geography.time_zones` | IANA time zone identities (`iana_name` unique, surrogate `time_zone_id`). A NEW name must be listed in the database server's tz database (`pg_timezone_names`; the `posix/` and `right/` alias trees are refused; checked by trigger on insert only, so it reflects the server's tzdata at that moment and is not re-validated when tzdata is updated; an already registered name skips the scan). UTC offsets are never an identity |
| `geography.countries` | One row per country: ISO alpha-2/alpha-3/numeric (unique, immutable), `display_name_content_key` (foreign key to `content.entries (key)`: the display name is managed content, not a column), dialing code, default currency (FK to `geography.currencies`), default locale, and the format settings as enum codes `distance_unit`, `first_day_of_week`, `date_format_code`, `time_format_code`. Single source of the format settings: markets inherit them |
| `geography.country_locales` | Locales supported in a country (many-to-many to `content.locales`; immutable link rows). Its primary key `(country_id, locale)` is the target of the deferred composite foreign key `fk_countries__default_locale`, so a country default locale must be one of its supported locales |
| `geography.country_time_zones` | Time zones used in a country (many-to-many; immutable link rows). Its primary key is the target of `fk_markets__country_time_zone`, so a market time zone must belong to the market's country |
| `geography.markets` | A first-class operating area inside one country: unique kebab-case `code`, `name` (at most 120 characters), country, default locale, currency, default time zone, and the half-open effective window `[effective_from, effective_to)` on the row (no version table). Distance unit and date/time formats are NOT stored here (inherited from the country). "In effect" is derived from `status = 'ACTIVE'` plus the window at read time |
| `geography.market_locales` | Locales a market supports (many-to-many; immutable link rows). `country_id` repeats `markets.country_id` on purpose (intentional denormalization, see below) so that `(country_id, locale)` can reference `country_locales`; `(market_id, locale)` is the target of the deferred composite foreign key `fk_markets__default_locale` |
| `geography.audit_events` | Append-only audit of every geography management mutation: actor, action, exactly one subject (`country_id`, `market_id` or, since GEO-002, `address_format_id`: three nullable foreign keys under `ck_audit_events__subject`), field-level `changes` as a JSON object `{field: [old, new]}`, reason, correlation id. Reference values are public, so values are recorded (unlike `configuration.audit_events`) |

**Single locale authority.** `content.locales` stays the one registry of locales; geography references it by foreign key (`geography.country_locales.locale`) and by trigger (see below). Dependency direction in the database is geography -> content only (the content schema has no foreign key, column or trigger function that reads geography tables except the one deactivation guard below, which is owned by geography). GEO-001 changed `content.locales` additively (expand step): `display_name text NOT NULL` (inserted rows without one get the tag itself, by `content.default_locale_display_name`), plus generated stored columns `language`, `script`, `region` derived from the tag, so they cannot drift. The CHECK `ck_locales__display_name_not_blank` guards the name.

**Activation rules enforced by the database** (guard triggers, safety net under the service). The rows an activation reads are locked `FOR SHARE` (country: default currency, default locale and the ACTIVE time zone rows it relies on; market: country, currency, time zone and locale), so a concurrent deactivation, which needs the row lock, serializes with it and exactly one of the two wins (race-tested for market activation versus country deactivation, and country activation versus deactivation of its only ACTIVE zone, in both orders). Two rules read SIBLING rows and therefore lock the row that owns the invariant first: deactivating a time zone locks every ACTIVE country that uses it (`FOR UPDATE`, in `country_id` order) before it checks that the country keeps another ACTIVE zone, so two concurrent deactivations of two different zones of one country serialize and the second is refused; removing a country time zone or locale link share-locks the country row before it reads the country status, so an activation of that country and the removal of its only zone link serialize (race-tested in both orders). Every guard failure carries a machine-readable key in the error DETAIL, exactly `geography_rule:<KEY>` (keys: `CURRENCY_NOT_ACTIVE`, `COUNTRY_NOT_ACTIVE`, `TIME_ZONE_NOT_ACTIVE`, `LOCALE_NOT_ACTIVE`, `NO_ACTIVE_TIME_ZONE`, `COUNTRY_HAS_ACTIVE_MARKETS`, `CURRENCY_IN_USE`, `TIME_ZONE_IN_USE`, `LOCALE_IS_ACTIVE_DEFAULT`, `LINKS_PROTECTED`, `PLANNED_IS_INITIAL`, `IMMUTABLE_IDENTITY`, `NOT_DELETABLE`, `NOT_IANA`, `ROW_IMMUTABLE`); the service classifies by that key and never by message text (messages contain user-chosen codes). Lock order (service and triggers): the markets of a country (`market_id` order), then the country, then currency, time zone and locale rows. One inversion is inherent: a time zone row is locked by the UPDATE itself before its trigger can lock the country, so a raw SQL zone deactivation racing a market activation can deadlock; PostgreSQL aborts one side (`40P01`) and the service reports a retryable `CONFLICT` (`CONCURRENT_UPDATE`). A country can become `ACTIVE` only with an `ACTIVE` default currency, an `ACTIVE` default locale and at least one `ACTIVE` linked time zone (so it is created `PLANNED`, linked, then activated; creating a country directly `ACTIVE` fails); a market can become `ACTIVE` only with an `ACTIVE` country, currency, default time zone and default locale; a currency, time zone or locale cannot be deactivated while an `ACTIVE` country or market depends on it (a time zone also not while it is the last `ACTIVE` zone of an `ACTIVE` country; a locale only when it is the default of an `ACTIVE` country or market, so a non-default supported locale can be deactivated on purpose and public reads then hide it); a country cannot be deactivated while it has `ACTIVE` markets. Identity (ISO codes, market code and country, time zone id and name, currency code, numeric code and minor unit digits) is immutable; DELETE on currencies, time zones, countries and markets is refused; `geography.audit_events` is append-only.

**Status machine** (currencies, time zones, countries, markets). `PLANNED` is the initial status only: the guard triggers refuse any UPDATE that sets a row back to `PLANNED`. The permitted transitions are `PLANNED -> ACTIVE`, `PLANNED -> INACTIVE`, `ACTIVE -> INACTIVE` and `INACTIVE -> ACTIVE`, each subject to the activation and deactivation rules above; the service never writes `PLANNED` and treats activation and deactivation as idempotent.

**Immutable link rows.** `geography.country_locales`, `geography.country_time_zones` and `geography.market_locales` are never updated (BEFORE UPDATE trigger `geography.forbid_mutation`): a link is inserted or deleted. Deleting a link of an `ACTIVE` country (locale or time zone) is refused by trigger (after share-locking the country row); adding one is allowed. A market's default time zone and default locale are protected by their composite foreign keys, so a link a market still uses cannot be removed; the service checks this with plain reads before it deletes anything (typed `IN_USE`), because the foreign key check would lock the market row in the opposite lock order. `markets.name` is limited to 120 characters (`ck_markets__name_not_blank`).

**Cross-schema triggers.** `trg_locales__geography_guard` (function `geography.guard_locale_deactivation`) is a BEFORE UPDATE trigger on `content.locales`: it refuses `is_active` true -> false for a locale that is the default of an `ACTIVE` country or market. It sits next to the existing `trg_locales__guard` (owned by content). Country and market guards read `content.locales.is_active` (`FOR SHARE`) at activation. `geography.countries.display_name_content_key` has a foreign key into `content.entries`.

**Derived, never stored.** Market readiness (what a market still lacks to go live) is evaluated in code by a readiness registry and is not a column; "market in effect" is `status` plus the window; the distance unit and formats of a market come from its country at read time; locale language, script and region are generated columns.

**Seeded launch reference data** (migration 0007, deterministic, no business values, no tax, payment or address data): currency `USD` (840, 2 minor digits, `ACTIVE`); four IANA zones `America/New_York`, `America/Chicago`, `America/Denver`, `America/Los_Angeles` (all `ACTIVE`); country `US` (USA, 840, `ACTIVE`, +1, default currency `USD`, default locale `en-US`, `MILES`, `SUNDAY`, `MDY`, `12_HOUR`) with `en-US` in `geography.country_locales` and all four zones in `geography.country_time_zones`; the content entry `geography.country.us.name` (`UI_LABEL`, `en-US` body `United States`, taken through the real lifecycle to `PUBLISHED` with five `content.audit_events` rows, exactly like migration 0006); market `la-oc` ("LA & OC", `PLANNED`, `en-US`, `USD`, `America/Los_Angeles`, `effective_from` = migration time) with `en-US` in `geography.market_locales`; three `geography.audit_events` rows (`COUNTRY_CREATED`, `COUNTRY_ACTIVATED`, `MARKET_CREATED`, actor `system:migration`, correlation `seed-0007`). `content.locales.display_name` for `en-US` is back-filled to `English (United States)`. No other market, country or currency is seeded, and no outbox event is emitted. `la-oc` stays `PLANNED` until the owner activates it through the management API.

Events and cache are not stored in this schema: geography events reuse `integration.outbox_events` (aggregate types `geography_country`, `geography_market` and, since GEO-002, `geography_address_format`; identifiers and counts only); see the store table below for the cache.

### `geography.*` address model (GEO-002): administrative areas, address formats and the canonical address

Migration `0008_address_model.sql`. One canonical structured address for every domain (customer, provider, business, booking), driven by a per-country, versioned format held as rows: no country-specific column, table or code path. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/ADDRESSES.md`, review in `NORMALIZATION_LOG.md`. Decisions: ADR-0023 (immutable canonical address and data-driven format) and ADR-0024 (provider-neutral boundary and privacy).

| Table | Role |
|---|---|
| `geography.administrative_areas` | States, provinces, regions and similar areas of one country, hierarchical through `parent_area_id`. `code` is the canonical code inside the country without the country prefix (`CA`, unique per country), `name` the official proper name (not translated UI copy), `area_type` one of `STATE, PROVINCE, TERRITORY, DISTRICT, REGION, COUNTY, OTHER`. Status is `ACTIVE` or `INACTIVE` only (no `PLANNED`: a row has no activation prerequisites). Identity (id, country, code, parent, `created_at`) is immutable by trigger, so a parent chain cannot form a cycle; name, type, status and display order can change; rows are never deleted. Only the areas a country format needs are loaded (no counties or cities) |
| `geography.address_formats` | One row per country VERSION: `status` (`DRAFT`, `PUBLISHED`), `display_template` (lines separated by a newline, `{FIELD_TYPE}` tokens) and the half-open effective window `[effective_from, effective_to)`. The exclusion constraint `ex_address_formats__no_overlap` (gist on country plus `tstzrange`, `WHERE status = 'PUBLISHED'`) forbids two published formats of a country in force at the same time, so exactly one format is in force at any instant |
| `geography.address_format_fields` | The ordered field definitions of one format version, one row per field type (`ORGANIZATION, ADDRESS_LINE_1, ADDRESS_LINE_2, DEPENDENT_LOCALITY, LOCALITY, ADMINISTRATIVE_AREA, POSTAL_CODE, SORTING_CODE`): display order, label content key (foreign key to `content.entries (key)`), required, maximum length, input type (`TEXT`, or `LOOKUP` for the administrative area only), validation pattern, example, autocomplete hint and normalization rule. Field order, requirement, length, pattern and normalization are data that both the server validator and every client form read from here. The postal-code rule is the pattern of the `POSTAL_CODE` field row: there is no `postal_code_rules` table |
| `geography.addresses` | The ONE canonical structured address: the parts as typed columns, the country, the exact format VERSION it was validated with, an optional administrative area reference (id, code and name), one optional `geography(Point,4326)` `location`, an optional time zone reference, the generated `formatted_address`, `validation_status`, `validation_source`, provider code and reference, and the `raw_input` JSON object. Immutable once inserted. No owner column (customer, provider, booking, business): the owning domains hold their own `address_id` reference |

**Address format status machine.** `DRAFT -> PUBLISHED`, one way (the trigger refuses `PUBLISHED -> DRAFT`; a format is created as `DRAFT` and any other initial status is refused). A `DRAFT` is created with all its fields in one transaction and is immutable: neither the row (template, period) nor the fields can be edited (a correction is a new version), and fields can only be inserted while the format is `DRAFT` (the field guard share-locks the format row, so a concurrent publication serializes with a field insert). Publication requires at least one field and a required `ADDRESS_LINE_1`, every field of the format named by the template and every template token a field of the format, and, for a `LOOKUP` field, at least one `ACTIVE` administrative area in the country; the start may only be raised (never lowered) and the end stays open. A `PUBLISHED` format is immutable except that its open end `effective_to` is closed exactly once, by the format that succeeds it, in the successor's publication transaction; it can never be deleted (`NOT_DELETABLE`). Publication locks the country row first (`FOR UPDATE`), so publications of one country serialize; the service never lets a new format start at or before the one it closes (`START_NOT_AFTER_CURRENT`), and the exclusion constraint is the final arbiter against overlap (`FORMAT_PERIOD_OVERLAP`). "In force" is derived from the window at read time; there is no `is_current` column.

**Addresses are immutable, and the address row is the snapshot.** A BEFORE UPDATE trigger refuses every `UPDATE` of `geography.addresses` (`ROW_IMMUTABLE`): a changed or enriched address (for example a later geocode) is a NEW row. A booking that stores `address_id` therefore keeps the exact address accepted at booking time, and no `address_snapshots` table exists (rejected, see `NORMALIZATION_LOG.md` GEO-002). DELETE is not refused by the trigger: every table that references an address will use `ON DELETE RESTRICT`, so an address that is still referenced cannot be removed, and the retention and erasure policy is DEBT-0036. The insert guard requires the format to be `PUBLISHED` (not that it is still in force: an old version stays valid for the addresses that were validated with it), the administrative area to be `ACTIVE` and the time zone to be `ACTIVE`, each row share-locked so a concurrent deactivation serializes with the insert. Composite foreign keys keep the row consistent: `(address_format_id, country_id)` to `address_formats` (the format belongs to the address country) and `(administrative_area_id, country_id, administrative_area_code)` to `administrative_areas` (the area belongs to the country and the stored code equals the area code). Cross-column CHECKs bind status, source, provider and location (`GEOCODED` and `VERIFIED` need a location; `MANUAL` never has one; `AUTOCOMPLETE` is never `VERIFIED`; `VERIFIED` only from `GEOCODER` or `ADMIN`; a provider code is present exactly for `AUTOCOMPLETE` and `GEOCODER`, with `IMPORTED` free).

**PostGIS: a single point.** `geography.addresses.location` is `geography(Point,4326)`, built as `ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography` AFTER the service validated latitude -90..90 and longitude -180..180 (PostGIS silently coerces out-of-range input, so a CHECK cannot catch it). Latitude and longitude are derived on read with `ST_Y` and `ST_X` of the geometry cast; there are no `latitude` or `longitude` columns, so they cannot drift from the point. No GiST index exists on the column: nothing filters by location yet, and the first spatial query (service areas and search) adds it through its own review (`DATABASE_CONVENTIONS.md` section 9).

**`raw_input` is JSON on purpose.** It keeps what the person or provider submitted before normalization, as an object whose shape depends on the source (structured form fields, or a query plus the selected suggestion and its fields). It is read back whole, never filtered relationally, limited to a JSON object of at most 4000 characters (`ck_addresses__raw_input`) and is personal data (never in ordinary responses or logs). Typed columns per source would be sparse and meaningless for most rows.

**Guard keys.** GEO-002 adds nine keys to the `geography_rule:<KEY>` vocabulary (24 in total): `FORMAT_NOT_DRAFT`, `FORMAT_MUST_START_AS_DRAFT`, `FORMAT_STATUS_TRANSITION`, `FORMAT_IMMUTABLE`, `FORMAT_INCOMPLETE`, `FORMAT_TEMPLATE_MISMATCH`, `LOOKUP_WITHOUT_AREAS`, `FORMAT_NOT_PUBLISHED`, `AREA_NOT_ACTIVE`. The existing keys `NOT_DELETABLE`, `IMMUTABLE_IDENTITY`, `ROW_IMMUTABLE` and `TIME_ZONE_NOT_ACTIVE` are reused by the new guards. The service classifies on the key, never on message text.

**`geography.audit_events` change (expand step).** The table gains one nullable column `address_format_id` (foreign key to `address_formats`, restrict) and the partial index `idx_audit_events__address_format`. `ck_audit_events__action` is widened with `COUNTRY_ADMINISTRATIVE_AREAS_UPDATED`, `ADDRESS_FORMAT_DRAFTED` and `ADDRESS_FORMAT_PUBLISHED`, and `ck_audit_events__subject` now has three branches (`COUNTRY_%` names exactly a country, `MARKET_%` exactly a market, `ADDRESS_FORMAT_%` exactly an address format; every other subject column is NULL). Both CHECKs are dropped and re-created wider in the same transaction: a pure widening, no row is changed, and the append-only trigger is not involved. Area changes are audited against the country (`COUNTRY_ADMINISTRATIVE_AREAS_UPDATED`, `changes` `{added, updated}` lists of area codes).

**Seeded address data** (migration 0008, deterministic reference data; no business values, no personal data, no outbox event, actor `system:migration`, correlation `seed-0008`): 51 administrative areas of the country `US` (the 50 states with `area_type` `STATE` and the District of Columbia with `DISTRICT`, all `ACTIVE`, no parents); US address format version 1, created as `DRAFT`, given its five fields, then published through the guard (`ADDRESS_LINE_1` required, 100; `ADDRESS_LINE_2` optional, 100; `LOCALITY` required, 60; `ADMINISTRATIVE_AREA` required, 50, `LOOKUP`; `POSTAL_CODE` required, 10, pattern `^[0-9]{5}(-[0-9]{4})?$`, example `12345`), template `{ADDRESS_LINE_1}`, `{ADDRESS_LINE_2}` and `{LOCALITY}, {ADMINISTRATIVE_AREA} {POSTAL_CODE}` on three lines, with the audit rows `ADDRESS_FORMAT_DRAFTED` and `ADDRESS_FORMAT_PUBLISHED`; and 12 content entries taken through the real content lifecycle (five field labels `address.field.line1`, `line2`, `city`, `state`, `postal_code` of type `UI_LABEL`, and seven validation messages `address.error.required`, `too_long`, `invalid_format`, `unknown_area`, `unsupported_field`, `invalid_characters`, `lookup_unavailable` of type `PLAIN_TEXT`; maximum scope `COUNTRY`, `en-US`, PLATFORM copy for all twelve plus US-scoped wording for the state label ("State") and the postal-code label ("ZIP code"), so 14 published versions and 68 `content.audit_events` rows). No other country has a format or areas (DEBT-0040) and no address row is seeded.

### `identity.*` (ID-001): application accounts, roles and the Keycloak mapping

Migration `0009_identity_accounts.sql`. The BananaGig account of a person and everything the application (not Keycloak) knows about who that person is on the platform. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/ACCOUNTS.md`, review in `NORMALIZATION_LOG.md`. Decisions: ADR-0025 (application account versus Keycloak identity) and ADR-0026 (role membership and the active role context). Requirements served: CU-03.03, CU-09.23 and PR-01.04 (one login holds several roles), SV-11.02 (name and the public display rule), SV-11.08 (roles section; admin accounts are separate logins), SV-11.09 (a status machine for closure; the closure rules are DEBT-0045).

| Table | Role |
|---|---|

**The account versus the external identity.** Keycloak authenticates a person; PostgreSQL knows the account. The Keycloak subject is NOT a column of `identity.accounts`: `identity.external_identities` maps `(provider_type, issuer, provider_subject)` to an account, the unique key lets one subject link at most one account (the database decides a race, not application code), and the link is immutable and never deleted. Keycloak keeps passwords, MFA factors, protocol sessions and tokens; nothing of that, and no token or password hash, is stored in this schema. The only provider data stored is the key that IS the link (issuer and subject), which is why those two columns exist at all. Future social federation (Google, Apple) still arrives through the same Keycloak subject, so the provider vocabulary has one value today (`ck_external_identities__provider_type`) and no per-provider columns or JSON. Admin identities (client `bananagig-admin`) are separate logins with NO account row (SV-11.08, ADR-0015, DEBT-0046).

**Roles are reference data; memberships are rows.** `identity.roles` holds the two application roles; the Keycloak realm roles `customer` and `provider` are NOT duplicated into it as data. They are used exactly once, as a bootstrap hint when an account is created (ADR-0025), and never read again. `identity.account_roles` has the primary key `(account_id, role_id)`: that key IS the rule "an account holds a role at most once", so a duplicate ACTIVE membership cannot exist, while one account may hold `CUSTOMER` and `PROVIDER` at once (CU-03.03). Membership transitions (guard trigger): `PENDING -> ACTIVE | INACTIVE`, `ACTIVE -> INACTIVE`, `INACTIVE -> ACTIVE`; a row starts `PENDING` or `ACTIVE`, and `INACTIVE -> PENDING` is refused. Activating needs an ACTIVE role (`ROLE_NOT_ACTIVE`) and a non-CLOSED account (`ACCOUNT_CLOSED`). The grant history (who, when, source, reason) lives in `identity.account_audit_events`; the membership row describes only the latest grant, so re-granting overwrites `granted_at`, `granted_by`, `grant_source`, `activated_at` and clears `deactivated_at`.

**Primary role: a pointer to the account's own membership.** `identity.accounts.primary_role_id` is the persisted PREFERRED role (used as the active role when a request names none). It is a composite foreign key `fk_accounts__primary_role (account_id, primary_role_id)` to `identity.account_roles (account_id, role_id)` (MATCH SIMPLE: NULL means no preference), so it can only name a role THIS account holds. A foreign key cannot say "and that membership is ACTIVE", and a CHECK cannot read another table, so two triggers add it: `identity.guard_accounts` requires the membership to be ACTIVE whenever the primary role is set or changed (`PRIMARY_ROLE_NOT_ACTIVE`, membership row share-locked), and `identity.guard_account_roles` refuses moving an ACTIVE membership out of ACTIVE while it is the account primary role (`PRIMARY_ROLE_IN_USE`, after locking the account row). The service therefore moves or clears the primary role BEFORE deactivating a role, and clears it when the account closes. A single pointer column makes "at most one primary role" true by construction; the rejected alternative (`is_primary boolean` on the membership plus a partial unique index) needs two row changes to move the preference and still has no foreign-key guarantee. The account is created without a primary role (`ACCOUNT_INITIAL_STATE`), so the two tables reference each other without any deferred constraint: account, then membership, then the pointer.

**Status machine and the history, with two deferred consistency triggers.** `accounts.status` is the CURRENT state, read on every authenticated request; `identity.account_status_history` holds every change (immutable, append-only, `from_status` NULL for the creation row). Transitions (trigger `identity.guard_accounts`): `PENDING -> ACTIVE | CLOSED`; `ACTIVE -> SUSPENDED | CLOSURE_REQUESTED`; `SUSPENDED -> ACTIVE | CLOSURE_REQUESTED | CLOSED`; `CLOSURE_REQUESTED -> ACTIVE | CLOSED`; `CLOSED` is terminal (any UPDATE of a closed account is refused, `ACCOUNT_CLOSED`). An account is inserted `PENDING` or `ACTIVE`, without a primary role. Closing requires no PENDING or ACTIVE membership and no primary role (`ACCOUNT_HAS_ACTIVE_ROLES`; the service deactivates the roles first, in the same transaction) and `ck_accounts__closed_at` ties `closed_at` to `status = 'CLOSED'`. Keeping a current state next to its history is intentional (see the denormalization table), and the two stay consistent in BOTH directions through two deferred constraint triggers (`DEFERRABLE INITIALLY DEFERRED`, `STATUS_HISTORY_MISMATCH`), both of which read the account status as it is AT COMMIT: `trg_accounts__status_history` (function `identity.check_status_history`, `AFTER INSERT OR UPDATE OF status` on `accounts`) requires that the newest history row of the account (highest `history_seq`) equals the CURRENT `accounts.status`, so a status change without its history row fails; `trg_account_status_history__consistent` (function `identity.check_status_history_row`, `AFTER INSERT` on `account_status_history`) requires that the row continues the previous row of the account (`from_status` equals the previous `to_status`, NULL for the first row) and that the newest row equals the current status, so a stray history row, a row that breaks the chain and a newest row that differs from the account all fail. Comparing with the current status read at commit, not with the row version that queued the event, is what lets a transaction pass through a transient status (suspend and reactivate) as long as the end state and the history agree. The service writes the status and its history row in one transaction, so both checks pass. Per account, `history_seq` order equals commit order because every status change locks the account row until commit.

**The active role is NOT persisted.** The role a request acts as is request-scoped application context, not a column. The web server keeps the chosen role in its server session and sends it in the `x-active-role` header; the API validates it against the ACTIVE memberships PostgreSQL holds on EVERY request (`ACCOUNT_ROLE_NOT_HELD` or `ACCOUNT_ROLE_NOT_ACTIVE` otherwise). Without a request role the persisted preference decides (the primary role if still active, else the only ACTIVE role, else none). A persisted active role was rejected (see `NORMALIZATION_LOG.md` ID-001): it would be a second source of truth beside the web session, it would make two browsers or devices of one account fight over one value, it would need its own consistency rule against deactivation, and switching it would write on a navigation event. Switching role never creates a Keycloak login or session (CU-03.03).

**Profile: one-to-one, names only, no display name.** `identity.account_profiles` is a separate table with `account_id` as its key because a person has a name only after giving one (the Keycloak access token carries no name claim, by minimization), so the name columns are `NOT NULL` and the row does not exist until then; it also keeps personal data in one table that the hot `accounts` row does not carry. The name rules (1 to 50 characters each, trimmed, no control or bidirectional-override characters: PRD CU-03 sign-up field table, SV-11.02) are structural, so they are CHECK constraints and contract constants, not configuration. There is NO stored `display_name`: the public display (first name and last initial, SV-11.02) is derived on read (`publicDisplayName`), so it cannot drift when a name changes, and no public profile API exists yet. `preferred_locale` references `content.locales` (the single locale authority) and `time_zone_id` references `geography.time_zones`; the market default stays the fallback and is never copied into the profile. `upsertProfile` reads the locale (`content.locales`) and the time zone (`geography.time_zones`) `FOR SHARE` inside its transaction, so a concurrent deactivation of that locale or zone serializes with the profile write; there is no trigger on `account_profiles`, so a deactivation committed AFTER the write is allowed and the profile keeps referencing the now-inactive locale or zone by design (a historical reference, the same stance as addresses keeping their time zone); readers fall back to the content chain and the market default.

**No phone data, no address ownership.** At ID-001 `identity` stored no contact data; since ID-002 it stores the email contact and its verification (section below). Since ID-003 it also stores the phone contact and its verification (section below, CU-03.04 to CU-03.06). It still stores no consent, and Keycloak keeps the login email, which is not copied (nor is any phone number ever written to Keycloak). `geography.addresses` stays ownerless: an `address_id` reference from identity (saved addresses, CU-09) is added by the checkpoint that has an address use case, with `ON DELETE RESTRICT`. Retention, erasure and export are open (DEBT-0045, DEBT-0036).

**Immutability and never-deleted rows.** No row of any `identity` table can be deleted (every table has a BEFORE DELETE refusal, `NOT_DELETABLE` or `ROW_IMMUTABLE`, and the foreign keys are `ON DELETE RESTRICT`); status changes and new rows replace deletion, so there is nothing to restore after a mistake and erasure needs its own reviewed procedure (DEBT-0045). `account_status_history` and `account_audit_events` refuse UPDATE and DELETE (`ROW_IMMUTABLE`). Identity columns are immutable (`IMMUTABLE_IDENTITY`): role id, code and `created_at`; account id and `created_at`; membership account and role; every column of `external_identities` except `last_seen_at`; profile account and `created_at`.

**Lock order and concurrency.** One order everywhere: the ACCOUNT row first (`FOR UPDATE` in every service mutation), then the ROLE row (`FOR SHARE`), then the membership, external identity and profile rows of that account (inside a grant the service, in `grantInTx`, takes the role share lock before the membership row lock; there is no lock cycle, because no transaction holds an exclusive role lock while it waits for an account or membership lock). A rule that reads sibling rows locks the owning account row first (`PRIMARY_ROLE_IN_USE`). Activation checks (`guard_account_roles`, `guard_external_identities`, `guard_account_profiles`) share-lock the role or account row they read, so a concurrent role deactivation or account closure, which needs the row lock, serializes with them and exactly one wins; the status check of a profile or identity write likewise serializes with a closure. The first request of a person is decided by the unique key: concurrent inserts of the same `(provider_type, issuer, provider_subject)` produce one winner; the loser's transaction (including the half-created account) rolls back and the service re-reads the winner's account. One inversion is inherent, as in GEO-001: a raw SQL membership deactivation locks the membership row before its trigger can lock the account row, so racing a service call that holds the account row it can deadlock; PostgreSQL aborts one side (`40P01`) and the service reports a retryable `CONFLICT` (`CONCURRENT_UPDATE`).

**Guard keys.** Every guard failure is SQLSTATE `23000` with DETAIL exactly `identity_rule:<KEY>` (a vocabulary separate from `geography_rule`); the service classifies on the key, never on message text. The 13 keys of ID-001 (ID-002 adds 13 more, listed in its section below): `NOT_DELETABLE`, `ROW_IMMUTABLE`, `IMMUTABLE_IDENTITY`, `ACCOUNT_INITIAL_STATE`, `ACCOUNT_STATUS_TRANSITION`, `ACCOUNT_CLOSED`, `ACCOUNT_HAS_ACTIVE_ROLES`, `ROLE_NOT_ACTIVE`, `ROLE_IN_USE`, `ROLE_STATUS_TRANSITION`, `PRIMARY_ROLE_NOT_ACTIVE`, `PRIMARY_ROLE_IN_USE`, `STATUS_HISTORY_MISMATCH`. PL/pgSQL does not short-circuit boolean operators, so the INSERT and UPDATE branches of `guard_accounts` and `guard_account_roles` are separate (`OLD` does not exist for an INSERT and must never be referenced in an expression together with `TG_OP`).

**Audit and events.** Account status changes are audited by `account_status_history` (actor, reason, correlation id) and by the outbox event; every other mutation writes its `account_audit_events` row or rows in the same transaction (`changes` records status pairs, grant source, role CODES and, for a profile update, the NAMES of the changed fields, never a value; it never holds a token, a subject or a name). Five outbox events (aggregate type `identity_account`, identifiers only, never a name, subject or token) reuse `integration.outbox_events`: `bananagig.identity.account-created.v1`, `external-identity-linked.v1`, `account-role-granted.v1`, `account-role-deactivated.v1`, `account-status-changed.v1`. Creating an account emits `account-created`, `external-identity-linked` and one `account-role-granted` per bootstrap role, and no `account-status-changed`. `account-role-deactivated` is emitted only for a membership that was ACTIVE (a PENDING membership was never announced by `account-role-granted`, so its deactivation is audited but not announced). Closing an account deactivates every PENDING or ACTIVE membership (one `ROLE_DEACTIVATED` audit row each) and, when it clears a primary role, writes a `PRIMARY_ROLE_CHANGED` audit row (`{primaryRole: [code, null]}`, same actor, reason and correlation id); it emits `account-status-changed` once. An actor (`account:<id>`, `system:<name>` or `admin:<subject>`, admin actions arrive with AD-07 and DEBT-0046) names WHO acted and is stored in `granted_by`, the audit actor, the history actor and the event `actor_id`; it is not the subject of the account being changed, which never appears in audit `changes`, events, errors, logs or responses.

**Seeded data** (migration 0009, deterministic reference data, no personal data, no outbox event, actor `system:migration`, correlation `seed-0009`): the two roles `CUSTOMER` and `PROVIDER` (both `ACTIVE`, name keys `identity.role.customer.name` and `identity.role.provider.name`) and 17 content entries taken through the real content lifecycle (the two role names; five account status labels `account.status.pending`, `active`, `suspended`, `closure_requested`, `closed`; four session labels `session.account.id`, `status`, `roles`, `active_role` and the message `session.account.unavailable`; five messages `account.error.name_required`, `name_too_long`, `name_invalid_characters`, `suspended`, `closed`). NO account, membership, external identity, profile or history row is seeded: an account appears on the first authenticated request of a person.

### `identity.*` email contact and verification (ID-002): email contacts and verification challenges

Migration `0010_email_verification.sql`. The email address BananaGig holds for a person and the proof that the person controls it. Keycloak remains the authentication authority and keeps the login email; BananaGig owns the marketplace contact and its verification state. ID-002 stores and exposes the state and gates nothing: the booking gate (CU-03/CU-04), chat, reviews, two-factor codes (CU-09.13) and account recovery consume it later. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/EMAIL_VERIFICATION.md`, review in `NORMALIZATION_LOG.md`. Decisions: ADR-0027 (the contact is owned by BananaGig, verified only by proof, uniqueness and replacement) and ADR-0028 (one challenge per send, keyed hashes, single use under a row lock, two-phase delivery). Requirements served: CU-03.04 to CU-03.06 (verify by code or link, resend, change address), SV-03.01 (code rules from configuration, single use, hashes only), SV-03.02 (one verified email per account), SV-03.04 (abuse protection), SV-03.05 (private, masked), CU-09.15 (a change is verified before it replaces the old address, which stays active until then).

| Table | Role |
|---|---|
| `identity.email_contacts` | The email addresses of an account, one row per address and account: `email_normalized` (the canonical form, the ONLY stored form: comparison key, uniqueness key and delivery address), `status` (`PENDING`, `VERIFIED`, `REPLACEMENT_PENDING`, `DISABLED`), `is_primary`, `source` (`USER_ENTERED`, `IDP_VERIFIED`), `verified_at`, `disabled_at`, `disabled_reason` (`REPLACED`, `SUPERSEDED`) and timestamps. PERSONAL DATA. Never deleted: a replaced or superseded address becomes `DISABLED` and stays as history |
| `identity.email_verification_challenges` | One verification intent per SEND. A resend creates a NEW challenge (new code, new magic token) and supersedes the open one in the same transaction, so the number of sends in a window is the number of rows. Holds only HMAC-SHA-256 hashes of the code and of the magic token, the expiry, the single-use marker (`used_at`, `consumed_via` `CODE` or `LINK`), the wrong-attempt counter, the invalidation (`invalidated_at`, `invalidation_reason` `SUPERSEDED`, `LOCKED`, `CONTACT_DISABLED` or `DELIVERY_FAILED`), the delivery outcome (`delivery_status`, `last_sent_at`) and the correlation id of the issuing request. Never deleted |
| `identity.account_audit_events` (changed) | Seven new `EMAIL_*` actions and the nullable `email_contact_id` (see Audit and events below) |

**Ownership: BananaGig owns the contact, and nothing is VERIFIED except by proof.** The login email stays in Keycloak, is not copied, and access tokens carry no email claim; a plain email claim is never persisted. An address becomes `VERIFIED` in exactly two ways: the person proves the mailbox with the code or the magic link (source `USER_ENTERED`), or a TRUSTED identity provider reported the address verified (source `IDP_VERIFIED`, born `VERIFIED`; decided by the pure function `decideIdpEmail`, which no HTTP path calls in ID-002). Verification state is NOT stored on `identity.accounts` (it would duplicate lifecycle state and could not represent a pending replacement next to the verified address); the account-level `emailVerificationStatus` is derived from the contact rows: `NONE` (no live contact), `PENDING` (a live contact and none verified), `VERIFIED` (a verified primary exists, even while a replacement is pending). No plaintext verification code, no plaintext magic token and no credential is stored anywhere in the database.

**One stored form of the address.** `email_normalized` is produced by ONE function (`canonicalizeEmail`, contracts): trimmed, domain IDNA-mapped to lower-case ASCII, local part a lower-cased ASCII dot-atom, dots and `+tags` kept (no Gmail-style folding), at most 254 characters. `ck_email_contacts__email_normalized` repeats the shape in the database as a safety net (length at most 254; a local part of 1 to 64 characters from the dot-atom alphabet, `@`, a domain of 3 to 253 characters from `[a-z0-9.-]`, so upper case, whitespace, control characters and non-ASCII characters cannot be stored); the function is the validator. The original typing is not kept (no `email_display` column, no second copy of the personal data). The address is PERSONAL DATA: never in a log line, an audit `changes` object, an event, an error or an API response; the owner receives it only MASKED (`c***@b***.localhost`).

**Contact status machine** (trigger `identity.guard_email_contacts`, `BEFORE INSERT OR UPDATE OR DELETE`; DELETE is always refused, `NOT_DELETABLE`). Inserting locks the account row first (`FOR UPDATE`) and refuses a `CLOSED` account (`ACCOUNT_CLOSED`).

| From | To | Rule |
|---|---|---|
| insert | `PENDING` | the account has no primary (`EMAIL_INITIAL_WITH_PRIMARY` otherwise): the first address, challenge purpose `INITIAL_EMAIL` |
| insert | `REPLACEMENT_PENDING` | the account has a primary (`EMAIL_REPLACEMENT_WITHOUT_PRIMARY` otherwise): a new address that replaces the primary once it verifies, challenge purpose `CHANGE_EMAIL` |
| insert | `VERIFIED` | only with source `IDP_VERIFIED` (`EMAIL_STATUS_TRANSITION`), only when the account has no primary (`EMAIL_INITIAL_WITH_PRIMARY`) and only created primary (`EMAIL_PRIMARY_CHANGE`); a `USER_ENTERED` address is never born verified |
| insert | `DISABLED` | refused (`EMAIL_STATUS_TRANSITION`) |
| `PENDING` | `VERIFIED` | the code or the link; `is_primary` must be set in the same UPDATE (`EMAIL_PRIMARY_CHANGE`: a verified address is the primary address of its account) and the account must not be `CLOSED` (`ACCOUNT_CLOSED`, account row share-locked) |
| `REPLACEMENT_PENDING` | `VERIFIED` | the code or the link, with the same two rules; in the same transaction the old primary becomes `DISABLED` with reason `REPLACED` (first, because only one row can be primary) |
| `PENDING`, `REPLACEMENT_PENDING` | `DISABLED` | the reason must be `SUPERSEDED` (replaced by a newer pending address, or the change was withdrawn) |
| `VERIFIED` | `DISABLED` | the reason must be `REPLACED`, and after the account row is locked a `REPLACEMENT_PENDING` row of the account must exist (`EMAIL_PRIMARY_NOT_REPLACEABLE`): a verified primary can only be replaced by a verified replacement |
| `DISABLED` | anything | refused: a disabled contact never changes again, not even `updated_at` or its reason (`IMMUTABLE_IDENTITY`); `DISABLED` is terminal |

`email_contact_id`, `account_id`, `email_normalized`, `source` and `created_at` are immutable (`IMMUTABLE_IDENTITY`), `verified_at` is set exactly once, with the transition to `VERIFIED`, and kept when the address is later replaced (`IMMUTABLE_IDENTITY`), and once a contact is `DISABLED` the whole row is frozen (`IMMUTABLE_IDENTITY`). CHECK constraints bind the columns to the status: `ck_email_contacts__verified_at` (a `VERIFIED` row has `verified_at`; a `PENDING` or `REPLACEMENT_PENDING` row has none; a `DISABLED` row keeps the value of its verified period or has none when it was superseded before it verified), `ck_email_contacts__idp_born_verified` (an `IDP_VERIFIED` row always has `verified_at`, so it can only be born verified), `ck_email_contacts__disabled` (`DISABLED` exactly when `disabled_at` and `disabled_reason` are both set) and `ck_email_contacts__disabled_reason` (`REPLACED`, `SUPERSEDED`). The primary flag: `ck_email_contacts__primary_is_verified` (only a `VERIFIED` row can be primary), the partial unique index `uq_email_contacts__primary_per_account` (at most one per account) and the UPDATE guard (`is_primary` flips to true only together with the transition into `VERIFIED` and to false only together with `DISABLED`, and a transition into `VERIFIED` must set `is_primary`, `EMAIL_PRIMARY_CHANGE`), so the primary is replaced atomically. The converse is enforced too: a row created `VERIFIED` (only from a trusted identity provider) must be created primary, and a row verified by an UPDATE must set `is_primary` in that UPDATE (`EMAIL_PRIMARY_CHANGE` both times; the guard's reason is that a second verified address per account has no use case yet). So `is_primary` and `status = 'VERIFIED'` coincide on every row, and an account has at most one `VERIFIED` row; the column is a stored function of the status, kept as the explicit name of the primary (recorded under Intentional denormalization).

**Uniqueness policy** (ADR-0027; behavior in `docs/engineering/EMAIL_VERIFICATION.md`).

| Case | Behaviour | Enforced by |
|---|---|---|
| Verified duplication | one `VERIFIED` address belongs to at most ONE account; no takeover and no transfer | partial unique index `uq_email_contacts__verified_address (email_normalized) WHERE status = 'VERIFIED'` |
| Pending duplication | ALLOWED across accounts: a pending claim proves nothing, so it neither blocks the real owner nor reveals that anyone else holds the address | deliberately no index on the address for pending rows |
| Same account | at most one primary (and, because a verified row is always the primary, at most one `VERIFIED` row), at most one open candidate (`PENDING` or `REPLACEMENT_PENDING`), one live row per address | `uq_email_contacts__primary_per_account`, `uq_email_contacts__open_per_account`, `uq_email_contacts__live_address_per_account` and the primary rules of the guard |
| Proving a mailbox another account already verified | `409 ACCOUNT_EMAIL_UNAVAILABLE` after a correct code or link; nothing changes; recovery of a lost mailbox is a support process (DEBT-0051) | a service pre-check at confirmation and, underneath, the unique index (two accounts verifying the same address concurrently have one winner) |
| Replacement | the candidate is `REPLACEMENT_PENDING`; the primary stays `VERIFIED` and primary until the candidate verifies; verification disables the old primary (`REPLACED`) and promotes the candidate atomically; a superseded or withdrawn candidate leaves the primary untouched | guard triggers and the deferred invariant trigger |

No answer before proof reveals whether an address is held elsewhere: setting the address and sending the verification answer identically whatever any other account holds.

**Deferred whole-account invariants** (`trg_email_contacts__invariants`, function `identity.check_email_account_invariants`, a CONSTRAINT trigger `AFTER INSERT OR UPDATE` on `email_contacts`, `DEFERRABLE INITIALLY DEFERRED`, `EMAIL_INVARIANT`). Checked once at COMMIT against the rows as they are then, so the multi-step replacement (disable the old primary, promote the candidate, consume the challenge) may pass through intermediate states inside its transaction. At commit: a pending INITIAL address (`PENDING`) and a primary never coexist; a `REPLACEMENT_PENDING` address needs a primary; an account that ever replaced a primary (a `DISABLED` row with reason `REPLACED`) still has one; a contact that is no longer open (not `PENDING` and not `REPLACEMENT_PENDING`) has no open challenge left. A second deferred trigger, `trg_email_verification_challenges__consumption` (function `identity.check_challenge_consumption`, `AFTER UPDATE` on `email_verification_challenges`, `DEFERRABLE INITIALLY DEFERRED`, `CHALLENGE_CONSUMPTION`), requires at commit that a challenge with `used_at` set belongs to a `VERIFIED` contact, so a challenge is consumed only together with the verification of its address, in the same transaction.

**Challenge: one row per send, hashes only.** `identity.email_verification_challenges` is the verification intent of ONE email. Resending issues a NEW challenge and supersedes the open one (`invalidation_reason` `SUPERSEDED`) in the same transaction, which is why the partial unique index `uq_email_verification_challenges__open_per_contact` can state that a contact has at most one open (usable) challenge, why the send history is kept, and why no send counter exists: the cooldown is the age of the newest challenge that is neither `FAILED` nor used (counted from its creation, so a delivery in flight holds a second send back), and the per-hour and per-day caps are counts of the account's challenge rows since a moment (failed deliveries count, so failing sends are bounded too). `code_hash` and `magic_token_hash` are HMAC-SHA-256 hex (`^[0-9a-f]{64}$`) of the numeric code (bound to the challenge id) and of the 256-bit magic-link token, keyed with `VERIFICATION_HASH_SECRET`, a deployment secret that is NOT in the database, so a database leak cannot verify an address and a 6-digit code cannot be brute-forced offline; `magic_token_hash` is unique (the lookup key of a link confirmation). The plaintext exists only in memory while the message is built and in the delivered message. Challenge state is derived, not flagged: a challenge is OPEN while `used_at` and `invalidated_at` are both NULL, EXPIRED when `expires_at` has passed (evaluated on the row loaded by key; no sweeper), CONSUMED when `used_at` is set (with `consumed_via`), CLOSED otherwise by `invalidation_reason`. `ck_email_verification_challenges__consumed` and `__invalidated` pair each timestamp with its how or why, `__closed_once` forbids both closures, `__expiry` requires `expires_at > created_at`, `__attempts` forbids a negative counter and `__delivery` ties `delivery_status` (`PENDING`, `SENT`, `FAILED`) to `last_sent_at`.

**Challenge guard** (trigger `identity.guard_email_verification_challenges`, `BEFORE INSERT OR UPDATE OR DELETE`; DELETE refused, `NOT_DELETABLE`). INSERT share-locks the account row of the contact and refuses a `CLOSED` account (`ACCOUNT_CLOSED`), then locks the contact row (`FOR UPDATE`), requires it to be `PENDING` or `REPLACEMENT_PENDING` (`CHALLENGE_NOT_OPEN`), requires the purpose to match (`PENDING` gives `INITIAL_EMAIL`, `REPLACEMENT_PENDING` gives `CHANGE_EMAIL`, `CHALLENGE_PURPOSE`) and requires a fresh start: `attempt_count` 0, not used, not invalidated, `delivery_status` `PENDING` (`CHALLENGE_STATE`). UPDATE: `challenge_id`, `email_contact_id`, `purpose`, both hashes, `expires_at`, `created_at` and `correlation_id` are immutable (`IMMUTABLE_IDENTITY`); only the attempt, use, invalidation and delivery fields change; a used or invalidated challenge never changes again (`CHALLENGE_CLOSED`); `attempt_count` only counts up, one attempt at a time (`CHALLENGE_ATTEMPTS`); and the delivery outcome is recorded once (`CHALLENGE_DELIVERY`: after `delivery_status` leaves `PENDING`, neither it nor `last_sent_at` changes). The configured maximum of wrong attempts (`verification.email.max_attempts`) is NOT in the schema: the service locks the challenge (`LOCKED`) in the same UPDATE that counts the attempt that reaches it.

**Indexes and their justification** (guardrail 11; the justification is also in the migration header). Deliberately NOT added: an index on `email_contacts.email_normalized` for pending duplicates (nothing filters pending rows by address) and a separate index on `email_contacts.account_id` for history (the leading column of `uq_email_contacts__account_contact` already serves every read by account, see the table below; an index follows a real query path through its own review), an index on `expires_at` (expiry is evaluated on the row loaded by key; there is no sweeper, and a retention job would add a partial index through its own review) and an index on `account_audit_events.email_contact_id` (the per-contact timeline reads the per-account index with the contact as a filter; an account has a handful of contacts).

| Index | Definition | Serves |
|---|---|---|
| `uq_email_contacts__verified_address` | UNIQUE `(email_normalized) WHERE status = 'VERIFIED'` | the rule "a verified address belongs to one account" and the lookup "is this address verified on any account" at the moment of verification |
| `uq_email_contacts__primary_per_account` | UNIQUE `(account_id) WHERE is_primary` | the rule "at most one primary" and the lookup of the account's primary address (read by `GET /account/me`) |
| `uq_email_contacts__open_per_account` | UNIQUE `(account_id) WHERE status IN ('PENDING', 'REPLACEMENT_PENDING')` | the rule "at most one open candidate" and the lookup of the pending candidate (read by `/account/me` and every verification call) |
| `uq_email_contacts__live_address_per_account` | UNIQUE `(account_id, email_normalized) WHERE status <> 'DISABLED'` | the rule only (an account cannot hold the same live address twice, for example verified and pending at once); the live rows of an account are a handful |

| `idx_email_verification_challenges__contact_created` | `(email_contact_id, created_at DESC)` | the send history of ONE contact, newest first: the resend cooldown (newest non-`FAILED`, unused row), the per-hour and per-day caps (rows since a moment) and the verification timeline; it also covers the foreign key. Plus `pk_email_contacts` and `pk_email_verification_challenges`. Foreign keys (all `ON DELETE RESTRICT`; rows are never deleted): `email_contacts.account_id` is covered by the prefix of `uq_email_contacts__account_contact`, `email_verification_challenges.email_contact_id` by `idx_email_verification_challenges__contact_created`, and the composite `account_audit_events (account_id, email_contact_id)` by the per-account audit index for its `account_id` prefix; the referenced side is the unique constraint `uq_email_contacts__account_contact`. No foreign key of the email model lacks a lookup path, and `account_audit_events.email_contact_id` has no index of its own (see above).

**Lock order and concurrency.** One order everywhere, extending ID-001: the ACCOUNT row first (`FOR UPDATE`), then the account's contact rows (`FOR UPDATE`, in `created_at` order), then the challenge row (`FOR UPDATE`). The guards follow it: a contact INSERT locks the account row before it reads the siblings (concurrent first-address inserts and the primary check serialize on it), disabling a `VERIFIED` contact locks the account row before it looks for the `REPLACEMENT_PENDING` sibling, the transition of a contact into `VERIFIED` share-locks the account row to refuse a `CLOSED` account, and a challenge INSERT share-locks the account row and then locks the contact row before it reads its status (account before contact before challenge, the same order). Every confirmation (code or link) takes that order, so a code and a link racing, two clients submitting the same code, a resend racing a verification, a replacement race and an expiry all run one after the other and end in exactly one outcome; the loser finds the address verified and gets an idempotent success (`changed: false`) with no second audit row or event. Wrong codes are counted under the challenge row lock and the counter is committed even though the call then fails. Two accounts verifying the same address at once are decided by `uq_email_contacts__verified_address`, not by application code. As in ID-001, one inversion is inherent: a raw SQL UPDATE locks the contact row before its trigger can lock the account row, so racing a service call that holds the account row it can deadlock; PostgreSQL aborts one side (`40P01`) and the service reports a retryable `CONFLICT`. The email itself is delivered OUTSIDE any transaction (two-phase delivery, ADR-0028): the challenge commits, the message is sent, then the outcome is recorded (`SENT` with `last_sent_at`, or `FAILED` together with the closure `DELIVERY_FAILED`); no lock is held across the network call. A crash between delivery and recording leaves a `PENDING` delivery whose code is still valid.

**Guard keys.** ID-002 adds 13 keys to the `identity_rule:<KEY>` vocabulary (26 in total; same SQLSTATE `23000`, classified by key, never by message text): `EMAIL_STATUS_TRANSITION`, `EMAIL_PRIMARY_CHANGE`, `EMAIL_PRIMARY_NOT_REPLACEABLE`, `EMAIL_INITIAL_WITH_PRIMARY`, `EMAIL_REPLACEMENT_WITHOUT_PRIMARY`, `EMAIL_INVARIANT`, `CHALLENGE_CLOSED`, `CHALLENGE_ATTEMPTS`, `CHALLENGE_DELIVERY`, `CHALLENGE_NOT_OPEN`, `CHALLENGE_PURPOSE`, `CHALLENGE_STATE`, `CHALLENGE_CONSUMPTION`. The existing keys `NOT_DELETABLE`, `IMMUTABLE_IDENTITY` and `ACCOUNT_CLOSED` are reused.

**`identity.account_audit_events` change (expand step).** The table gains the nullable column `email_contact_id` and the COMPOSITE foreign key `fk_account_audit_events__account_email_contact (account_id, email_contact_id)` to `email_contacts (account_id, email_contact_id)` (target `uq_email_contacts__account_contact`, restrict, MATCH SIMPLE so it is not checked when `email_contact_id` is NULL), which guarantees that an audit row can only name a contact of the audited account; and `ck_account_audit_events__action` is dropped and re-created WIDER in the same transaction with seven actions: `EMAIL_ADDED`, `EMAIL_CHANGE_REQUESTED`, `EMAIL_VERIFICATION_REQUESTED`, `EMAIL_VERIFICATION_FAILED`, `EMAIL_VERIFICATION_LOCKED`, `EMAIL_VERIFIED`, `EMAIL_PRIMARY_CHANGED`. The new `ck_account_audit_events__email_contact` requires `(action LIKE 'EMAIL\_%') = (email_contact_id IS NOT NULL)`: the contact is named exactly for the email actions. A pure widening: every existing row satisfies both CHECKs and the foreign key (none is an `EMAIL_*` action and `email_contact_id` is NULL), no row is rewritten and the append-only trigger is not involved. The audit trail names the contact by id and, in `changes`, by the MASKED address; it never holds a full address, a code, a token or a hash.

**Audit and events.** Every contact or verification change writes its audit row or rows and its outbox event or events in the same transaction (the verification that replaces a primary writes `EMAIL_VERIFIED` and `EMAIL_PRIMARY_CHANGED`; every wrong code writes `EMAIL_VERIFICATION_FAILED` with the attempt number, and the attempt that locks the challenge also writes `EMAIL_VERIFICATION_LOCKED`). Five outbox events (aggregate type `identity_account`, identifiers only, never an address, code, token or hash) reuse `integration.outbox_events`: `bananagig.identity.email-contact-added.v1`, `email-verification-sent.v1`, `email-verified.v1`, `email-verification-failed.v1`, `email-change-requested.v1`. The migration seeds emit no event.

**Seeded configuration** (migration 0010, through the real change workflow of CFG-001: parameter created, change drafted, submitted, approved by `system:migration-review`, published and activated, so 6 `configuration.audit_events` rows per parameter and 48 in total; actor `system:migration`, correlation `seed-0010`). Eight `INTEGER` parameters, owner `security`, sensitivity `INTERNAL`, approval `SECOND_APPROVER`, criticality `CRITICAL` (never served from a cache or last-known-good), required, `PLATFORM` scope only (no override level). The service reads them fresh on every call, never defaults them in code, and fails closed when they cannot be read.

Content types: 1 `EMAIL_SUBJECT` and 1 `EMAIL_BODY` (`account.email.verification.subject` and `.body`), 10 `UI_LABEL` and 22 `PLAIN_TEXT`. The address is personal data that has no erasure or anonymization procedure yet: retention is DEBT-0045. Rotating `VERIFICATION_HASH_SECRET` invalidates open challenges (they expire in minutes); no data migration is needed.

### `identity.*` phone contact and verification (ID-003): phone contacts and verification challenges

Migration `0011_phone_verification.sql`. The mobile phone number BananaGig holds for a person and the proof, by an SMS code, that the person controls it. Keycloak remains the authentication authority and is NOT a phone store: the number is never written to Keycloak, a token, an event or a log. ID-003 stores and exposes the state (masked, to the owner only) and gates nothing. It mirrors the ID-002 email model on purpose and differs where the channel differs: the canonical form (E.164 plus the country), the line-type snapshot, the SMS delivery, no magic link and a CONFIGURABLE number of accounts per verified number. Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/PHONE_VERIFICATION.md`, review in `NORMALIZATION_LOG.md`. Decisions: ADR-0030 (shared verification primitives are code, not schema), ADR-0031 (E.164 with its country; accounts per number is configuration), ADR-0032 (SMS delivery and phone-intelligence ports) and ADR-0033 (exact trusted-proxy hops). Requirements served: CU-03.04 to CU-03.06, SV-03.01 (code rules from configuration, single use, hashes only), SV-03.02 (accounts per number, blocked line types), SV-03.04 (abuse protection).

| Table | Role |
|---|---|
| `identity.phone_contacts` | The phone numbers of an account, one row per number and account: `phone_e164` (the canonical form, the ONLY stored number: comparison, uniqueness and delivery form), `country_code` (ISO alpha-2, foreign key to `geography.countries`), `status` (`PENDING`, `VERIFIED`, `REPLACEMENT_PENDING`, `DISABLED`), `is_primary`, `source` (`USER_ENTERED` only), `line_type` and `line_type_checked_at` (a snapshot of the phone-intelligence result, both NULL when no lookup was needed), `verified_at`, `disabled_at`, `disabled_reason` (`REPLACED`, `SUPERSEDED`) and timestamps. PERSONAL DATA (`phone_e164`). Never deleted |
| `identity.phone_verification_challenges` | One verification intent per SMS SEND (the ID-002 challenge without the magic link). A resend creates a NEW challenge and supersedes the open one in the same transaction, so the number of sends in a window is the number of rows. Holds only the HMAC-SHA-256 `code_hash`, the expiry, the single-use marker (`used_at`), the wrong-attempt counter, the invalidation (`invalidated_at`, `invalidation_reason` `SUPERSEDED`, `LOCKED`, `CONTACT_DISABLED` or `DELIVERY_FAILED`), the delivery outcome (`delivery_status`, `last_sent_at`) and the correlation id. No `consumed_via` (the code is the only method) and no `updated_at`. Never deleted |
| `identity.account_audit_events` (changed) | Seven new `PHONE_*` actions and the nullable `phone_contact_id` (see below) |

**Ownership and what is not stored.** A number becomes `VERIFIED` only by proof (the SMS code); `source` has the single value `USER_ENTERED` (there is no trusted-provider shortcut for phones, so the column exists only so a source can be added by widening the CHECK). A guard refuses any insert except `PENDING` or `REPLACEMENT_PENDING`: a number is never born verified. Verification state is NOT stored on `identity.accounts` and there is no `contacts_verified` column: the account-level `phoneVerificationStatus` (`NONE`, `PENDING`, `VERIFIED`) and the `contacts` summary of `GET /account/me` (`emailVerified`, `phoneVerified`, `contactsVerified`) are derived from the contact rows at read time. No plaintext code and no credential is stored anywhere in the database.

**One stored form of the number.** `phone_e164` is produced by ONE function (`canonicalizePhone` over libphonenumber-js; see ADR-0031): a plus sign, a non-zero first digit and 7 to 15 digits (`ck_phone_contacts__phone_e164`, `^\+[1-9][0-9]{6,14}$`). No national-number, display or as-typed copy is stored: formatting is derived on read from the canonical value and the country, and the masked form (`+*******0142`, the only form that leaves the server, to the owner only) is derived too. `country_code` is the country the numbering library resolved FROM THE NUMBER (a shared calling code such as +1 is resolved to US or CA); it is a foreign key to `geography.countries (iso_alpha2)` plus a shape CHECK, and the service accepts only ACTIVE countries whose `dialing_code` equals the number's calling code. `phone_e164` is PERSONAL DATA: never in a log line, an audit `changes` object, an event, an error or an API response.

**Contact status machine** (trigger `identity.guard_phone_contacts`, `BEFORE INSERT OR UPDATE OR DELETE`; DELETE is always refused, `NOT_DELETABLE`). The lifecycle is the email lifecycle without the identity-provider paths. Inserting locks the account row first (`FOR UPDATE`) and refuses a `CLOSED` account (`ACCOUNT_CLOSED`).

| From | To | Rule |
|---|---|---|
| insert | `PENDING` | the account has no primary (`PHONE_INITIAL_WITH_PRIMARY` otherwise): the first number, challenge purpose `INITIAL_PHONE` |
| insert | `REPLACEMENT_PENDING` | the account has a primary (`PHONE_REPLACEMENT_WITHOUT_PRIMARY` otherwise): a new number that replaces the primary once it verifies, challenge purpose `CHANGE_PHONE` |
| insert | `VERIFIED`, `DISABLED` | refused (`PHONE_STATUS_TRANSITION`) |
| `PENDING`, `REPLACEMENT_PENDING` | `VERIFIED` | the code; `is_primary` must be set in the same UPDATE (`PHONE_PRIMARY_CHANGE`); the account must not be `CLOSED` (`ACCOUNT_CLOSED`, account row share-locked); and the number cap below (`PHONE_NUMBER_CAP`). For a replacement the old primary becomes `DISABLED` (`REPLACED`) in the same transaction, first, because only one row can be primary |
| `PENDING`, `REPLACEMENT_PENDING` | `DISABLED` | the reason must be `SUPERSEDED` (`PHONE_STATUS_TRANSITION`) |
| `VERIFIED` | `DISABLED` | the reason must be `REPLACED` (`PHONE_STATUS_TRANSITION`), and after the account row is locked a `REPLACEMENT_PENDING` row of the account must exist (`PHONE_PRIMARY_NOT_REPLACEABLE`) |
| `DISABLED` | anything | refused: a disabled contact never changes again (`IMMUTABLE_IDENTITY`); any other pair is `PHONE_STATUS_TRANSITION` |

`phone_contact_id`, `account_id`, `phone_e164`, `country_code`, `source`, `line_type`, `line_type_checked_at` and `created_at` are immutable (`IMMUTABLE_IDENTITY`; the line-type snapshot is never refreshed in place), `verified_at` is set exactly once. CHECK constraints bind the columns to the status: `ck_phone_contacts__verified_at` (`VERIFIED` has `verified_at`, `PENDING` and `REPLACEMENT_PENDING` have none), `ck_phone_contacts__disabled` (`DISABLED` exactly when both `disabled_at` and `disabled_reason` are set), `ck_phone_contacts__disabled_reason` (`REPLACED`, `SUPERSEDED`), `ck_phone_contacts__primary_is_verified` (a primary is `VERIFIED`), `ck_phone_contacts__line_type_pair` (`line_type` and `line_type_checked_at` are NULL together) and `ck_phone_contacts__line_type` (`MOBILE`, `LANDLINE`, `VOIP`, `VIRTUAL`, `UNKNOWN`, `HIGH_RISK`). As for email, `is_primary` and `status = 'VERIFIED'` coincide on every row (the CHECK one way, the guard the other way, `PHONE_PRIMARY_CHANGE`).

**Uniqueness policy and accounts per number** (ADR-0031; behavior in `docs/engineering/PHONE_VERIFICATION.md`). Unlike email, a verified number is NOT unique across accounts at the database level, on purpose.

| Case | Behaviour | Enforced by |
|---|---|---|
| Verified duplication | at most `verification.phone.max_accounts_per_number` accounts (PLATFORM default 1, overridable per COUNTRY and MARKET, structural ceiling 5) may hold one number `VERIFIED`; no takeover, no displacement | the service (transaction advisory lock on the number, then a count of the OTHER accounts) AND the guard trigger (the same lock, the same count, the value the service passes in the transaction setting `app.phone_max_accounts`): `PHONE_NUMBER_CAP`. No unique index: the permitted number is configuration data, so it cannot be a constraint of the schema |
| Pending duplication | ALLOWED across accounts: a pending claim proves nothing, so it neither blocks the real owner nor reveals that anyone else holds the number | deliberately no index on the number for pending rows |
| Same account | at most one primary, at most one open candidate (`PENDING` or `REPLACEMENT_PENDING`), one live row per number | `uq_phone_contacts__primary_per_account`, `uq_phone_contacts__open_per_account`, `uq_phone_contacts__live_number_per_account` and the primary rules of the guard |
| Proving a number held elsewhere beyond the cap | `409 ACCOUNT_PHONE_UNAVAILABLE` AFTER a correct code; nothing changes; recovery is a support process (DEBT-0061) | the service pre-check and, underneath, the guard |
| Replacement | as for email: the candidate is `REPLACEMENT_PENDING`, the primary stays `VERIFIED` and primary until the candidate verifies | guard triggers and the deferred invariant trigger |

**The `PHONE_NUMBER_CAP` rule** (inside `identity.guard_phone_contacts`, on the transition into `VERIFIED` only). After the account row is share-locked (a `CLOSED` account verifies nothing, `ACCOUNT_CLOSED`) the guard takes `pg_advisory_xact_lock(hashtextextended('phone:' || phone_e164, 0))`, which serializes the verifications of ONE number across accounts. It reads the transaction setting `app.phone_max_accounts` with `current_setting(..., true)`; a value matching `^[1-5]$` is the cap, anything else (unset, empty, out of range, written by another client) falls back to the structural ceiling of 5. It then counts `count(DISTINCT account_id)` of the OTHER accounts (`account_id <> OLD.account_id`) that hold the same `phone_e164` with `status = 'VERIFIED'` AND whose account `status <> 'CLOSED'`: a closed account no longer holds its number (a recycled number), so a `VERIFIED` row of a `CLOSED` account (rows are never deleted) does not count. If that count is greater than or equal to the cap the transition fails with `identity_rule:PHONE_NUMBER_CAP`. The configured value lives in configuration (`verification.phone.max_accounts_per_number`) and is resolved by the service for the number's country; the schema holds only the ceiling. The count is served by `idx_phone_contacts__verified_number`.

**Deferred whole-account invariants** (`trg_phone_contacts__invariants`, function `identity.check_phone_account_invariants`, a CONSTRAINT trigger `AFTER INSERT OR UPDATE` on `phone_contacts`, `DEFERRABLE INITIALLY DEFERRED`, `PHONE_INVARIANT`). Checked once at COMMIT, so the multi-step replacement may pass through intermediate states inside its transaction. At commit: a pending INITIAL number (`PENDING`) and a primary never coexist; a `REPLACEMENT_PENDING` number needs a primary; an account that ever replaced a primary (a `DISABLED` row with reason `REPLACED`) still has one; a contact that is no longer open has no open challenge left. A second deferred trigger, `trg_phone_verification_challenges__consumption` (function `identity.check_phone_challenge_consumption`, `AFTER UPDATE` on `phone_verification_challenges`, `PHONE_CHALLENGE_CONSUMPTION`), requires at commit that a challenge with `used_at` set belongs to a `VERIFIED` contact.

**Challenge: one row per send, a hash only.** `identity.phone_verification_challenges` is the verification intent of ONE SMS. Resending issues a NEW challenge and supersedes the open one (`SUPERSEDED`) in the same transaction, which is why `uq_phone_verification_challenges__open_per_contact` can state that a contact has at most one open challenge and why no send counter exists: the resend cooldown is the age of the newest challenge that is neither `FAILED` nor used (counted from its creation), and the per-hour and per-day caps are counts of the account's challenge rows since a moment (failed deliveries count). `code_hash` is the HMAC-SHA-256 hex (`^[0-9a-f]{64}$`) of the numeric code, bound to the challenge id, in its own domain (`bananagig:phone-code:v1`, so an email hash can never verify a phone code), keyed with `VERIFICATION_HASH_SECRET`, a deployment secret that is NOT in the database; the code is never stored. State is derived (OPEN while `used_at` and `invalidated_at` are NULL, EXPIRED when `expires_at` has passed, CONSUMED, CLOSED by reason); there is no sweeper and no status column. `purpose` (`INITIAL_PHONE`, `CHANGE_PHONE`) is a frozen snapshot of the contact status at issuance.

**Challenge guard** (trigger `identity.guard_phone_verification_challenges`, `BEFORE INSERT OR UPDATE OR DELETE`; DELETE refused, `NOT_DELETABLE`). INSERT share-locks the account row of the contact and refuses a `CLOSED` account (`ACCOUNT_CLOSED`), then locks the contact row (`FOR UPDATE`), requires it to be `PENDING` or `REPLACEMENT_PENDING` (`PHONE_CHALLENGE_NOT_OPEN`), requires the purpose to match (`PHONE_CHALLENGE_PURPOSE`) and a fresh start: `attempt_count` 0, not used, not invalidated, delivery `PENDING` (`PHONE_CHALLENGE_STATE`). UPDATE: `challenge_id`, `phone_contact_id`, `purpose`, `code_hash`, `expires_at`, `created_at` and `correlation_id` are immutable (`IMMUTABLE_IDENTITY`); a used or invalidated challenge never changes again (`PHONE_CHALLENGE_CLOSED`); `attempt_count` only counts up, one attempt at a time (`PHONE_CHALLENGE_ATTEMPTS`); the delivery outcome is recorded once (`PHONE_CHALLENGE_DELIVERY`). The configured maximum of wrong attempts (`verification.phone.max_attempts`) is NOT in the schema.

**Indexes and their hot queries** (guardrail 11; the justification is also in the migration). Deliberately NOT added: an index on `phone_contacts.country_code` (countries are never deleted and no query filters contacts by country), an index on `phone_e164` for pending duplicates, a separate `account_id` index (the prefix of `uq_phone_contacts__account_contact` serves it), an index on `expires_at` (no sweeper) and one on `account_audit_events.phone_contact_id` (the per-account index serves the timeline).

**Lock order and concurrency.** The ID-002 order: the ACCOUNT row first, then the account's contact rows, then the challenge row; the number-cap advisory lock is taken by the guard inside the verifying UPDATE, after the account share lock. A contact INSERT locks the account row before it reads the siblings; disabling a `VERIFIED` contact locks the account row before it looks for the `REPLACEMENT_PENDING` sibling; a challenge INSERT share-locks the account row and then locks the contact row. Two accounts verifying the same number at once serialize on the number's advisory lock, so under a cap of 1 exactly one wins (the loser gets `PHONE_NUMBER_CAP`, reported as `409 ACCOUNT_PHONE_UNAVAILABLE`). The SMS is delivered OUTSIDE any transaction (two-phase delivery as for email, ADR-0028; the port is ADR-0032): the challenge commits, the message is sent, then the outcome is recorded (`SENT` with `last_sent_at`, or `FAILED` together with `DELIVERY_FAILED`).

The existing keys `NOT_DELETABLE`, `IMMUTABLE_IDENTITY` and `ACCOUNT_CLOSED` are reused. ### `identity.*` sessions, devices and the revocation watermark (ID-004): application sessions, devices, MFA and recovery

Migration `0012_application_sessions.sql`. What BananaGig itself owns about the way a person is signed in: the registry of the identity-provider sessions the API has seen, the browsers of an account with the trusted-browser window, and the "sign out everywhere" watermark. Keycloak remains the authority for passwords, the TOTP credential, recovery codes (its own `recovery-authn-codes` credential) and the protocol sessions: NOTHING in this schema stores a credential, a token, a TOTP secret, a recovery code, a raw IP address or a raw user agent. The second-factor and password state is NOT stored (read from Keycloak; transitions are observed and audited, below). Normalized model; full column documentation in `DATA_DICTIONARY.md`, relationships in `ERD.md`, behavior in `docs/engineering/SESSIONS_AND_MFA.md`, review in `NORMALIZATION_LOG.md`. Decisions: ADR-0034 to ADR-0036. Requirements served: CU-09.12 (sessions end when the password changes), CU-09.13 (trusted browser, 30 days), CU-09.20 (security activity for the configured period), CU-03.11 (reset link validity), SV-01.12 (keep me signed in, 30 days).

| Table | Role |
|---|---|
| `identity.application_sessions` | The application session registry: ONE row per Keycloak session the API has seen on an authenticated web request, created on first sight. `keycloak_session_id` is the `sid` claim (a protocol reference, unique across accounts); `account_device_id` is the browser it came from (attached once after login, nullable); `created_at`, `last_seen_at` (touched at most once a minute); `revoked_at` and `revocation_reason` (`SIGN_OUT`, `REVOKED_BY_USER`, `SIGN_OUT_EVERYWHERE`, `KEYCLOAK_ENDED`, `DEVICE_REMOVED`, `PASSWORD_CHANGED`), set together and terminal. No status column and no `expires_at`: liveness is derived. `fillfactor = 80`. Never deleted |
| `identity.account_devices` | The browsers of an account: `device_hash` (hex HMAC-SHA-256 of a server-issued cookie secret, keyed outside the database and bound to the account), the three coarse closed families `browser_family`, `os_family` and `device_class`, `first_seen_at` and `last_seen_at`, the trusted-browser window `trusted_at` and `trusted_until` (set and cleared together) and `removed_at` (terminal). One row per (account, browser). Never deleted |
| `identity.accounts` (changed) | One new nullable column `sessions_not_before timestamptz`, the revocation watermark. NULL until the first "sign out everywhere" |
| `identity.account_audit_events` (changed) | Sixteen new security actions, the nullable `application_session_id` and `account_device_id` (see below) |

**Application session registry versus Keycloak session.** The registry exists for one reason: access tokens live minutes (300 s), so "sign out everywhere" and "revoke this session" take effect at once only if the API can refuse a token whose session was revoked. Every web-context request that goes through `requireAccount` resolves the token `sid` to its row in ONE statement (the lookup is `uq_application_sessions__keycloak_session`); a revoked row is refused with 401 `SESSION_REVOKED`; a `sid` that belongs to another account is treated as revoked and never leaked. The row is a reference plus BananaGig's own observations: it copies no Keycloak session attribute beyond the `sid` and the `last_seen_at`, which is the application's own observation (the last request the API saw), not Keycloak's. The `sid` is never logged, never returned by an API (clients receive the `application_session_id`), never put in an audit `changes` object or an event. The coarse device of a session is reached through the device row, not copied.

**Session state is derived, never stored.** `ACTIVE` = `revoked_at IS NULL`, inside the `session.keep_signed_in_days` window and, when the identity provider can be asked, still known to it; `ENDED` = revoked with `SIGN_OUT` or `KEYCLOAK_ENDED`; `REVOKED` = revoked with `REVOKED_BY_USER`, `SIGN_OUT_EVERYWHERE`, `DEVICE_REMOVED` or `PASSWORD_CHANGED`. Listing reconciles with Keycloak: a non-revoked row older than 15 s that Keycloak no longer lists is revoked `KEYCLOAK_ENDED` (audit `SESSION_ENDED`); if Keycloak cannot be asked the list is returned unreconciled (`reconciled: false`) and nothing is mutated. There is no sweeper and no `status` or `expires_at` column.

**Revocation: a per-row terminal state PLUS an account watermark.** Revoking a session sets `revoked_at` and `revocation_reason` together (`ck_application_sessions__revoked_pair`) and the row never changes again (`SESSION_REVOKED_TERMINAL`). "Sign out everywhere" additionally raises `identity.accounts.sessions_not_before` to the moment of the revoke-all. The watermark is needed for the sessions that have NO row yet (a Keycloak session that existed before the revoke-all but whose token the API had not yet seen): a login whose `auth_time` is older than the watermark is refused at first sight. A session that already has a row is governed by its own `revoked_at` only. The comparison tolerates 2 seconds of clock skew (`auth_time` has whole-second resolution): a first-seen session is refused only when `auth_time + 2 s < sessions_not_before`. First-sight creation takes the account row `FOR SHARE` and revoke-all takes it `FOR UPDATE`, so exactly one order happens: either the new row exists when revoke-all runs (and is revoked) or the first sight reads the raised watermark. Guard trigger `trg_accounts__sessions_not_before` (`identity.guard_accounts_sessions_not_before`, `BEFORE UPDATE OF sessions_not_before`, only when the value changes): the watermark never moves back and never to NULL, and never more than 1 minute into the future (`SESSIONS_WATERMARK`). A CLOSED account stays immutable (`guard_accounts` is unchanged), so the service skips the watermark for it.

**Trusted browser: an attribute of (account, device), 1:1.** `trusted_at`/`trusted_until` live ON `account_devices`: the trust is a fact about this account's relationship to this browser, one window per row (`ck_account_devices__trust_pair`: both or neither; `__trust_window`: `trusted_until > trusted_at`). Trusted = `trusted_until > clock_timestamp()` AND `removed_at IS NULL`, evaluated by the reader: an elapsed window needs no write and no sweeper. Trust is cleared by untrust and by removal (`ck_account_devices__removed_untrusted`). The window length is the configuration `session.trusted_browser_days`. Trusting a browser has NO effect on the identity provider's own prompt for a second factor (Keycloak cannot skip OTP for a device without a custom extension) and never bypasses a step-up guard; the managed copy says so plainly. History of trust and untrust is in the audit rows (`DEVICE_TRUSTED`, `DEVICE_UNTRUSTED`).

**Device identification and privacy.** The web server issues an HttpOnly cookie holding a random 32-byte base64url secret and registers it at login (`POST /account/security/sessions/current`). The API stores ONLY `device_hash = HMAC-SHA-256(VERIFICATION_HASH_SECRET, domain bananagig:device:v1, account id, secret)` as 64 lower-case hex characters (`ck_account_devices__device_hash`): a database leak yields no usable cookie, and because the account id is part of the input the same browser has a different, unlinkable hash on every account (`uq_account_devices__account_hash (account_id, device_hash)` is therefore per account). `device_hash` is a pseudonymous browser identifier: treated as personal data for retention (DEBT-0045), but it is not a credential (the cookie secret is, and it is never stored). The user agent is reduced to three closed families by an in-house classifier and discarded (`ck_account_devices__browser_family`, `__os_family`, `__device_class`; `OTHER` for anything else); no raw IP, no location and no GeoIP column exists. The families are the FIRST classification of the row and immutable. `last_seen_at` of a session is touched on the request path; the "last seen" of a device is DERIVED on read (GREATEST of its own `last_seen_at`, written when the browser registers a login, and the newest `last_seen_at` of its sessions), so the hot path never writes the device row.

**Guard keys.** ID-004 adds 8 keys to the `identity_rule:<KEY>` vocabulary (48 in total; same SQLSTATE `23000`, classified by key, never by message text): `SESSIONS_WATERMARK` (the watermark moves back, to NULL or into the future), `DEVICE_IMMUTABLE` (the device identity, hash, families or `first_seen_at` changed), `DEVICE_LAST_SEEN_MONOTONIC`, `DEVICE_REMOVED_TERMINAL` (a removed device cannot be trusted, restored, born removed or receive a session), `SESSION_IMMUTABLE` (id, account, `keycloak_session_id` or `created_at` changed), `SESSION_REVOKED_TERMINAL` (a revoked session never changes again), `SESSION_DEVICE_IMMUTABLE` (the device of a session is set once from NULL and never changed) and `SESSION_LAST_SEEN_MONOTONIC`. The existing keys `NOT_DELETABLE` (devices and sessions cannot be deleted) and `ACCOUNT_CLOSED` (a CLOSED account gets no device and no new session) are reused. Lock order: the ACCOUNT row first (`FOR UPDATE`), then the device row, then the session rows; the guards share-lock the account row they read (`FOR SHARE`) and the device row at attach (`FOR SHARE`, so a concurrent removal, which needs the row lock, serializes with the attach). The only paths that do not take the account row `FOR UPDATE` are the request-path touch (one statement on one session row) and first-sight creation (account row `FOR SHARE`, then the INSERT).

**`identity.account_audit_events` change (expand step).** The table gains two nullable columns and two COMPOSITE foreign keys, `fk_account_audit_events__account_session (account_id, application_session_id)` to `application_sessions (account_id, application_session_id)` (target `uq_application_sessions__account_session`) and `fk_account_audit_events__account_device (account_id, account_device_id)` to `account_devices (account_id, account_device_id)` (target `uq_account_devices__account_device`), both restrict, MATCH SIMPLE, so an audit row can only name a session or device of the audited account. `ck_account_audit_events__action` is dropped and re-created WIDER in the same transaction with sixteen actions (the 21 existing ones are kept; 37 in total): `SESSION_CREATED`, `SESSION_ENDED`, `SESSION_REVOKED`, `SESSIONS_REVOKED_ALL`, `DEVICE_TRUSTED`, `DEVICE_UNTRUSTED`, `DEVICE_REMOVED`, `MFA_ENROLLMENT_REQUESTED`, `MFA_ENABLED`, `MFA_DISABLED`, `RECOVERY_CODES_REQUESTED`, `RECOVERY_CODES_ENABLED`, `RECOVERY_CODES_DISABLED`, `PASSWORD_RESET_REQUESTED`, `PASSWORD_CHANGED`, `PASSWORD_RESET_COMPLETED`. The new `ck_account_audit_events__session` requires `(action LIKE 'SESSION\_%') = (application_session_id IS NOT NULL)` and `ck_account_audit_events__device` requires `(action LIKE 'DEVICE\_%') = (account_device_id IS NOT NULL)`; the underscore is escaped, so `SESSION\_%` matches `SESSION_CREATED`, `SESSION_ENDED` and `SESSION_REVOKED` but NOT `SESSIONS_REVOKED_ALL` (which has no session reference), and `DEVICE\_%` matches the three `DEVICE_` actions. A pure widening: no existing row is a new action and both new columns are NULL for all existing rows, no row is rewritten and the append-only trigger is not involved. The audit rows name the session by `application_session_id`, never the Keycloak `sid`, and carry no token, address or user agent in `changes`.

**MFA, recovery and the security timeline are not stored.** (1) The second-factor state (TOTP configured, recovery codes configured) and the password-changed instant are read from Keycloak on demand; there is no `mfa_enabled` column on `accounts`, no table of factors and no stored recovery code or code hash (Keycloak owns the `recovery-authn-codes` credential). (2) Transitions are OBSERVED lazily by comparing Keycloak's state with the last audited state of the account (under the account lock, idempotently) and written as `MFA_ENABLED`, `MFA_DISABLED`, `RECOVERY_CODES_ENABLED`, `RECOVERY_CODES_DISABLED`, `PASSWORD_CHANGED` or `PASSWORD_RESET_COMPLETED`. A factor that is already configured the FIRST time it is seen, with no enrolment request audited before, is a BASELINE: it is anchored with `changes.baseline = true` and no event (state that pre-dates the audit trail, not a transition); baseline rows are excluded from the timeline. (3) The security activity timeline is a READ MODEL over `identity.account_audit_events` (the 16 security actions plus `EMAIL_VERIFIED`, `EMAIL_PRIMARY_CHANGED`, `PHONE_VERIFIED`, `PHONE_PRIMARY_CHANGED`), newest first, cursor `before`, limited to the last `security.activity_log_days`; there is no `security_activity_events` table. The partial index `idx_account_audit_events__account_security_state` serves the "latest audited state" lookups (below).

**Indexes and their hot queries** (guardrail 11; the justification is also in the migration). Foreign keys are all `ON DELETE RESTRICT`; no referenced row is ever deleted or re-keyed.

| Index | Definition | Hot query |
|---|---|---|
| `uq_account_devices__account_hash` | UNIQUE `(account_id, device_hash)` | THE lookup of `registerSession` (upsert by the hashed cookie) and the rule that one browser is one row per account |
| `uq_account_devices__account_device` | UNIQUE `(account_id, account_device_id)` | the target of the composite foreign keys of `application_sessions` and `account_audit_events`; its `account_id` prefix also serves every read of ONE account's devices (a handful) and the `account_id` foreign key, so the device list needs no further index |
| `uq_application_sessions__keycloak_session` | UNIQUE `(keycloak_session_id)` | THE lookup of every authenticated web request (`sid` to row), the one-statement touch, and the rule that a `sid` is one row (two concurrent first requests insert ONE row) |
| `uq_application_sessions__account_session` | UNIQUE `(account_id, application_session_id)` | the target of the audit composite foreign key; also the key of revoke-by-id (a session of another account is not found) and the join of the timeline to its session |
| `idx_application_sessions__account_live` | `(account_id) WHERE revoked_at IS NULL` | the session list, revoke-all, the expiry close and the reconciliation: they read ONLY the live sessions of one account (a handful, at most about 200); the list sorts them in memory. Deliberately NOT keyed on `last_seen_at` |
| `idx_application_sessions__device` | `(account_id, account_device_id) WHERE account_device_id IS NOT NULL` | the sessions of a device: removing a browser, the trusted flag of the session list, the derived last seen of the device list; also the composite foreign key to `account_devices`. Neither column is written after the one-time device attach |
| `idx_account_audit_events__account_security_state` | `(account_id, occurred_at DESC) WHERE action IN` (the nine observed actions: `MFA_ENABLED`, `MFA_DISABLED`, `RECOVERY_CODES_ENABLED`, `RECOVERY_CODES_DISABLED`, `MFA_ENROLLMENT_REQUESTED`, `RECOVERY_CODES_REQUESTED`, `PASSWORD_CHANGED`, `PASSWORD_RESET_COMPLETED`, `PASSWORD_RESET_REQUESTED`) | "the latest audited state of a second factor, of the password and of the reset request of ONE account", read on every security overview and every login registration. Without it these rare actions would be found by scanning the account's whole audit history (one `SESSION_CREATED` row per login). Partial: the common rows (sessions, devices, contacts) are not in it |

Why `(account_id) WHERE revoked_at IS NULL` and not `(account_id, last_seen_at)`: `last_seen_at` is written on the request path, once a minute per session. A column that is part of an index makes every such UPDATE a non-HOT update (new index entries, index bloat, more WAL). With no index on `last_seen_at` and `fillfactor = 80` (free space left on each page for the new row version) the touch is a HOT update. The live sessions of one account are few, so the list sorts them in memory. The index is partial because revoked rows (the large majority over time) are never read by these queries. Deliberately NOT indexed: `revoked_at` and `revocation_reason` (no query filters history by them; the re-propagation lookup goes by `keycloak_session_id`), `created_at`, `account_devices.last_seen_at` and `trusted_until` (the device list reads one account's few rows; trust is evaluated on the row), and the two new audit foreign key columns `application_session_id` and `account_device_id` (the referenced rows are never deleted or re-keyed and no query filters audit rows by them; the timeline reads `idx_account_audit_events__account` and joins the session by its key). Foreign keys and their lookup paths: `application_sessions.account_id` to `accounts` and the composite `(account_id, account_device_id)` to `account_devices` (served by `idx_application_sessions__device`); `account_devices.account_id` to `accounts` (the prefix of `uq_account_devices__account_device`); the two audit composites to the unique keys above.

**Events.** Seven outbox events (aggregate type `identity_account`, identifiers only, never a token, a `sid`, a secret or an address) reuse `integration.outbox_events`: `bananagig.identity.session-created.v1`, `session-revoked.v1`, `sessions-revoked-all.v1`, `mfa-enabled.v1`, `mfa-disabled.v1`, `password-reset-requested.v1`, `password-reset-completed.v1`. The migration seeds emit no event. Revocation propagation to Keycloak is best effort AFTER the database commit and never undoes the application revocation.

**Retention and privacy.** Sessions, devices and audit rows are never deleted (revocation, removal and untrust are columns, not deletes); the audit table keeps `ON DELETE RESTRICT` on every reference, so no row can be purged by deleting its parent, and the purge of old sessions, removed devices and audit rows is open together with the other identity retention work (DEBT-0057 note, DEBT-0045). The coarse families are the only device descriptors; no raw IP, location or user agent exists to erase. Rotating `VERIFICATION_HASH_SECRET` makes every stored `device_hash` unmatchable: browsers are simply registered again as new device rows (their trust is lost; the old rows remain as history) and open verification challenges of the other channels expire in minutes; no data migration is needed.

## Stores and authority

| Store | Role | Authoritative? |
|---|---|---|
| PostgreSQL | Transactional state, jobs (pg-boss), **committed events (outbox)** | **Yes** |
| Valkey (configuration cache) | Cache and last-known-good copies of resolved configuration | No: PostgreSQL is authoritative; CRITICAL parameters are never cached |
| NATS JetStream | Event transport (stream `BANANAGIG_EVENTS`, 7-day retention, 2-minute duplicate window) | No: events originate from the outbox |
| Valkey (content cache) | Cache and last-known-good copies of resolved (un-rendered) content entries, plus generation counters for invalidation | No: PostgreSQL is authoritative; CRITICAL and LEGAL entries are never cached nor served from last-known-good |
| Valkey (geography cache) | Short-lived cache of public geography reads (keys `bg:{env}:geo:v1:<what>:<gen>`, generation counter `bg:{env}:geo:gen` bumped after commit, default TTL 300 s); management reads bypass it | No: PostgreSQL is authoritative; every cache failure degrades to a database read, and a lost generation bump is bounded by the TTL |
| Valkey (web session, account) | The web server session record (Keycloak tokens and the chosen active role) stays in Valkey as before; there is NO cache of the account, its roles or its status: PostgreSQL is read on every authenticated account request (a unique-key lookup, the account row and its memberships; DEBT-0047) | No: losing it signs the user out and forgets the chosen role, nothing else; the roles themselves are re-read from PostgreSQL and the active role is validated on every request |
| Valkey | Cache, derived state, rate limits | No (rebuildable, TTL on every key) |
| OpenSearch | Search projection | No (rebuilt from PostgreSQL) |
| SeaweedFS (S3) | Media/blobs | Authoritative for blob bytes; PostgreSQL holds metadata |

## Identity boundary (INF-004, ID-001)

Keycloak (database `keycloak`, infrastructure-owned) owns credentials, authentication, protocol sessions, MFA factors and token issuance; none of that is mirrored in PostgreSQL (the only session datum BananaGig stores, since ID-004, is its own application session registry, which references the Keycloak session id and holds no token or credential). Since ID-001 the BananaGig database owns the application account: schema `identity` (see the `identity.*` section above) holds the account, its mapping to the Keycloak login (`identity.external_identities`: provider type, issuer and the immutable Keycloak `sub`, unique together), the application roles and memberships, the status with its history, the core profile and the audit trail. There is no `users` table and no table of Keycloak data. The Keycloak realm roles (`customer`, `provider`) are not application data: they seed the first roles of a new account once and are never read again (ADR-0025). Admin logins are a separate Keycloak client and have no row in `identity` (ADR-0015, DEBT-0046). The email contact and its verification are stored since ID-002 (`identity.email_contacts` and `identity.email_verification_challenges`, ADR-0027, ADR-0028, `docs/engineering/EMAIL_VERIFICATION.md`); the phone contact and its verification are stored since ID-003 (`identity.phone_contacts` and `identity.phone_verification_challenges`, ADR-0030 to ADR-0033, `docs/engineering/PHONE_VERIFICATION.md`); the application session registry, the device registry and the revocation watermark are stored since ID-004 (`identity.application_sessions`, `identity.account_devices`, `identity.accounts.sessions_not_before`, ADR-0034 to ADR-0036, `docs/engineering/SESSIONS_AND_MFA.md`); passwords, TOTP secrets and recovery codes are never stored (Keycloak owns them); address ownership is not stored yet. Web sessions live in Valkey (non-authoritative, TTL on every key). See `docs/engineering/IDENTITY.md` and `docs/engineering/ACCOUNTS.md`.
