# Database Conventions

The binding conventions every migration and database-touching feature follows. `DATA_MODEL_GUARDRAILS.md` holds the review rules; this document holds the concrete choices. Decisions with architectural weight are recorded as ADRs (0001, 0004, 0008, 0010, 0011, 0012).

## 1. Schemas and ownership

| Class | Schemas / objects | Rule |
|---|---|---|
| **APPLICATION OWNED** | `public.schema_migrations` (migration bookkeeping), `integration` (outbox), and every future domain schema | Created and changed only by `db/migrations/*.sql` |
| **INFRASTRUCTURE OWNED** | `pgboss.*` (pg-boss), the whole `keycloak` database | Never altered by our migrations; accessed only through the owning library or product |
| **EXTENSION OWNED** | PostGIS: `public.spatial_ref_sys`, `geometry_columns`, `geography_columns`, PostGIS functions and types | Never altered or dropped; excluded from the schema snapshot |

**Schemas created now:** `integration` (outbox), `configuration` (CFG-001) and `content` (CFG-002), because each is used today. Per ADR-0008 every other domain schema is created by the migration of the first feature that needs it, so empty namespaces are not created speculatively.

**Deferred schemas (not created):** `identity`, `geography`, `catalog`, `provider`, `capacity`, `search`, `booking`, `finance`, `banana_credit`, `subscription`, `tax`, `messaging`, `trust`, `admin`, `audit`. Their names are reserved by this list; a different name needs an ADR. `configuration` and `content` are no longer deferred: they exist (CFG-001, CFG-002). `public` holds infrastructure only, never product tables.

Future migrations must not alter infrastructure- or extension-owned objects. Need something from pg-boss or PostGIS? Use their APIs, or create our own object in an application schema.

## 2. Naming

| Object | Convention | Example |
|---|---|---|
| schema | snake_case, singular domain noun | `banana_credit`, `integration` |
| table | snake_case, **plural** | `outbox_events` |
| column | snake_case, singular | `published_at` |
| primary key column | `<entity>_id` (singular entity) | `outbox_event_id` |
| foreign key column | name of the referenced key | `provider_id` |
| primary key constraint | `pk_<table>` | `pk_outbox_events` |
| foreign key constraint | `fk_<table>__<column>` | `fk_bookings__provider_id` |
| unique constraint | `uq_<table>__<columns>` | `uq_schema_migrations__filename` |
| check constraint | `ck_<table>__<rule>` | `ck_outbox_events__attempts_nonnegative` |
| index | `idx_<table>__<columns>` (partial: add the predicate meaning) | `idx_outbox_events__pending` |
| boolean | predicate, `is_`/`has_` prefix | `is_active` |
| timestamp | `_at` suffix; date-only `_on` | `created_at`, `starts_on` |

Exception: bookkeeping table `public.schema_migrations` uses its natural key `version` (not `schema_migration_id`); it is migration infrastructure, not a domain entity. (The earlier guardrail names `ix_`/`pk_` were superseded by this table in INF-003.)

## 3. Identifiers (UUID strategy)

**UUIDv4 generated by PostgreSQL: `uuid PRIMARY KEY DEFAULT gen_random_uuid()`.** (ADR-0011)

- PostgreSQL 17 has no built-in UUIDv7 (`uuidv7()` arrives in PostgreSQL 18), and UUIDv7 would need either an extension or application-side generation. UUIDv4 is available cleanly today, so v4 is chosen. Revisit when the server moves to PostgreSQL 18: new tables may then default to `uuidv7()` (time-ordered keys index better). Existing ids are never rewritten.
- Generated server-side (database default). Clients never choose authoritative ids. A caller-supplied id is allowed only when it is an idempotency or correlation token stored in its own column.
- No sequential integer business identifiers anywhere (no `serial`/`identity` primary keys for entities). Human-friendly reference numbers, if ever needed, are separate columns.
- Public/external ids may differ from internal ids later (separate column); do not leak internal keys by accident.
- Exceptions need to be justified in the migration header: for example `public.schema_migrations.version` is a small integer because it is an ordered, human-managed version number, not a business entity.

## 4. Timestamps

- Real-world instants are `timestamptz`, stored with UTC semantics (the database session timezone is irrelevant; always convert at the edge). `timestamp without time zone` is prohibited for user or business events.
- `created_at timestamptz NOT NULL DEFAULT now()` on every table. `updated_at timestamptz NOT NULL DEFAULT now()` on mutable tables, maintained by the application inside the same transaction (a trigger is added only if drift appears).
- `occurred_at`: when the business fact happened (may differ from `created_at`, e.g. imported or delayed facts). Events carry `occurredAt` in the envelope.
- `effective_from` / `effective_to`: validity interval of versioned data, half-open `[from, to)`, `effective_to` NULL meaning open-ended, with a check `effective_to IS NULL OR effective_to > effective_from` and an exclusion or unique constraint preventing overlaps for the same entity.
- Date-only facts (a calendar day with no instant) use `date` with the `_on` suffix and an explicit timezone column when the day depends on a place.

## 5. Money

**Integer minor units plus an explicit currency**, never floating point. (ADR-0011)

- `amount_minor bigint NOT NULL` (for example cents) and `currency char(3) NOT NULL` with `CHECK (currency ~ '^[A-Z]{3}$')` (ISO 4217 code). An amount column never exists without its currency column; related columns share one currency by construction (one `currency`, several `*_minor` columns) or carry their own.
- `NUMERIC(19,4)` was rejected: it invites fractional-minor-unit drift and per-row scale decisions; integer minor units make arithmetic exact and rounding an explicit, single, documented step.
- Rounding happens only where a rate is applied (tax, percentage fees, FX), in one named function per use, with the rule stored next to the rate data (for example half-even or half-up, decided per tax regime) and tested. Intermediate results keep full precision as integers or high-precision numeric inside the computation and are rounded once at the boundary.
- Never store computed totals that can drift; if a total is stored (statement snapshot), it is an immutable snapshot (see guardrail 14).
- **Banana operational units are NOT money.** They are plain integer units (`bigint`, whole units, no currency column), held in their own ledger structures. They are never stored in an `amount_minor` column, never share a column with monetary values, and a conversion between Banana units and money exists only as explicit, versioned business configuration. Money and Banana units cannot be summed or compared by type or by column.
- Configurable prices, fees and rates are product configuration data, never schema defaults or code constants.
- No financial tables exist yet.

## 6. Transactions, isolation, locking

Transaction boundaries belong to the caller (service layer), never to repositories. Use `Database.transaction(fn, options)` from `@bananagig/database`.

**Options:** `isolationLevel` (default `read committed`), `readOnly`, `timeoutMs` (statement timeout for the transaction), `lockTimeoutMs`, `correlationId` (also taken from the request context; stored as `app.correlation_id` for future audit triggers).

**Nesting:** an inner `transaction()` joins the outer one (no savepoints, one commit). An inner call that asks for a different isolation level, or read-write inside read-only, throws `TransactionOptionError`. Outer timeouts and correlation id apply. Need an independent commit? Do not nest; restructure.

**Rollback:** any thrown error rolls back everything, including joined inner work.

### Isolation levels

| Level | Use for | Notes |
|---|---|---|
| **READ COMMITTED** (default) | Ordinary CRUD and single-statement invariants | Each statement sees committed data. Combine with row locks for read-then-write on invariant-bearing rows |
| **REPEATABLE READ** | Multi-read consistent snapshots (reports, a calculation that reads several tables and must see one moment) | Read-mostly. Writes can fail with 40001 and must be retried |
| **SERIALIZABLE** or explicit locking | High-contention invariants across rows where locking the guarding row is awkward (write skew) | Not global. Callers must retry on 40001/40P01 (`isRetryableConcurrencyError`). Prefer a row lock on a single guard row when one exists |

SERIALIZABLE is **not** the default and is never applied globally.

### Row locks (`applyRowLock`)

| Clause | Allowed use |
|---|---|
| `FOR UPDATE` | Row will be changed or deleted; balances and any read-then-write on invariant-bearing rows |
| `FOR NO KEY UPDATE` | Non-key columns change while FK-referencing inserts must keep working (parent rows) |
| `FOR SHARE` | Guarantee the row does not change until commit, without changing it |
| `FOR KEY SHARE` | Guarantee the key is not changed or deleted (FK checks take this) |
| `NOWAIT` | Fail fast on contention (user-facing paths map the error to CONFLICT) |
| `SKIP LOCKED` | **Only** queue-like claiming (outbox relay, job claim). Never for balances, credit lots, reservations, payments or any read that must see every row |

Rules: lock in a consistent order (table, then primary key ascending); keep transactions short; never hold a lock across a network call (the outbox relay claims with a short lease transaction and publishes afterwards); always bound waits with `lockTimeoutMs` or the pool's `lock_timeout`. Future critical uses (Banana credit account mutation and lot allocation, slot confirmation, dispute resolution, payment state transitions) lock the owning row(s) with `FOR UPDATE` in a documented order inside one transaction. No business implementation exists yet.

Error codes to handle: `55P03` lock not available/lock timeout, `40P01` deadlock, `40001` serialization failure, `57014` statement timeout/cancel.

### Advisory locks

- Allowed: the migration runner; singleton maintenance tasks (`withAdvisoryLock('maintenance', id, fn)`: run only if the lock is free); controlled projection rebuilds; outbox retention purge.
- **Not allowed:** protecting financial or inventory state; those use row locks on the data they guard.
- Transaction-scoped (`advisoryXactLock`) when tied to a transaction; session-level `withAdvisoryLock` only through the helper (always unlocked in `finally`).
- Keys are registered in `ADVISORY_NAMESPACES` (`packages/database/src/locks.ts`): `maintenance=1`, `projectionRebuild=2`, `outboxPurge=3` (two-int form, `(namespace, id)`). The migration runner uses the one-bigint form key `7265001`, a separate key space. New namespaces are added to the registry and to this table in the same change.

## 7. Connection pools and timeouts

Defaults live in `packages/database/src/policy.ts`; environment variables (`DB_POOL_MAX`, `DB_IDLE_TIMEOUT_MS`, `DB_CONNECTION_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`) override them. Business code never sets limits.

| Role | max (min is 0: pg opens lazily) | idle timeout | connect timeout | statement timeout | lock timeout | idle-in-transaction timeout |
|---|---|---|---|---|---|---|
| api | 10 | 30 s | 5 s | 15 s | 5 s | 30 s |
| worker | 10 (+5 pg-boss pool) | 30 s | 5 s | 60 s | 10 s | 60 s |
| migrations | 1 | 1 s | 10 s | 10 min | 30 s (runner sets `lock_timeout`) | none |
| tests | 5 | 1 s | 5 s | 10 s | 3 s | 30 s |

- **Statement timeout:** every application connection has one, so a runaway query is cancelled (SQLSTATE 57014) instead of holding a connection forever. Controlled maintenance or migration work overrides it explicitly (per transaction `timeoutMs`, or the migrations role).
- **Capacity:** PostgreSQL `max_connections` is 100 locally (`superuser_reserved_connections` 3). Worst case for one api replica, one worker replica (pool + pg-boss), one migration run, one test run and an allowance of 20 for Keycloak is 56, asserted by an integration test (`connectionBudget()`); with N replicas multiply the api and worker parts. A production deployment must size `max_connections` (or add PgBouncer) before adding replicas.

## 8. Observability

`createDbTelemetry` (observability package) plugs into `Database` hooks and exposes, at `/metrics`: `db_query_duration_seconds{operation}`, `db_transaction_duration_seconds{outcome}`, `db_slow_queries_total`, `db_connection_errors_total`, and `db_pool_connections{pool,state}`. Queries also produce `db.query` spans carrying the correlation id. A slow query (`DB_SLOW_QUERY_MS`, default 500) logs a warning. **SQL text is not logged or attached to spans unless `DB_LOG_SQL=true`** (off by default; SQL can embed sensitive literals); only the operation keyword is recorded. Never log bind parameters, secrets, payment details or private message contents.

## 9. PostGIS

- **Points:** `geography(Point, 4326)`, built with `ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography`. Longitude first.
- **Service areas:** `geography(MultiPolygon, 4326)` with `CHECK (ST_IsValid(area::geometry))`. Geography keeps point-in-area and distance accurate over any extent without casts or planar error; `ST_Covers(area, point)` answers containment. Use `geometry` only for planar computations that need geometry-only functions, with an explicit cast and a comment.
- **SRID 4326** everywhere; never mix SRIDs.
- **Distance units:** meters. `ST_Distance` and `ST_DWithin` on geography take meters.
- **Indexes:** every geography column used in a filter gets `CREATE INDEX idx_<table>__<column> ON ... USING GIST (<column>)`. Radius queries use `ST_DWithin` (index-assisted), never `ST_Distance(...) < x`. Verified by `postgis.itest.ts`.
- **Latitude/longitude validation happens BEFORE building a point** (API boundary: lat -90..90, lng -180..180). PostGIS silently coerces out-of-range input into range instead of failing, so a CHECK on the stored value cannot catch a bad input (verified by test).
- Spatial columns hold the location; derived address text is a separate concern. No geographic business tables exist yet.

## 10. Idempotency and outbox

- **Outbox: implemented** in INF-003 (`integration.outbox_events`, relay in the worker). Producers insert in the same transaction as the state change (`insertOutboxEvent(trx, ...)`); the relay claims with a lease, publishes to JetStream with `Nats-Msg-Id = outbox_event_id`, then marks published; delivery is at-least-once, consumers dedupe by `eventId`. PostgreSQL is the committed-event source; NATS is transport. (ADR-0012)
- **Idempotency records: deferred.** No cross-domain implementation exists yet and a generic table without its first user would be speculative schema. It enters with the first checkpoint that has externally triggered writes (payment webhooks or an API operation accepting an `Idempotency-Key`), as `integration.idempotency_records` (`idempotency_key`, `operation_type`, `request_hash`, `status`, `result_reference`, `created_at`, `completed_at`, `expires_at`; unique on `(operation_type, idempotency_key)`), written in the same transaction as the effect it guards. Tracked as DEBT-0013.

## 11. Database security baseline

- **Local development (DEV ONLY):** the API, worker and migration runner connect as the container's bootstrap superuser (`bananagig`, password from `.env`, a dev placeholder). Verified `pg_hba.conf` of the dev container: connections over the unix socket and loopback *inside the container* use `trust` (this is the upstream image default, used by the healthcheck and `docker exec psql`); every connection arriving over the network (other containers, and the host through the published port, which is bound to 127.0.0.1 only) requires `scram-sha-256`. This simplification (superuser at runtime) is acceptable only on a developer machine.
- **Target model (not yet implemented, DEBT-0012):** a `bananagig_migrator` role owns all application schemas and runs migrations (DDL); a non-superuser `bananagig_app` role used by api and worker has `USAGE` on application schemas and `SELECT/INSERT/UPDATE/DELETE` on their tables via default privileges, no DDL, no `CREATE`, no extension rights; pg-boss's schema is created by the migrator (its construction plan) and used by the runtime role; PostGIS and other extensions are installed by the migrator. Superuser is never used at runtime. Future schema ownership: each domain schema is owned by the migrator role; runtime roles hold only the grants above.
- No `trust` authentication outside the dev container (production images must not keep the upstream loopback `trust` rules); production requires TLS (`sslmode=verify-full`) and secrets from a secret store.
- Connection strings are redacted before logging (`redactConfig`); telemetry never records credentials or SQL parameters.
