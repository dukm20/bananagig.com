# Consent and legal-version history

ID-005 records what an account did with each legal document: which exact version it accepted, in which language, with which text hash, when, and what happened since (a newer version, a withdrawal). The legal documents themselves (their text, versions, translations, approval and publication) belong to the content registry (CFG-002); this layer owns only the ACCOUNT'S relationship to a version. Nothing is accepted for a person: an acceptance exists only as the result of an explicit request that names the version the person was shown. Decisions: ADR-0037 (the append-only event log bound to the exact version, locale and hash) and ADR-0038 (policy as configuration and derived current state). Baselines: ADR-0018 (content model), ADR-0020 (legal never falls back, never cached), ADR-0016 (configuration), ADR-0025 (application account).

Requirements served: CU-03 (the sign-up consent field: "Required checkbox for Terms of Service and Privacy Policy, both linked; consent version and time stored"; the screen is NOT built, DEBT-0076), SV-02.04 ("Legal and consent texts are versioned; each acceptance records the exact version"), CU-09.22 (the account's consent history with document versions and dates: the data and a minimal page exist, the final account screen does not), R-13 (optional consents are never pre-ticked: nothing in this layer pre-selects, defaults or auto-accepts), PR-01 (the provider sign-up acknowledgements: structurally supported, only the two documents below are seeded, DEBT-0080) and AD-07 (an admin accepts the current confidentiality policy before console access: a purpose can be added the same way, not built, DEBT-0080).

## Scope

In scope: migration 0013 (two tables, the in-force function, four guards, the audit extension, two LEGAL entry shells, four configuration parameters, 40 managed content entries), `ConsentService` (`packages/accounts/src/consent-service.ts`) with its pure evaluator and policy parser, four API operations, the page `/consents` with two BFF handlers, and the signup-readiness services.

Out of scope (nothing exists for any of these, see TECH_DEBT): the sign-up and provider-onboarding screens that REQUIRE consent (DEBT-0076); any other purpose such as provider agreements, marketing, cookies or the confidentiality policy (DEBT-0080); notifying people of a new version, an admin compliance console, a consent export, reading the full text of a historical version (DEBT-0078); a regional consent-law engine and market-scoped policy (DEBT-0079); retention and erasure of consent records (DEBT-0045, DEBT-0057).

## Ownership

| Question | CFG-002 (content registry) | ID-005 (this layer) |
|---|---|---|
| The legal text, its versions, translations, approval (second approver), publication, effective window | owns (LEGAL entries, immutable `content.versions`) | never copies a word of it |
| The hash of the text | computes it (`body_sha256`, insert trigger) | stores it, bound to the version by a composite foreign key |
| Which version is in force now, in a language | the resolver (`resolver.ts`) | reuses the SAME definition (`identity.consent_version_state`, parity-tested) |
| Who must accept which document, and what a newer version does to an old acceptance | nothing | configuration (CFG-001): `consent.<purpose>.required_for` and `consent.<purpose>.reacceptance` |
| That an account accepted or withdrew a purpose, when, which version, locale and hash | nothing | owns (`identity.consent_events`, append-only) |
| Whether the account is currently compliant | nothing | DERIVED at read time (`getRequirements`); no flag is stored |
| The screens' copy (labels, notices, errors) | owns (entries `account.consent.*`) | seeds it through the real lifecycle, renders nothing itself |
| The legal wording | Legal publishes it through the content workflow | none is shipped; a fresh environment has no version of either document |

## The model

```text
identity.consent_purposes (reference data)         content.entries (LEGAL)  ->  content.versions (immutable)
  purpose_code PK   document_entry_id  ---------->   legal.terms_of_service        version_id, locale, body_sha256 ...
  withdrawal_policy  status                          legal.privacy_policy                 ^
        ^                                                                                 | composite FK
identity.consent_events (append-only)                                                     | (version_id, locale, body_sha256)
  account_id, purpose_code, event_seq, event_type ACCEPTED|WITHDRAWN,
  version_id, locale, body_sha256, occurred_at, source, application_session_id, correlation_id
```

- **Purposes.** `TERMS_OF_SERVICE` and `PRIVACY_POLICY` are seeded (both `NOT_WITHDRAWABLE`, `ACTIVE`). A purpose is bound to exactly ONE LEGAL entry (`document_entry_id` is unique: no parallel catalogue of purposes and documents) and carries the structural `withdrawal_policy` (`NOT_WITHDRAWABLE` for conditions of the service, `WITHDRAWABLE` for optional consents). `purpose_code`, `document_entry_id` and `withdrawal_policy` are immutable and rows are never deleted; only `status` changes (`INACTIVE` retires a purpose: it cannot be accepted and is no longer evaluated, existing events stay, an accepted withdrawable consent can still be withdrawn).
- **The event log.** ONE append-only table is both the immutable acceptance record and the history. Each row is `ACCEPTED` or `WITHDRAWN`, numbered per (account, purpose) by `event_seq` (1, 2, 3, ...). A correction is a new event; UPDATE, DELETE and TRUNCATE are refused by trigger (`ROW_IMMUTABLE`, the audit tables' pattern). The first event of a history is always `ACCEPTED`.
- **The composite binding.** `(version_id, locale, body_sha256)` references `content.versions (version_id, locale, body_sha256)` (the additive `uq_versions__version_locale_hash`). The version is immutable and never deleted, so the row proves WHAT was accepted without storing it, and the stored locale and hash cannot disagree with the version: the database proves them. A wrong hash or locale is a foreign key violation (SQLSTATE 23503), not a service check that could be bypassed. The text itself is read through the version id.
- **Derived current state.** `NONE`, `ACCEPTED` or `WITHDRAWN` is the type of the LATEST event of an account and purpose. No `current_accepted` column exists, so nothing can drift. Whether an acceptance still SATISFIES the purpose is a separate, policy-dependent question answered by the evaluator (below).
- **Idempotency.** Accepting the version the latest event already accepts changes nothing and answers `changed: false` with that event (even when the version has been superseded since, or the purpose deactivated; the claimed locale and hash are still compared first); the same for a repeated withdrawal. A different version after an acceptance is a new `ACCEPTED` event, which must not be older (same locale: a greater version number) and is refused as `CONSENT_VERSION_NOT_CURRENT` when it is not in force. An acceptance after a withdrawal is a re-grant: any version in force, the same one included.
- **Withdrawal.** Allowed only for a `WITHDRAWABLE` purpose, only when the latest event is `ACCEPTED`, and refused (`CONSENT_REQUIRED_FOR_ROLE`) while the purpose is REQUIRED for a role of the account (so a required consent cannot be withdrawn to dodge the requirement). The `WITHDRAWN` event carries the same version, locale and hash as the acceptance it withdraws (trigger `CONSENT_WITHDRAWAL_VERSION`). Closing an account has no consent consequence. Both seeded purposes are `NOT_WITHDRAWABLE`, so today every withdrawal is `409 ACCOUNT_CONSENT_NOT_WITHDRAWABLE`; the machinery is exercised with purposes added later.
- **Time and session.** `occurred_at` is the DATABASE clock, set by the guard trigger (a supplied value is overwritten with the instant at which eligibility was checked). No client timestamp, raw IP address or user agent is stored. `application_session_id` (ID-004) is optional and tied to the same account by the composite foreign key `(account_id, application_session_id)`; the API always passes the caller's own session. `source` has the single value `ACCOUNT_API`.
- **Audit and events.** In the SAME transaction as the event: an audit row `CONSENT_ACCEPTED` / `CONSENT_WITHDRAWN` (action list now 39, `consent_event_id` set exactly for the `CONSENT_` actions, `changes` = `{purposeCode, eventSeq}`) and the outbox event `bananagig.identity.consent-accepted.v1` / `consent-withdrawn.v1` (aggregate `identity_account`, payload `accountId`, `purposeCode`, `consentEventId`, `eventSeq`, `contentVersionId`). Neither holds text, locale or hash; they are reachable through the version id.

## Database-enforced eligibility

An `ACCEPTED` event can only be inserted for a version that is IN FORCE at the moment of the insert, and the database says so, not only the service. The guard trigger `identity.guard_consent_events` (BEFORE INSERT) takes the locks in one order and then decides:

1. the account row `FOR SHARE` (the service already holds it `FOR UPDATE`; a writer outside the service takes the share lock here, so closing the account serializes with the insert); a CLOSED account gets `ACCOUNT_CLOSED`;
2. the purpose row `FOR SHARE`;
3. (ACCEPTED only) the `content.versions` row `FOR SHARE`;
4. only THEN `v_now := clock_timestamp()` and `identity.consent_version_state(version_id, document_entry_id, v_now)`.

`consent_version_state` is the SINGLE definition of "in force", used by the trigger and by every service query (so the page, the evaluator and the guard cannot disagree). It returns `NOT_FOUND` for a version that does not exist, belongs to another entry than the purpose's document, is not PLATFORM scope, or is not published (DRAFT, IN_REVIEW, APPROVED, REJECTED and CANCELLED are indistinguishable from an unknown id); `IN_FORCE` when the version is published (SCHEDULED, PUBLISHED or SUPERSEDED are workflow labels, the timestamps decide), its entry and locale are active and `effective_from <= at < effective_to` (half-open); `NOT_CURRENT` otherwise. A SCHEDULED version whose start has passed but which the activation job has not yet advanced IS in force, exactly as the resolver serves it. The exclusion constraint of `content.versions` guarantees at most one in-force version per entry, locale and scope, which is why "the version in force" is well defined. Only PLATFORM-scope versions can be accepted; the shell entries are created with `max_scope_type` PLATFORM, so a country- or market-scoped version of these documents cannot exist yet (DEBT-0079).

The rest of the guard (all rule keys are reported as `DETAIL identity_rule:<KEY>`, SQLSTATE 23000): `CONSENT_SEQUENCE` (`event_seq` must be previous + 1, the first is 1; two writers racing for one number also collide on `uq_consent_events__account_purpose_seq`, so a history cannot fork), `CONSENT_PURPOSE_INACTIVE`, `CONSENT_VERSION_NOT_FOUND`, `CONSENT_VERSION_NOT_CURRENT`, `CONSENT_DUPLICATE` (ACCEPTED after ACCEPTED of the same version), `CONSENT_VERSION_STALE` (same entry and locale, version number not greater), `CONSENT_NOT_WITHDRAWABLE`, `CONSENT_NOT_ACCEPTED` (first event not ACCEPTED, or WITHDRAWN after WITHDRAWN), `CONSENT_WITHDRAWAL_VERSION`. The purpose guard adds `CONSENT_PURPOSE_DOCUMENT` (the entry must be LEGAL), `CONSENT_PURPOSE_IMMUTABLE` and `NOT_DELETABLE`.

**Why an accept racing a publish is safe.** Publishing a successor closes the head version's window by updating the head's row. Because the trigger share-locks that row BEFORE it reads the clock and evaluates the window: (a) if the publication committed first, the accept's lock waits for it, the next statement sees the closed window and the accept is refused (`CONSENT_VERSION_NOT_CURRENT`); (b) if the accept holds the lock first, the publication's update waits for the accept's transaction, so the accept lands as a valid historical fact (the version WAS in force at `occurred_at`) and the publication follows. There is no interleaving in which an event is stored for a version that was not in force at its own `occurred_at`. This relies on the default READ COMMITTED isolation of the write transaction (each statement takes a fresh snapshot, so the check after the lock sees what the lock waited for; the read-only snapshot reads use REPEATABLE READ). The lock order is part of the design: publishing locks the ENTRY row and then the VERSION row, so the trigger must never take an entry or locale lock after the version lock (that would deadlock with a publication); entry and locale activation are therefore not locked by the trigger (DEBT-0081). A future least-privilege database role needs UPDATE on `content.versions`, `identity.accounts` and `identity.consent_purposes` because `FOR SHARE` requires it, or the trigger must become `SECURITY DEFINER` (DEBT-0081, DEBT-0012).
**Contract for anything that closes a window (found by the service tests).** The guarantee "every acceptance lies inside its version's window" holds only if the closer locks the version row BEFORE it reads the clock, as `ContentService.publish` does (it locks the head row `FOR UPDATE`, then reads the clock). A closer that evaluates the clock first and then waits for the row lock, for example `UPDATE content.versions SET effective_to = clock_timestamp() ...` run by hand or by a back-office script, can store an acceptance a few milliseconds after the close. Any such script must `SELECT ... FOR UPDATE` the version row first. The service test file reproduces the failure with the unsafe order on purpose.

The service pre-checks the same function without the lock, only to answer with a precise error; the trigger is the arbiter, and its rule keys are mapped to the same typed errors for a race.

**Accept check order** (under the account lock; the order is information control: the CLASS of an error never reveals the locale or hash of a version that is not in force): (1) a malformed claim is `VALIDATION_FAILED`; unknown purpose `PURPOSE_NOT_FOUND`; (2) a version that is unknown, another document's, not published (any non-published status) or not PLATFORM scope is `VERSION_NOT_FOUND`; (3) if the latest event already accepts this very version, the claimed locale and hash are compared (`LOCALE_MISMATCH`, `HASH_MISMATCH`) and then the answer is `changed: false`; (4) an INACTIVE purpose is `PURPOSE_INACTIVE`; (5) a version not in force now is `VERSION_NOT_CURRENT`, BEFORE any comparison of the claim, so a stale or scheduled version with a wrong locale or hash is 409, never 400; (6) only then `LOCALE_MISMATCH` (exact), `HASH_MISMATCH`, and the insert.

## Requirement evaluation

`getRequirements(accountId, { locale?, purposes? })` answers "what must this account accept now, and is it compliant?":

- **Roles considered**: the account's `account_roles` with status `PENDING` or `ACTIVE`. A provider role that was requested but is not active yet already needs the provider's agreements. A purpose is **required** when ANY considered role is in its `required_for` list.
- **Locale**: the request's `locale`, else the profile's `preferred_locale`, else the platform default (`content.locales.is_platform_default`). An explicit locale must be a REGISTERED locale of `content.locales` and is compared exactly (`es-mx` is not `es-MX`); anything else is `VALIDATION_FAILED` (`reason` `INVALID_LOCALE`, `field` `locale`). Legal documents never fall back to another locale (ADR-0020): if the language has no version in force, the document is unavailable.
- **Consistency**: `getConsents` and `getRequirements` read the account, roles, locales, versions in force and latest events in ONE read-only REPEATABLE READ snapshot (no lock), so a concurrent accept or publication cannot make `current`, `history` and the requirements disagree with each other; the configuration policy is read outside that snapshot.
- **Evaluated purposes**: every ACTIVE purpose, or the ACTIVE ones among `purposes` (unknown code `CONSENT_PURPOSE_NOT_FOUND`; an INACTIVE purpose is silently skipped; duplicates removed).
- **The policy** (below) is read per evaluated purpose, fresh (CRITICAL parameters are never cached), and parsed strictly; an unknown role code in `required_for` or an invalid value is `UNAVAILABLE` (`POLICY_INVALID`), never "nobody is required".

Order of the evaluator (`evaluateRequirement`, pure, table-tested):

1. no considered role needs the purpose: `NOT_REQUIRED`;
2. the latest event is an acceptance and the mode is lenient: `NO_REACCEPT` is `SATISFIED` by any accepted version in any locale, and `REACCEPT_FOR_NEW_USERS_ONLY` is `SATISFIED` when the accepted locale equals the evaluated one, in both cases EVEN WHEN NO DOCUMENT IS IN FORCE (a gap in Legal's timeline, or the deactivation of the entry or locale, does not un-satisfy people who already accepted);
3. no version in force in the evaluated locale: `DOCUMENT_UNAVAILABLE` (still the case under `REACCEPT_REQUIRED` even if the account accepted earlier, and for anyone the lenient rules did not satisfy);
4. the latest event is not an acceptance (none, or `WITHDRAWN`): `OUTSTANDING`;
5. otherwise by the **re-acceptance mode** of the purpose:

| Mode | Satisfied when | Otherwise |
|---|---|---|
| `REACCEPT_REQUIRED` (seeded default) | the accepted `version_id` IS the version in force | `REACCEPTANCE_REQUIRED` (a newer version, or an acceptance in another language, needs a new acceptance) |
| `REACCEPT_FOR_NEW_USERS_ONLY` | the accepted version has the SAME locale as the evaluated one, whatever its version number | `OUTSTANDING` (never accepted in this language) |
| `NO_REACCEPT` | any accepted version in any locale (decided at step 2, before the document is looked at) | never fails after step 2 |

Examples (account accepted version 1 of a document in `en-US`): version 2 `en-US` becomes the version in force: `REACCEPT_REQUIRED` gives `REACCEPTANCE_REQUIRED`, the other two give `SATISFIED`. The account is then evaluated in `es-MX` where version 1 is in force: `REACCEPT_REQUIRED` gives `REACCEPTANCE_REQUIRED`, `REACCEPT_FOR_NEW_USERS_ONLY` gives `OUTSTANDING` (never accepted in `es-MX`), `NO_REACCEPT` gives `SATISFIED`. If `es-MX` has no version in force, `REACCEPT_REQUIRED` gives `DOCUMENT_UNAVAILABLE` and `REACCEPT_FOR_NEW_USERS_ONLY` gives `DOCUMENT_UNAVAILABLE` too (the acceptance was in another locale), while `NO_REACCEPT` stays `SATISFIED`; and for a person evaluated in the locale they accepted in, a gap in Legal's timeline leaves the two lenient modes `SATISFIED` and `REACCEPT_REQUIRED` `DOCUMENT_UNAVAILABLE`. A person whose preferred locale has no LEGAL version stays `DOCUMENT_UNAVAILABLE` under `REACCEPT_REQUIRED`: there is no silent fallback by design, and a gating flow must pass the locale it actually shows. A person who accepts in a second language makes that acceptance their latest event; cross-language equivalence is not modelled (DEBT-0079).

| Status | Meaning | Counts as outstanding |
|---|---|---|
| `NOT_REQUIRED` | no considered role requires the purpose (it may still be accepted voluntarily; `acceptanceState` says so) | no |
| `SATISFIED` | required and satisfied under the mode | no |
| `OUTSTANDING` | required, never accepted (or withdrawn, or never accepted in this language under the middle mode) and a document is in force | yes |
| `REACCEPTANCE_REQUIRED` | required, accepted before, but the mode needs the version in force | yes |
| `DOCUMENT_UNAVAILABLE` | required, no version is in force in the evaluated locale, and the lenient rules did not already satisfy it: nothing can be accepted now | yes |

`satisfied` is true when no required purpose is outstanding; `outstanding` lists their codes. Each requirement carries `document` (the version in force in the evaluated locale: `entryKey`, `versionId`, `version`, `locale`, `bodySha256`, `effectiveFrom`; null when none) and `accepted` (the latest event when it is an acceptance).

**DOCUMENT_UNAVAILABLE in a fresh environment.** Migration 0013 creates the two LEGAL entry SHELLS (`legal.terms_of_service`, `legal.privacy_policy`: owner LEGAL, PUBLIC, CRITICAL, `SECOND_APPROVER`, `EXACT`, max scope PLATFORM, no versions) and ships no legal text. Until Legal publishes a version in a language, every required purpose in that language is `DOCUMENT_UNAVAILABLE` (no one has accepted anything yet, so the lenient modes cannot satisfy it either), nobody can accept, and `satisfied` is false. The same holds in CI. **How Legal publishes the first versions**: through the content workflow of `docs/engineering/CONTENT.md` (create a version of the entry in a locale, submit it as its author, approve it as a DIFFERENT approver, publish; the roles `content-legal` plus `content-write` / `content-approve` apply). There is no consent-specific publishing path and no seed text. For development see `docs/engineering/LOCAL_DEVELOPMENT.md`. A test or smoke scenario that needs a document must publish one through the real workflow with two approvers.

## Configuration

Four CFG-001 parameters seeded by migration 0013 through the real change workflow (`SECOND_APPROVER`, CRITICAL so never cached and never last-known-good, sensitivity INTERNAL, owner `legal`, scopes PLATFORM, COUNTRY and MARKET):

| Key | Type | Value | Source |
|---|---|---|---|
| `consent.terms_of_service.required_for` | JSON array of role codes (pattern, unique, at most 10) | `["CUSTOMER","PROVIDER"]` | PRD CU-03 and PR-01 (both roles accept the Terms); not yet confirmed with Legal (DEBT-0077) |
| `consent.privacy_policy.required_for` | same | `["CUSTOMER","PROVIDER"]` | same |
| `consent.terms_of_service.reacceptance` | ENUM `NO_REACCEPT`, `REACCEPT_FOR_NEW_USERS_ONLY`, `REACCEPT_REQUIRED` | `REACCEPT_REQUIRED` | engineering ASSUMPTION: the PRD does not say what a new version does to existing acceptances (DEBT-0077) |
| `consent.privacy_policy.reacceptance` | same | `REACCEPT_REQUIRED` | same ASSUMPTION |

An empty `required_for` list means nobody is required. The keys are derived from the purpose code in lower case (`consentRequiredForKey`, `consentReacceptanceKey`). The consumer (`createConsentPolicyProvider`, `apps/api/src/modules/consent/wiring.ts`) resolves both keys of a purpose in ONE `resolveMany` at PLATFORM scope (no context, so a COUNTRY or MARKET override is allowed by the definition but never read, DEBT-0079), with NO code default, and parses them strictly (`parseConsentPolicy`: an array of distinct role codes of the right shape, at most 10; a mode from the closed list). A missing, unreadable or invalid value fails the operation closed: `AccountError UNAVAILABLE` with reason `POLICY_INVALID` or `POLICY_UNREADABLE`, answered `503 ACCOUNT_UNAVAILABLE`. `accept` does not read the policy; `withdraw` reads it only for an ACTIVE purpose; `getRequirements` reads it per evaluated purpose.

## API

Under `/api/v1`, tag `consent`, every route behind `requireAccount()` (web identity context, ACTIVE account; a revoked session is `401 SESSION_REVOKED`). No route accepts an account id, subject or role; the time is the server's. Every response, errors included, is `Cache-Control: no-store`. Bodies are validated raw and strictly (`strictBody`, body limit 2048 bytes); the guard order is 401, 403, 400 for the path parameter or query, 400 for the body.

| Operation (`operationId`) | Method and path | Notes |
|---|---|---|
| `getAccountConsents` | GET `/account/consents` | no query at all. `current`: one row per purpose that is ACTIVE or has events (`state` NONE/ACCEPTED/WITHDRAWN from the latest event, structural `withdrawable`, `latest`); `history`: every event newest first, capped at `CONSENT_HISTORY_LIMIT` (200); each event holds the version id, number, locale and hash, never the text |
| `getAccountConsentRequirements` | GET `/account/consents/requirements?locale=` | only `locale`, once, a locale tag of 2 to 35 characters; the evaluation above |
| `acceptAccountConsent` | POST `/account/consents/{purpose}/accept` `{versionId, locale, bodySha256}` | strict body; `versionId` a UUID (lower-cased), `locale` compared exactly, `bodySha256` lower-case hex; 200 for a new acceptance and for the idempotent repeat (`changed` false) |
| `withdrawAccountConsent` | POST `/account/consents/{purpose}/withdraw` | no body, or exactly `{}`; 200 also for the idempotent repeat |

`{purpose}` must match `^[A-Z][A-Z0-9_]{1,63}$` (otherwise `400 VALIDATION_FAILED`, issue `params.purpose`, the value never echoed); a well-formed unknown code is `404 ACCOUNT_CONSENT_PURPOSE_NOT_FOUND`. `details` of a consent error hold ONLY `messageKey` (`account.consent.error.<code>`), plus `outstanding` (purpose codes, at most 50, each well-formed) for `CONSENT_REQUIRED`; no version id, locale, hash or service message is ever echoed. Other typed account errors from these routes keep their code and status, but the message becomes a fixed text and `details` shrink to short `reason` and `field` tokens.

| Code | HTTP | Category | When |
|---|---|---|---|
| `ACCOUNT_CONSENT_PURPOSE_NOT_FOUND` | 404 | NOT_FOUND | unknown purpose |
| `ACCOUNT_CONSENT_VERSION_NOT_FOUND` | 404 | NOT_FOUND | unknown version, another document's, not published (any status), not PLATFORM scope: ONE answer, nothing about unpublished text is disclosed (a nil UUID is the same) |
| `ACCOUNT_CONSENT_PURPOSE_INACTIVE` | 409 | CONFLICT | accepting a retired purpose |
| `ACCOUNT_CONSENT_VERSION_NOT_CURRENT` | 409 | CONFLICT | published but superseded or not yet effective (an old version arriving after a newer acceptance is also this) |
| `ACCOUNT_CONSENT_LOCALE_MISMATCH` | 400 | VALIDATION | the claimed locale differs from the version's |
| `ACCOUNT_CONSENT_HASH_MISMATCH` | 400 | VALIDATION | the claimed hash differs from the version's |
| `ACCOUNT_CONSENT_NOT_WITHDRAWABLE` | 409 | CONFLICT | the purpose is `NOT_WITHDRAWABLE` (checked first) |
| `ACCOUNT_CONSENT_NOT_ACCEPTED` | 409 | CONFLICT | nothing accepted to withdraw |
| `ACCOUNT_CONSENT_REQUIRED_FOR_ROLE` | 409 | CONFLICT | withdrawing a purpose a considered role requires |
| `ACCOUNT_CONSENT_REQUIRED` | 409 | CONFLICT | raised by `requireConsents` only (a future gated action); no route raises it today; `details.outstanding` |
| `ACCOUNT_UNAVAILABLE` | 503 | DEPENDENCY | database, policy or default locale unavailable (generic) |
| `ACCOUNT_VALIDATION_FAILED` | 400 | VALIDATION | for example `reason` `INVALID_LOCALE` on the requirements read |
| `ACCOUNT_CONFLICT` | 409 | CONFLICT | a sequence collision that is not the same acceptance (`CONCURRENT_UPDATE`, retryable; practically unreachable under the account lock) |
| `ACCOUNT_SUSPENDED` / `ACCOUNT_CLOSED` | 403 | AUTHORIZATION | the account cannot act (also refused by `requireAccount()` before the service) |

OpenAPI documents only 200 and the generic 400, 401, 403, 404, 409 and 503; the per-operation codes are in each summary. AsyncAPI documents `IdentityConsentAccepted` and `IdentityConsentWithdrawn`. Both are GENERATED (`pnpm specs:generate`); never hand-edit them.

The consent routes are NOT rate limited. That gap is DORMANT today (both seeded purposes are `NOT_WITHDRAWABLE` and a repeated accept is an idempotent no-op, so an account can append at most one event per published version) and MUST be closed BEFORE the first `WITHDRAWABLE` purpose is seeded (DEBT-0081). `GET /account/me` carries no consent summary on purpose (it would add configuration reads to a hot read); `GET /account/consents/requirements` carries `satisfied`.

## The web page and its guarantee

`/consents` (server component, `force-dynamic`, `noindex`) shows what the signed-in person must accept, the legal text, an Accept control and the history. **Guarantee: Accept is offered only for the text that was verified to be the version in force, and what is posted is exactly that version.** For every purpose whose status is `OUTSTANDING` or `REACCEPTANCE_REQUIRED` the page fetches the text from the PUBLIC content resolver (`resolveContent({ key: document.entryKey, locale: document.locale })`) and offers the Accept form only if the resolver returns `contentType` LEGAL, `resolvedLocale` equal to the requirement's locale, and a `versionId` AND `bodySha256` exactly equal to the requirement's `document` (and a non-empty value). Otherwise (registry down, a newer or older version served, a hash that differs) it shows the registry copy `account.consent.document.unavailable_note` and NO form. The hidden fields `purpose`, `versionId`, `locale`, `bodySha256` come from that verified document; the API verifies them again against the immutable version and refuses a forged or stale form (`LOCALE_MISMATCH`, `HASH_MISMATCH`, `VERSION_NOT_CURRENT`). `format: 'html'` values are rendered as the content layer does; `text` values are never injected unescaped.

Other rules of the page (PRD R-13): no checkbox, nothing pre-ticked or auto-submitted, no script, no GET that changes state; accepting is always an explicit POST. A Withdraw form appears only when the purpose is withdrawable, the state is ACCEPTED and no role requires it. A withdrawable purpose that is NOT required has no Accept form (only `OUTSTANDING` and `REACCEPTANCE_REQUIRED` get one), so after a voluntary withdrawal it cannot be re-granted from this page (DEBT-0080). The history shows purpose, event, version number, language, time and a 12-hex-digit shortened hash; no event id, source or account id. A notice (`?notice=accepted|already_accepted|withdrawn`) is shown only when the data proves it; an unknown `?error=` word shows the generic message. All copy comes from the registry (`account.consent.*`); an element whose copy cannot be served is omitted, the sign-in control falls back to the bootstrap text. `/session` links to the page for signed-in users.

BFF handlers (`apps/web/src/lib/auth/consent-handlers.ts`): `POST /auth/consents/accept` (fields exactly `purpose`, `versionId`, `locale`, `bodySha256`) and `POST /auth/consents/withdraw` (field `purpose`). Non-POST is 405, a wrong `Origin` is 403, a signed-out caller is `303 /session`, a missing, extra, repeated or malformed field is 400 and changes nothing. The result is `303 /consents?notice=...` or `?error=ACCOUNT_CONSENT_<CODE>` (a closed list of the consent codes; anything else is `API_ERROR`); nothing a person submitted is placed in a redirect, cookie or log. `401 SESSION_REVOKED` ends the local session (`endRevokedSession`). No step-up is required for consent.

## Signup-readiness services

`ConsentOperations` offers three calls for flows that must gate on consent: `listOutstandingConsents(accountId, options?)` (the required purposes that are not satisfied, as requirement objects), `hasRequiredConsents(accountId, options?)` (boolean) and `requireConsents(accountId, options?)` (throws `AccountError('CONSENT_REQUIRED', ..., { outstanding })`). `options` are the `getRequirements` options: `locale` and `purposes`. The three gate calls REFUSE an explicitly EMPTY `purposes` list (`VALIDATION_FAILED`, reason `INVALID_FIELD`, field `purposes`): an empty list would silently pass the gate (`getRequirements`, a read, simply evaluates nothing for it). An account with no PENDING or ACTIVE role has every purpose `NOT_REQUIRED`, so a gating flow must grant the role first and pass an explicit, NON-EMPTY `purposes` list. **No flow calls them yet** (DEBT-0076): there is no sign-up screen (CU-03) and no provider onboarding (PR-01), and `requireConsents` has no caller.

How a future flow uses them: the sign-up or onboarding screen reads `getAccountConsentRequirements` (or the services in-process), shows each `document` and its text (verified as the page above does), posts `acceptAccountConsent` for each ticked-by-the-person purpose, then gates the next step on `hasRequiredConsents` / `requireConsents(accountId, { purposes: ['TERMS_OF_SERVICE', 'PRIVACY_POLICY'], locale })` (the role granted first, the purposes explicit and non-empty, the locale the flow actually shows). A provider flow evaluates the account's PENDING provider role the same way, so the provider's agreements appear as soon as the role is requested. The flow must treat `DOCUMENT_UNAVAILABLE` as "cannot proceed yet" and never as "nothing required". The service is in-process only; do not expose it through an account id.

## Adding a purpose

A new purpose (an independent-business acknowledgement, marketing email, the admin confidentiality policy) is ONE migration, forward-only, in this order:

1. the LEGAL entry shell, created exactly as `0013` does (content type LEGAL, owner LEGAL, PUBLIC, CRITICAL, `SECOND_APPROVER`, `EXACT`, max scope PLATFORM, the `ENTRY_CREATED` audit row); Legal publishes its versions later through the content workflow;
2. the `identity.consent_purposes` row (`purpose_code`, `document_entry_id`, `withdrawal_policy`: `WITHDRAWABLE` for an optional consent, `NOT_WITHDRAWABLE` for a condition of the service; status `ACTIVE`);
3. the two parameters `consent.<purpose lower case>.required_for` and `consent.<purpose lower case>.reacceptance`, through the real change workflow, same definitions as 0013 (an empty `required_for` for an optional purpose is valid and means NOT_REQUIRED for everyone);
4. the copy: `account.consent.purpose.<purpose lower case>` (the label the page and the history render), through the real content lifecycle.

Then run the Data Model Review Gate (DATA_MODEL, DATA_DICTIONARY, NORMALIZATION_LOG, snapshot). No code change is needed for the model, the API or the evaluator; the page iterates the purposes it receives. A purpose code must match `^[A-Z][A-Z0-9_]{1,63}$` and a purpose is never deleted. Optional consents are never pre-ticked (R-13): a flow that offers one must present an unticked control. Note the page does not yet offer Accept for a purpose that is not required (DEBT-0080). **Hard precondition for the first `WITHDRAWABLE` purpose: a rate limit on accept and withdraw** (a Valkey limiter keyed per account, limit from configuration, failing closed) must exist first, because a withdrawable purpose is the only way to append events without bound (DEBT-0081, DEBT-0080).

## Privacy

Never stored in consent rows, audit `changes`, events, logs, errors or responses: the legal text; a raw IP address; the user agent; a client timestamp; a token; the Keycloak `sid`, subject or any identifier of the login; the hash or version id the client CLAIMED, when it was wrong (errors are fixed messages with a message key). What IS stored per acceptance: account id, purpose, sequence, type, version id, locale, the SHA-256 of the text, the database time, the optional application session id (the registry's own id, not the `sid`) and the correlation id. A hash of a public document is not secret; the owner sees it. Logs carry codes and ids only (the only service log line is `consent policy unavailable` with the purpose code). `GET` responses concern one person's legal acceptances and are `no-store`. Consent rows and their audit are never purged: a legal record may have to be kept against an erasure request, a policy decision that does not exist yet (DEBT-0081, DEBT-0045, DEBT-0057).

## Evidence: what the hash covers

The hash and the version id identify the SOURCE (the template body) of the legal version, which is immutable. The page shows the rendered, sanitized HTML (or text) of that same version. So the evidence of an acceptance is the immutable source version (id, locale, hash); the rendered output is a deterministic function of the source and of the renderer version, and the renderer is not part of the record. A pinned rendering test in the API integration test (a LEGAL markdown fixture with its expected HTML) fails on purpose when the renderer or the sanitizer changes the output of a legal document, so such a change is a conscious decision. A stronger design, comparing a hash of the rendered output at accept time (and storing it), is future work (DEBT-0078).

## Operations and troubleshooting

| Symptom | Likely cause |
|---|---|
| every required purpose is `DOCUMENT_UNAVAILABLE`, `satisfied: false`, no Accept form | no version of the LEGAL entry is in force in the evaluated language (and the lenient modes did not already satisfy it): Legal has not published one (a fresh environment, CI), the version is scheduled for later, the locale is inactive, or the person's language has no translation (legal documents never fall back). Publish through the content workflow |
| the page shows `document.unavailable_note` although `document` is set | the PUBLIC resolver did not return that exact version (id, hash, locale, LEGAL): registry outage, or a publication raced the page load; reload |
| `409 ACCOUNT_CONSENT_VERSION_NOT_CURRENT` on a form that was just shown | a newer version took effect between the page load and the POST; reload and accept the current one |
| `400 ACCOUNT_CONSENT_HASH_MISMATCH` / `LOCALE_MISMATCH` | the posted values are not those of the version (forged, or edited form); never repaired |
| `404 ACCOUNT_CONSENT_VERSION_NOT_FOUND` for a version you can see in the content console | it is not published, not PLATFORM scope, or belongs to another document |
| `503 ACCOUNT_UNAVAILABLE` on the requirements read | a `consent.*` parameter is missing or invalid, a `required_for` role does not exist, the registry cannot be read, or there is no platform default locale |
| `409 ACCOUNT_CONSENT_NOT_WITHDRAWABLE` for the Terms or Privacy Policy | by design: both seeded purposes are `NOT_WITHDRAWABLE` |
| a person must accept again after changing language | `REACCEPT_REQUIRED` and `REACCEPT_FOR_NEW_USERS_ONLY` compare against the evaluated language (DEBT-0079) |
| after a new version everyone is `REACCEPTANCE_REQUIRED` | that is the seeded `REACCEPT_REQUIRED` mode; change `consent.<purpose>.reacceptance` through a change request if Legal decides otherwise |
