# Identity (Keycloak, tokens, sessions)

## Purpose

Work with BananaGig authentication and authorization: the Keycloak realm, token validation in the API, the web session, test identities, and the application account (account, external identity link, application roles, active role, core profile, email and phone contacts and their verification) that a verified identity maps to.

## When to use

- Changing the realm file, a client, a role, a scope or MFA policy.
- Protecting an API route, adding a guard, or reading the caller's identity.
- Changing web login, session or logout behavior.
- Writing tests that need a signed-in user.
- Anything that reads or changes the application account: bootstrap, roles and memberships, the active role, the status machine, the core profile.
- Anything that reads or changes the email contact or its verification: adding or changing the address, the code and magic link, resend and attempt limits, the trusted-identity-provider rule, the email events and audit, the verification screen.
- Anything that reads or changes the phone contact or its verification: adding or changing the number, E.164 canonicalization and the country, the SMS code, resend and attempt limits, the accounts-per-number and line-type policy, the SMS and phone-intelligence adapters, the phone events and audit, the derived `contacts` summary, the trusted-proxy hop count behind the source-address limit.
- Anything that reads or changes application sessions, devices and the trusted browser, "sign out everywhere", the second factor (authenticator app, recovery codes), step-up guards, the Keycloak service account or admin client, the web browser flow of the realm, the security timeline, or the password reset (ID-004).

## Architecture rules

- Keycloak owns authentication only; accounts, profiles, application roles and permissions belong to the BananaGig database, linked by the immutable issuer and `sub` in `identity.external_identities` (ADR-0013, ADR-0025). Never key data by username or email. The subject is NOT a column of `accounts` and is never the account id.
- The account is created lazily at the FIRST authenticated request of the normal web context (`requireAccount()`), in one transaction, status `ACTIVE`; the unique key `(provider_type, issuer, provider_subject)` decides a race (the loser rolls back and re-reads). Initial roles come ONCE from the token realm roles (`BOOTSTRAP_ROLE_BY_IDENTITY_ROLE`: `customer` to `CUSTOMER`, `provider` to `PROVIDER`) and are never read again; PostgreSQL is the only authority for application roles (DEBT-0044).
- Roles are reference data; membership is one row per (account, role); the preferred (primary) role is a composite foreign key to the account's own membership plus triggers. The ACTIVE role of a request is context, NOT persisted: the web server session keeps it and sends `x-active-role`, and the API validates it against the ACTIVE memberships on every request (403 `ACCOUNT_ROLE_NOT_HELD` or `ACCOUNT_ROLE_NOT_ACTIVE`). Switching role never creates a Keycloak login or session (ADR-0026).
- Concurrency: one lock order (the ACCOUNT row first with `FOR UPDATE`, then the ROLE row `FOR SHARE`, then the membership, identity and profile rows of that account), natural uniqueness for idempotency. Privacy: no client-supplied account id, subject or role; no token, name or subject of the account's login in logs, audit `changes`, events, errors or responses (an actor `account:<id>`, `system:<name>` or `admin:<subject>` names WHO acted and is not the subject of the account being changed); `mapDbError` logs only the SQLSTATE or error class of an outage; admin logins have no account (403 on account routes). Account routes send `Cache-Control: no-store`.
- Status and events: `accounts.status` plus the immutable `account_status_history` are kept consistent in both directions by two deferred constraint triggers that read the CURRENT status at commit (a transient status passes, a stray row or a broken `from_status` chain fails); closing an account audits `ROLE_DEACTIVATED` per membership and `PRIMARY_ROLE_CHANGED` when it clears a primary role, and `account-role-deactivated` is emitted only for a membership that was ACTIVE.
- Browsers use Authorization Code + PKCE S256 with a server-side session; tokens never reach the browser; no implicit flow, no password grant, no client secret on browser clients (ADR-0014).
- Identity roles (`customer`, `provider`) are not application permissions. Admin is a separate client with a client role and its own flow (ADR-0015). Admin tokens carry no customer/provider roles.
- Authorization is enforced in the API on the server. UI hiding is not security.
- Tokens carry minimal claims: sub, iss, aud, exp, iat, azp, typ, sid, acr, scope, roles. Never add email, phone, names or internal ids.
- The realm file is the single source of truth. The password grant exists only on the dev-only client (`bananagig.devOnly`).
- Email ownership (ADR-0027): BananaGig owns the marketplace contact (`identity.email_contacts`); the Keycloak email claim is never trusted or copied. An address is VERIFIED only by proof (code or magic link) or because a TRUSTED identity provider reported it verified: `decideIdpEmail` requires a canonical address, `email_verified === true` (boolean) AND a brokered provider in the caller's `trustedProviders` (empty by default; a Keycloak realm user never counts). Anything else is a suggestion and is never persisted.
- ONE canonical form (`canonicalizeEmail`): trimmed, domain IDNA lower-case ASCII, local part a lower-cased ASCII dot-atom, dots and `+tags` kept (no Gmail folding), at most 254 characters. It is the comparison key, the uniqueness key and the delivery address; never store a second form. Return the address only MASKED (`maskEmail`), only to its owner, and never in a log, audit `changes`, event or error.
- Uniqueness is the database's: a VERIFIED address belongs to one account (partial unique index); PENDING duplicates across accounts are allowed (a pending claim proves nothing and must not reveal who holds the address); one primary, one open candidate and one live row per address per account. A proven mailbox that another account verified is `ACCOUNT_EMAIL_UNAVAILABLE`, never a takeover; add and send answer identically whatever another account holds.
- Challenge lifecycle (ADR-0028): one challenge per SEND (a resend supersedes the open one); the code (CSPRNG digits) and the 256-bit token are shown once and stored only as HMAC-SHA-256 keyed with `VERIFICATION_HASH_SECRET` (code hash bound to the challenge id, constant-time compare); single use under the row lock (account row, then contacts, then challenge `FOR UPDATE`); wrong attempts counted under that lock and committed although the call fails; the attempt that reaches the maximum locks the challenge; a repeated successful confirmation is an idempotent success with no second side effect.
- The magic link carries the token in the URL FRAGMENT (`/verify-email#token=`): never sent to a server, so in no log, trace or Referer. Opening it verifies nothing; the page shows a button and the web server POSTs the token in a body. Never put a code or token in a query string, a redirect URL, a cookie or a log.
- Sending is two-phase: commit the challenge, deliver through the `EmailSender` port OUTSIDE any transaction, then record the outcome; a failed delivery invalidates its challenge (`DELIVERY_FAILED`) and does not start the cooldown. The identity service never touches SMTP or a template engine: the composition root supplies the sender and the content-registry renderer.
- Limits are CFG-001 parameters (`verification.email.*`, CRITICAL, read fresh, fail closed when unavailable). The cooldown, hourly and daily caps and the attempt maximum are counted in PostgreSQL per ACCOUNT; the reusable Valkey limiter (ADR-0029) adds source address, target address and device. It fails CLOSED for operations that send mail and open only for confirmation. A refusal never names the dimension.
- Change email: the new address is `REPLACEMENT_PENDING`; the verified primary stays VERIFIED and primary until the candidate verifies, then the old one is `DISABLED/REPLACED` in the same transaction. Setting the primary again withdraws a pending change; a different address supersedes the pending one. Step-up authentication, the notice to the old address and the screens are later (DEBT-0050).
- Phone ownership (ADR-0031): BananaGig owns the phone contact (`identity.phone_contacts`); Keycloak is NOT a phone store (no phone claim, never written to Keycloak, a token, an event or a log). A number is VERIFIED only by the SMS code: there is no trusted-provider shortcut and a contact is never created VERIFIED (`source` has the single value `USER_ENTERED`). The lifecycle is the email one (`PENDING`, `REPLACEMENT_PENDING`, `VERIFIED`, `DISABLED`); the verified primary stays active until its replacement verifies.
- ONE canonical form (`canonicalizePhone` in `packages/accounts/src/phone.ts`): E.164 produced over libphonenumber-js (pinned, `min` metadata). Never write a custom dialing rule or a hardcoded calling code. Input is NFKC-normalized and restricted to digits and punctuation (letters and extensions are refused); the number must be VALID for its numbering plan; the ISO country is resolved FROM THE NUMBER (a +1 416 number is CA), never from the hint; an international number ignores the hint. A national number needs the caller's country or the only ACTIVE country in geography. Then geography decides availability: the country must be ACTIVE and its configured dialing code must equal the number's calling code. No second form (national, formatted) is stored. The number leaves the server only as `maskPhone` (`+*******0142`), to its owner.
- Delivery and intelligence are ports (ADR-0032). `SmsSender` (`RenderingSmsSender` renders `sms.verification.phone.body` from the content registry, then hands the text to an `SmsTransport`). Adapters: `ValkeyFakeSmsTransport` (`SMS_TRANSPORT=fake`, DEV/TEST only, holds the plaintext code in a Valkey list with a 15-minute TTL, refused in production, read by `FakeSmsInbox`) and `DisabledSmsTransport` (the production default; every send fails as non-retryable `ACCOUNT_PHONE_DELIVERY_FAILED`). `PhoneIntelligence` classifies a number: `FakePhoneIntelligence` (DEV/TEST) picks the line type from the last three digits (901 VOIP, 902 VIRTUAL, 903 LANDLINE, 904 HIGH_RISK, 905 the lookup fails, otherwise MOBILE); `UnknownPhoneIntelligence` (production default) returns UNKNOWN. The lookup fails CLOSED: an error or more than five seconds is `PHONE_RISK_UNAVAILABLE` and nothing is stored or sent.
- SMS challenge (ADR-0030): the hardened email challenge WITHOUT a magic link. One challenge per send; the code (`verification.phone.code.length` CSPRNG digits) is shown once in the SMS; only an HMAC-SHA-256 bound to the challenge id and keyed with `VERIFICATION_HASH_SECRET` is stored, in its own hash domain `bananagig:phone-code:v1` (a hash can never verify in the other channel); the primitives shared with email are `verification-crypto.ts` and `verification-core.ts`, everything else is per channel. A code of an earlier SMS (superseded by a resend) is answered "used or replaced" and costs no attempt. Lock order: account row, the account's phone contacts, the challenge row, then the advisory lock of the number.
- Phone limits differ from email: besides the PostgreSQL cooldown, hour, day and attempt counts per ACCOUNT, Valkey counts requests per account, source address and device (`requests.max_per_hour`) AND SMS to one NUMBER across all accounts (`number.max_per_hour`; the key is an HMAC of the E.164, never the raw number), because an SMS costs money and pumping targets a number. Setting the number and sending fail CLOSED when the limiter is unreachable; confirmation fails open. A send refused by the cooldown or a cap is detected BEFORE the limiter is consumed, so a refused request never spends the per-number budget. A refusal never names the dimension.
- Accounts per number is DATA, not an index (ADR-0031): `verification.phone.max_accounts_per_number` (default 1, overridable per COUNTRY and MARKET). Pending duplicates are always allowed and never counted. At the correct code the service takes `pg_advisory_xact_lock` on the number, counts the OTHER accounts holding it VERIFIED and refuses with `409 ACCOUNT_PHONE_UNAVAILABLE` only AFTER a correct code (before that, add and send answer identically whatever any other account holds: no enumeration, no takeover; recovery is a support process, DEBT-0061). It passes the value in the transaction setting `app.phone_max_accounts`, and the guard trigger takes the same lock and enforces it, with a structural ceiling of 5, so raw SQL cannot exceed it.
- Line-type policy (`verification.phone.blocked_line_types`, default `["VIRTUAL","HIGH_RISK"]`, MOBILE never blockable): read for the number's country; when the list is not empty the number is classified BEFORE anything is stored or sent (`PHONE_NOT_ACCEPTED` carries no line type). The result is stored on the contact as a snapshot (`line_type`, `line_type_checked_at`) and re-applied at send and confirm without calling the vendor again, so tightening the policy affects pending numbers. An empty list means no lookup at all.
- Privacy: no code, hash or full number in a log line, an audit `changes` object, an event, an error or a response (only the masked number, ids, statuses, country, line type and attempt numbers); the fake sink is the only place a plaintext code exists and it is DEV/TEST only. `GET /account/me` carries `phone` (masked) and `contacts` (`emailVerified`, `phoneVerified`, `contactsVerified`), DERIVED at read time by `deriveContactsVerification` from the two statuses; there is no `contacts_verified` column, so it cannot drift. ID-003 stores and exposes state and gates nothing (booking and provider onboarding gates will read the summary).
- Source address (ADR-0033, DEBT-0055): `request.ip` is the address that exactly `TRUSTED_PROXY_HOPS` proxies away from the socket (Fastify `trustProxy` is the function `trustHops`: `hop < hops`), so with 1 hop it is the LAST `X-Forwarded-For` entry, with 0 the socket; the client-chosen leftmost entry is never read. Caddy REPLACES the header (`header_up X-Forwarded-For {remote_host}`), the web server forwards one value (`clientIpOf` takes the last entry) and the API is reachable only through the proxy. Production must set `TRUSTED_PROXY_HOPS` explicitly (configuration requires it for the API role there); outside production it defaults to 1.
- Sessions (ADR-0034): `requireAccount()` resolves the verified token's `sid` to a row of `identity.application_sessions` on EVERY request (one statement; created on first sight); a revoked row, or a `sid` that belongs to another account, is `401 SESSION_REVOKED` at once, which is why "sign out everywhere" works within a second although access tokens live 300 s. The database row is authoritative; Keycloak is told AFTER the commit, best effort, and the result is reported (`keycloak`: `ENDED | UNAVAILABLE | NOT_NEEDED`). Never store a token; never log, return, audit or put the `sid` in an event (the API hands out the application session id). Active or ended is DERIVED, never a status column.
- The revocation watermark `identity.accounts.sessions_not_before` only gates a session FIRST SEEN after a revoke-all (its `auth_time` is older, with 2 s of skew tolerance); first sight takes the account row `FOR SHARE`, revoke-all `FOR UPDATE`. Lock order for the security tables: account row, then device row, then session rows.
- Keycloak owns the factors (ADR-0036): BananaGig stores no TOTP secret and no recovery code; it asks `SecurityIdentityProvider` (the Keycloak admin client of the service account `bananagig-security`, ADR-0035) and OBSERVES transitions (`MFA_ENABLED`, `PASSWORD_CHANGED`, ...) by comparing with the last audit action under the account lock; a factor already present at first sight is a baseline, not a transition. Enrolment goes through `kc_action` (`CONFIGURE_TOTP`, `CONFIGURE_RECOVERY_AUTHN_CODES`).
- NEVER trust `acr_values`, `claims` or any authorization parameter that travels through the browser: the browser can drop or change them and Keycloak ignores `acr_values` for a user without a factor. The second factor is enforced INSIDE the flow (`bananagig-browser` bound to `bananagig-web` plus the client attribute `minimum.acr.value=bananagig:mfa`) and the API reads `auth_time` and `acr` from the VERIFIED token (`step-up.ts`). The web client's `stepUp` and `kcAction` login parameters come from closed lists; a step-up is ONE round trip (the login transaction records it and the callback verifies the token instead of starting another) and a `kc_action` needs the one-shot enrollment marker the API-accepted `POST /auth/security/mfa-enroll` left for that browser session.
- Step-up guards (`requireRecentAuthentication()`, `requireMfa()`, `requireStepUp(requirement)`): list them AFTER `requireAccount()` and BEFORE `strictBody` in `preValidation`. They answer `401 STEP_UP_REQUIRED` in RFC 9470 shape (`WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age, acr_values`, `details` = `StepUpDetails`), `403 MFA_ENROLLMENT_REQUIRED` when the person has no factor, and fail closed (`503`) when Keycloak cannot be asked. The window is `security.step_up_valid_minutes`, read per request. A trusted browser NEVER satisfies a guard.
- The trusted browser is a RECORD: `identity.account_devices.trusted_until` (config `session.trusted_browser_days`) is shown and expires, but it does NOT change when Keycloak asks for a code (Keycloak cannot skip OTP per device without a custom extension, DEBT-0066). Say so in every copy and API summary; do not build UI that implies otherwise.
- Device cookie contract: `bg_device` / `__Host-bg_device` (https), HttpOnly, SameSite=Lax, Path=/, 400 days, 43 base64url chars; sent once per login in a request BODY; stored only as `HMAC-SHA-256(VERIFICATION_HASH_SECRET, 'bananagig:device:v1', account_id, secret)`; the first device of a session wins; a removed device is terminal (the web server rotates the cookie); the user agent becomes three closed families and is discarded.
- Password reset: public `POST /auth/password-reset`, ALWAYS the same `202`; rate limits `password-reset:email|ip` that fail CLOSED; everything that depends on the address belonging to an account (lookup by the canonical VERIFIED email, audit, Keycloak calls) runs DETACHED so the caller waits for identical work; the link is sent by Keycloak only when Keycloak's own address equals the verified one. Keycloak 26.3.5 has no native "sign out other devices on password change", so the service revokes older sessions (`PASSWORD_CHANGED`) when it observes the new password.
- Realm lint rules (`scripts/lib/realm.mjs`): service accounts only on `bananagig-security` with exactly `manage-users`; a realm file that declares `requiredActions` REPLACES Keycloak's defaults, so the product actions are listed and enabled and `delete_credential`, WebAuthn registration and `idp_link` are disabled (any client can start `kc_action=delete_credential`); the built-in `account` and `account-console` clients are declared disabled (an undeclared one is created enabled); the web flow, the MFA floor and `acr.loa.map` must agree; the production build keeps the service-account user (dropping it drops the role mapping), strips the dev secret and the dev SMTP server.

## Implementation pattern

1. Protect a route: `preHandler: requireAuthenticated()` or `requireRealmRole(...)` / `requireAnyRole(...)` / `requireClientRole(client, role)` / `requireAuthContext('admin')` from `apps/api/src/plugins/auth.ts`; declare `security: [{ bearerAuth: [] }]` in the route schema (public routes declare `security: []`), then `pnpm specs:generate`.
2. Read identity: `request.principal` (subject, clientId, realmRoles, clientRoles, authContext). Never log or return the token.
3. Change the realm: edit the JSON, `pnpm identity:check`, `pnpm identity:sync`, then integration tests and smoke. Add a policy rule in `scripts/lib/realm.mjs` plus a test when a new rule matters.
4. Need a signed-in user in a test: forged tokens (`createTestKeys`, `signToken`) for unit tests; `authorizationCodeLogin` (real PKCE) or `devAccessToken` for integration tests.
5. Protect a route that needs the account: `preValidation: [requireAccount({ includeProfile? }), strictBody(Schema)]`, read `request.account` (`activeRole`, `roles`, `status`), never `request.principal.realmRoles`, and never accept an account id or role from the client. A role is granted only by `AccountService.grantRole` from server code; there is no grant endpoint.
6. Email operation: take the account from `requireAccount()`, validate the body with `strictBody(Schema)` (a code or token is never coerced), call `EmailVerificationService` with `{ clientIp: request.ip }`, map `AccountError` through `toAppError` (429s carry `Retry-After`), answer `no-store`. A new email error code goes into `EMAIL_ERROR_CODES`, `toAppError`, the content seed (`account.email.error.<code>`) and the error-mapping table test.
7. Phone operation (`apps/api/src/modules/account/phone-routes.ts`): same shape as 6 with `PhoneVerificationService` and `{ clientIp: request.ip }`; a new phone error code goes into `PHONE_ERROR_CODES`, `toAppError`, the content seed (`account.phone.error.<code>`) and the error-mapping table test. A new SMS goes through `RenderingSmsSender` and a managed `sms.*` entry, never a string in code. A new vendor is one `SmsTransport` class (or one `PhoneIntelligence` class) plus the `SMS_TRANSPORT` / `PHONE_INTELLIGENCE` value; the policy that blocks line types stays configuration.
8. Protect a route with a step-up (ID-004): `preValidation: [requireAccount(), requireRecentAuthentication() /* or requireMfa() */, strictBody(Schema)]`; the client reacts to `401 STEP_UP_REQUIRED` with one login round trip (`/auth/login?returnTo=...&stepUp=recent|mfa`) and the person repeats the action. Add the route to the security module (`apps/api/src/modules/security/routes.ts`) or call the guard from another module; email and phone changes are not protected yet (DEBT-0050, DEBT-0062).
9. A new security audit action or event: add it to `SECURITY_AUDIT_ACTIONS` / `SECURITY_EVENTS` (contracts), widen `ck_account_audit_events__action` in a NEW migration (never edit 0012), seed `account.security.activity.<type>` copy, and keep the `SESSION_`/`DEVICE_` prefix to reference checks in mind. The timeline is a filtered read of the audit log, never a copy.
10. A new Keycloak call: add it to `KeycloakAdminClient` and the `SecurityIdentityProvider` port (and `FakeSecurityIdentityProvider`), reduce failures to a CODE, and check whether `manage-users` still suffices; widening the service account's roles needs a linter change and an ADR note.

## Testing requirements

- Unit: forged tokens for every rejection category (none, HS256, wrong key, issuer, audience, expired, not-before, wrong type, missing claims); guards (401 before 403); logs never contain token segments.
- Integration (live Keycloak): real PKCE login per user, wrong verifier and code reuse rejected, redirect URI exact match, implicit/plain/missing-PKCE refused, password grant refused for production clients, claim allow-list, admin context separation, logout invalidates refresh.
- Web: PKCE verifier matches the challenge, state/nonce/replay checks, cookie attributes, CSRF-safe logout, no browser storage in source.
- Account: first-request bootstrap with real tokens, N parallel first requests give exactly one account (repeat the run), idempotent grants, active role not held or not active, suspended and closed accounts, admin context refused, strict bodies (coerced-body regression table), status history at commit (transient status, stray row, `from_status` gap), closure audit rows and events, and privacy by log capture (no token, subject or name in the output).
- Email: canonicalization tables, masking, strict request validation (no coercion), crypto (CSPRNG, keyed hashes, constant-time compare), the trusted-provider table, expiry through crafted rows (never sleeps), single use, the attempt race (concurrent wrong codes never exceed the maximum), code versus link racing, resend racing verify, replacement races, duplicate verified across accounts (including the race), cooldown and hour/day caps with a fake policy, limiter fail-closed versus fail-open, delivery failure, audit/outbox/log scans for the plaintext code, token, hashes and the full address, Mailpit receiving the real message, and the smoke scenario.
- Phone: canonicalization tables (international and national forms, shared calling codes, extensions and letters refused, idempotence), masking, strict request validation, policy parsing, the shared primitives (with pinned email hash values so the refactor is provably neutral), the SMS and intelligence adapters, the same challenge races as email (attempts never exceed the maximum, resend racing verify), the number cap under concurrency (N parallel verifications of one number end at exactly the cap, with the trigger as the second line), line-type refusals through the fake classifier suffixes, limiter fail-closed on set/send and fail-open on confirm, a refused send not spending the per-number budget, privacy scans (no code, hash or full number in rows, logs, events or responses; the fake sink as the only plaintext), the proxy-trust semantics for 0, 1 and 2 hops, a static test of the Caddyfile, and the smoke scenario (real tokens, fake sink, a spoofed header through Caddy creating no bucket, no number or code in Loki).
- Sessions and security (ID-004): forged tokens with `signToken(keys, { sid, authTime | authTimeAgoSec, acr })` drive the registry without Keycloak (a token without `sid` is 401; revoking one `sid` refuses THAT token on its very next request on ANY `requireAccount` route while another `sid` keeps working; revocation latency under a second; a never-seen session older than the watermark is refused at first sight; a sid of another account is refused and never reassigned; isolation between accounts; SUSPENDED/CLOSED 403 before any session logic). Step-up: no, old, malformed and future `auth_time`, the exact `WWW-Authenticate`, `requireMfa` with and without TOTP and with the provider down. Use `FakeSecurityIdentityProvider` (`setUser`, `addSession`, `failNext(method, times)`, `hold(method)` to prove a caller does not wait for Keycloak, `calls`, `endedSessions`, `sentResetEmails`) and `StaticSecurityPolicyProvider`; prove the uniform password-reset answer (known, unknown, invalid, unverified, closed all identical) and that the detached work is awaited by `drain()`. Live Keycloak (`keycloak-security.itest.ts`): token claims of the web client, the admin client against the real server, the MFA floor and recovery codes (numbered, single use), the closed built-in surface. Realm linter negative tests for every rule. Privacy scans: no token, `sid`, subject, device secret, user agent, IP, address, code or link in rows, logs, events or responses.

## Data-model considerations

Schema `identity` (migrations 0009, 0010 and 0011, eleven tables) holds the application account and the email and phone contacts; see `docs/engineering/ACCOUNTS.md` and ADR-0025 and ADR-0026. Any change goes through the Data Model Review Gate (database skill). There is no users table and nothing of Keycloak (credentials, tokens, sessions) is stored; contact data is ID-002 and ID-003, address ownership is not modelled.
ID-004 (migration 0012) adds `identity.application_sessions`, `identity.account_devices`, `identity.accounts.sessions_not_before`, the wider audit action list with a session and a device reference, six configuration parameters and 86 content entries (`docs/engineering/SESSIONS_AND_MFA.md`); the schema now holds thirteen `identity` tables. Still nothing of Keycloak (credential, secret, code, token) is stored.

## Common failure modes

- Realm edits not applying: `--import-realm` skips an existing realm; use `pnpm identity:sync` or `pnpm stack:reset` (LRN-0013).
- Issuer mismatch (401 on every token): the pinned issuer is the PUBLIC URL; check `KEYCLOAK_PUBLIC_URL` and that Keycloak runs with `KC_HOSTNAME`.
- Built-in `admin-cli` re-enabling the password grant: it is disabled in the realm file (LRN-0014).
- Session cookie missing after login: SameSite must be Lax (not Strict) and redirects must use `WEB_PUBLIC_URL`.
- Login works in the stack but not in `pnpm dev`: expected (DEBT-0020).
- 403 `ACCOUNT_CONTEXT_NOT_SUPPORTED` on an account route: an admin or non-web token (account routes serve `azp` `bananagig-web` only). A person who suddenly has a new empty account: the issuer or the Keycloak user changed (the issuer is part of the link key).
- `ACCOUNT_EMAIL_RATE_LIMITED` or `UNAVAILABLE` (reason `RATE_LIMITER_UNAVAILABLE`) on a send: Valkey is the limiter and sends fail closed; `pnpm dev:deps`. `UNAVAILABLE` with reason `POLICY_UNAVAILABLE`: a `verification.email.*` parameter is missing or invalid (CRITICAL parameters never fall back).
- A code or link that worked a moment ago now says used: a resend supersedes the previous challenge; a repeated successful confirmation is an idempotent success, a superseded one is `ACCOUNT_EMAIL_CODE_USED`.
- A magic link that does nothing when opened signed out: the fragment does not survive the login redirect; sign in, then open the link again.
- `ACCOUNT_PHONE_DELIVERY_FAILED` on every send: `SMS_TRANSPORT=disabled` (the production default; no provider exists, DEBT-0059). For development set `SMS_TRANSPORT=fake` and read the code with `FakeSmsInbox`; the fake values are refused in production.
- `ACCOUNT_PHONE_RISK_UNAVAILABLE` or `ACCOUNT_PHONE_NOT_ACCEPTED` in development: the fake classifier picks the line type from the last three digits (901 VOIP, 902 VIRTUAL, 903 LANDLINE, 904 HIGH_RISK, 905 the lookup fails); with `PHONE_INTELLIGENCE=unknown` every number is UNKNOWN. Both are expected when the market blocks those types.
- `ACCOUNT_PHONE_INVALID` with reason `COUNTRY_NOT_SUPPORTED` for a well-formed number: its country is not ACTIVE in geography or its configured dialing code differs from the number's calling code. `COUNTRY_REQUIRED`: a national-format number with no country and no ACTIVE default.
- `ACCOUNT_PHONE_RATE_LIMITED` for a number the user has not tried: the per-number budget counts sends across ALL accounts, regardless of ownership; `UNAVAILABLE` (reason `POLICY_UNAVAILABLE` or `RATE_LIMITER_UNAVAILABLE`) as for email.
- All users behind the proxy share one source-address bucket, or a spoofed `X-Forwarded-For` creates new buckets: the first means `TRUSTED_PROXY_HOPS` is 0 or too low, the second that it is too high or that something other than the proxy can reach the API; check it against the real topology (ADR-0033).
- Every request of one browser is `401 SESSION_REVOKED`: the session was signed out elsewhere, its browser was removed, a revoke-all raised the watermark above this login's `auth_time`, or the `sid` belongs to another account; sign in again. A token without `sid` is `401 INVALID_TOKEN`.
- `mfa.available: false` on the security page or `keycloak: UNAVAILABLE` on a revocation: the admin client cannot reach Keycloak or is refused (`TOKEN_REJECTED`): wrong `KEYCLOAK_SECURITY_CLIENT_SECRET`, or the dev realm was not re-imported (`pnpm identity:sync`).
- `error=step_up_required` after the login: Keycloak issued a lower level than requested (a user with no second factor asked for `mfa`: ignored by Keycloak); enrol first.
- Password-only users are asked for their password again on every new authorization request: expected (the SSO cookie of a level-1 session is below the MFA floor). Do not gate the password form by level.
- No reset email: the address is not the verified primary email, Keycloak holds a different address, the limiter refused, or no SMTP server exists (Mailpit in development; none in a production realm build).

## Known BananaGig-specific lessons

- Tokens are issued with `iss` = public URL even when fetched through `keycloak-auth:8080` (`KC_HOSTNAME` + backchannel-dynamic, LRN-0013).
- Keycloak's client-secret endpoint returns `{"type":"secret"}` without a value for public clients; assert on `value`.
- The public auth host exposes only `/realms/bananagig/*` and `/resources/*`; the dev admin console is on `keycloak-admin.localhost` (DEV ONLY).
- Production realm: `pnpm identity:build-prod` (dev client/users removed, https origins, admin OTP required).
- Keycloak realm roles are an identity fact and a one-time bootstrap hint; the application roles in `identity.account_roles` can differ afterwards (a provider role added server-side does not change the token). A closed account is blocked permanently for its login (403 `ACCOUNT_CLOSED`) because the link is permanent.
- The admin client carries `configuration-read`, `configuration-write` and `configuration-approve` plus the original admin role; dev users `admin.dev` and `admin2.dev` hold all of them so second-approver flows can be exercised. These client roles are temporary access control until application RBAC exists (DEBT-0021).
- Hashing a 6-digit code with plain SHA-256 is reversible from a leaked table in a millisecond: the HMAC key lives outside the database. Counting sends as challenge rows (one per send) removes every counter that could drift. A deferred constraint trigger is the right place for "the whole account is consistent at COMMIT" when a replacement passes through intermediate states (LRN-0035 pattern).
- The `email_verified` flag of Keycloak is not evidence for BananaGig: an administrator or a realm import sets it. Trust is a function of the brokered provider, not of the flag alone.
- A calling code is not a country (`+1` is the US and Canada): take the country from the numbering library's resolution of the number, then cross-check availability and the dialing code against geography. A policy that is configuration (accounts per number) cannot be a unique index; see LRN-0039. `trustProxy` as a hop-count function and the proof that the proxy replaces the header: LRN-0040.
- A refusal that depends on another account's data (`ACCOUNT_PHONE_UNAVAILABLE`) is only safe AFTER the caller has proven control of the number; before that, every answer must be identical whatever any other account holds.
- Keycloak facts measured in the ID-004 lab (26.3.5): `acr_values` is ignored for users without a factor and an essential `claims` acr is not enforced for them, so enforcement must be the flow's floor (LRN-0042); a partial `requiredActions` list replaces the defaults and any client can start `kc_action=delete_credential` (LRN-0043); recovery codes are numbered and cannot be created through admin REST; `manage-users` is the minimum role for ending sessions and `execute-actions-email`; the reset form's "log out other sessions" box is unchecked by default; the user is not logged in after a reset; `refreshTokenMaxReuse` 0 loses racing refreshes, 1 tolerates them (single-flight in the web server on top); a wrong-then-right password during lock-out gets the same generic error (no oracle) and anyone who knows an address can lock a user for 15 minutes (PRD).
- A unique-per-`sid` upsert plus a revocation row needs the account-row `FOR SHARE` / `FOR UPDATE` serialization for sessions Keycloak created that the API has not seen yet (LRN-0045).

## Do not

- Do not put tokens in localStorage, cookies readable by JS, URLs or logs.
- Do not add the implicit flow, the password grant, or a client secret to a browser client.
- Do not import `@bananagig/identity/testing` from production code.
- Do not add profile, email or phone claims to API tokens.
- Do not model business permissions as Keycloak roles or mix admin capability into realm roles.
- Do not create a users table, store the Keycloak subject on `accounts`, or duplicate profile data in Keycloak.
- Do not use a Keycloak realm role as an application permission or read it after the account exists; authorize with `request.account`.
- Do not accept an account id, subject or role from the client, and do not add an endpoint that grants a role.
- Do not persist the active role, create an admin account, or log a token, a name or the subject of an account's login.
- Do not trust or copy the Keycloak email claim, persist a plain claim, or mark an address VERIFIED without a code, a link or a trusted provider's verified flag.
- Do not store, log, audit, put in an event or return a plaintext code, token, hash or full address; do not put a token in a query string; do not let a GET change state.
- Do not hardcode a code length, validity, cooldown, cap or attempt limit; do not make the limiter fail open on an operation that sends mail.
- Do not replace the verified primary before its replacement verifies, and do not transfer a verified address between accounts.
- Do not store a phone number in Keycloak or a token, mark a number VERIFIED without the SMS code, or store a second form of the number (national, formatted, as typed).
- Do not write a custom dialing rule or hardcode a calling code, a country or a default country; use `canonicalizePhone` and geography.
- Do not enable `SMS_TRANSPORT=fake` or `PHONE_INTELLIGENCE=fake` in a shared or production environment, and do not read the fake sink from production code.
- Do not hardcode the accounts-per-number, the blocked line types or any phone limit, and do not replace the per-number lock, the count and the guard trigger with a unique index.
- Do not reveal whether another account holds a number before a correct code, and do not let a refused send consume the per-number budget.
- Do not use `trustProxy: true` or read the leftmost `X-Forwarded-For` entry; do not publish the API port or put anything but the trusted proxies in front of it.
- Do not store a token, the Keycloak `sid`, a device secret, a raw user agent, a raw IP, a TOTP secret or a recovery code, and do not log or return the `sid` or the Keycloak subject; do not add an account id, subject or session id of Keycloak to any security route.
- Do not rely on `acr_values`, `max_age` or an essential `claims` parameter from the browser to enforce a factor, and do not let a trusted browser satisfy a step-up guard or imply in copy that it skips the code prompt.
- Do not enable `kc_action` without the enrollment marker, re-enable `delete_credential`, WebAuthn registration or `idp_link` without the feature, or re-enable the built-in account console or `resetPasswordAllowed`.
- Do not give `bananagig-security` more than `manage-users`, add another service account, or commit a real secret; do not make the password-reset answer, status or timing depend on whether an account exists, or send the link to any address but Keycloak's own when it equals the verified one.
- Do not call Keycloak inside a transaction or let its failure undo a revocation.
